# 2026-09-10

## The 0x80000-0x97FFF mystery region is much bigger than thought

- Mined the newly-disassembled comm ROM for far calls into the main
  ROM's address range - none were new (the combined recursive-descent
  run already resolves any in-range far call automatically), but this
  surfaced that the comm ROM makes **150+ distinct far calls** into
  the previously-flagged `0x80000-0x97xxx` region, across dozens of
  separate segments spanning all the way to `0x97C95` (~96KB total).
- Confirmed via TekWiki that there is no third ROM chip for the 2230
  (just the two 27512 EPROMs on board A10, plus the comm option ROM),
  ruling out "this is a ROM we simply don't have a dump of."
- Found direct evidence this is real, tested RAM instead: the main ROM
  contains a classic non-destructive RAM-size-test pattern (read,
  write `0xAA55`, restore) targeting `es=0x8000` - the textbook way
  period boot code detects how much memory is actually installed.
- Went looking for how code gets loaded into that RAM for the comm ROM
  to call into it (checked 2 of 5 call sites of a generic memcpy-style
  utility function, `SUB_FBC09`); didn't find it there. Still open -
  documented as a real, possibly hard limit on what static analysis of
  these three ROM dumps alone can recover, since RAM contents loaded
  at runtime (however they get there) aren't present in any ROM dump.
- Wrote up in `MEMORY_MAP.md` (including the PlantUML diagram) and
  `disasm/NOTES.md`; updated `TODO.md` with the concrete next checks
  (remaining 3 memcpy call sites, other possible loading mechanisms).
