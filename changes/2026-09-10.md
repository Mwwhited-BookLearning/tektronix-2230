## Correction: the comm ROM is NOT bank-switched

- User pushed back on the bank-switching assumption ("i dont know why
  someone would use bank switching if they have enough address space
  to not use bank switching") and asked whether the comm ROM itself
  might just be sitting in the "missing memory hole." Checked it
  directly: every far-call target landing in `0x80000-0x8FFFF` was
  tested against the comm ROM's own function-start signatures at
  `file_offset = phys - 0x80000` — **82 of 84 distinct targets land
  exactly on a known function start.** The main ROM's already-proven
  code also makes several direct far calls straight into that range.
- Corrected: `160-2998` is a plain fixed-address 64KB device at
  physical `0x80000-0x8FFFF`, same simple pattern as the two main-ROM
  halves - no bank-switching at all. This resolved most of the
  "0x80000-0x97FFF mystery region" from earlier: the lower half was
  just the comm ROM at the wrong (arbitrary bookkeeping) address this
  project had been using for it. The genuine remaining mystery is
  narrower: `0x90000` and up.
- Reworked the tooling to match: `160-2998` is now registered directly
  in `gen_disasm_x86.CHIPS` like the other two chips (no more per-page
  virtual addressing). `gen_disasm_2998.py` simplified to a thin
  heuristic-entry-point supplement on the same real address space.
  `gen_source.py` gained an `only_chips` parameter so the comm ROM's
  heuristic-assisted coverage doesn't leak confidence into the main
  ROM's proven-only `.asm` files. Regenerated and re-validated
  everything: main ROM 10,488 instructions (9,480 exact + 1,003 alt-
  encoding, 0 mismatches, comm ROM now contributing 99 proven
  instructions); comm ROM with the heuristic layer included, 20,446
  instructions (18,290 exact + 2,151 alt-encoding, 2 real mismatches
  likely decode drift into header text, 3 unconverted).
- Reaching further into the main ROM surfaced x87 FPU instructions and

  handle yet; conservatively excluded from conversion (safe raw-`db`
  fallback) rather than risk getting their NASM syntax wrong. Also
  found and fixed a genuine encoding-duplicate case (opcode `0x82`

## The 0x90000-0x97FFF region is fully resolved (address-decode alias)

- User asked whether the `0x90000-0x97FFF` targets might make sense as
  a "shadow" of `0x80000-0x8FFFF`. A plain `+0x10000` shift didn't fit
  (1/82 matched), but brute-forcing every possible base offset against
  all 82 observed far-call targets found `base=0x88000` gives **82/82
  exact matches** against the comm ROM's own function-start signatures.
  So `0x90000-0x97FFF` is the same comm-ROM bytes as `0x88000-0x8FFFF`
  (file offset `0x8000-0xFFFF`, its own upper half/pages 2-3), visible
  a second time - almost certainly incomplete address-line decoding in
  the comm ROM's chip-select logic, not a separate device.
- Wired this into the tooling: `gen_disasm_x86.CHIPS` gained a
  `"2998_alias_90000"` entry (a `slice` of the same comm-ROM file,
  mapped at `0x90000`) and `load_chips()` learned to honor `slice`.
  This alone grew the main disassembly from 10,488 to **13,510**
  proven-reachable instructions (comm ROM's own proven-reachable count
  went from 99 to 397, now that its aliased calls resolve too).
- Re-validated everything (0 mismatches after also fixing `loopne`/
  `loope`/`loopz`/`loopnz`, which had the same missing-near-branch-
  handling bug `loop` alone used to have) and regenerated all three
  `.asm` files plus the comm ROM's heuristic-included pass.

## Found: the option-board presence/RAM-detection routine

- User asked two connected questions: might the `0xAA55` pattern
  (previously read as a generic RAM-size test) be an install-check for
  the comm option card, and might it involve RAM/memory-mapped I/O on
  the comm board specifically? **Both confirmed correct - it's one
  routine (`SUB_E44F1`, `160-3633`) doing both in sequence:**
  1. Checks `ES:DI = 0x8000:0x0004` (physical `0x80004`) for a valid
     ROM-header-style checksum (byte + one's-complement = `0xFF` - the
     exact same pattern used in every ROM's own self-ID header,
     decoded on day one of this project).
  2. Only if that passes, tests whether the same address is *also*
     writable (the `0xAA55` save/write/verify/restore sequence),
     gated additionally on a config byte at `[0x1B83] == 0x1E`.
  3. Packs the result into status byte `[0x1BF9]`.
- This ties directly back to the `"Function requires options not
  installed in this instrument"` string found in `160-3532` at the
  very start of the project.
- Found this function's caller is `SUB_E416F` (`160-3633`), which
  turned out to be a **self-test dispatcher**: ~25 calls to individual
  subsystem-test subroutines in sequence, each folding a return code
  into an accumulator. `SUB_E44F1`'s call is notably NOT folded into
  that accumulator the same way its neighbors are - consistent with
  "is an option installed" being informational rather than pass/fail.
  Full call list and inferred variable roles (`[0x1B10]`, `[0x1B18]`,
  `[0x1BF9]`, `[0x1B83]`) written up in `disasm/NOTES.md`.
- Added activity diagrams for both to `JUMP_MAP.md`.

## Variables list, strings/constants catalog, and language assessment

- Split the small variable table out of `FUNCTIONS.md` into its own
  `VARIABLES.md`, per the user's request.
- User asked whether this firmware looks hand-written or compiled, and
  if compiled, what language. Answer: **compiled C**, not hand-written
  assembly. Strongest evidence: the HPGL plotter code uses literal
  `%c`/`%d` printf-style format strings (e.g. `"PU%d,%d;"`) - C's
  standard-library convention specifically, not something Pascal does.
  Supporting evidence: uniform compiler-template prologues/epilogues
  on every function, repeated near-identical function pairs, `les`/
  `lds` far-pointer idioms, and null-terminated string literals
  throughout the main ROM (147/169 and 149/171 of all strings found).
  One piece of evidence initially looked like it argued for Pascal -
  the comm ROM's GPIB command table uses length-prefixed strings
  (131/185), and the pervasive `retf N` callee-cleanup calling
  convention is literally called "the Pascal calling convention" - but
  both are better explained as a hand-built fast-parsing table format
  and a deliberate embedded-C code-size optimization, respectively,
  given the much harder-to-fake printf-format-string evidence. Full
  write-up in `disasm/NOTES.md` "What language was this written in?".
- Extracted every printable string from all three ROMs directly from
  the raw binaries (independent of disassembly) and classified each as
  length-prefixed or null-terminated, confirming the split cleanly by
  ROM/table. Surfaced two big finds along the way: what looks like the
  actual front-panel menu/parameter tree names (`160-3633`, e.g.
  `ACQ_MODE_SETUP_TABLE`), and the self-test dispatcher's printed
  diagnostic output text (`160-3532`, e.g. `"2230/2220 Power up tests

- Wrote up as `STRINGS.md` (curated, categorized, human-readable) with

## Main ROM heuristic layer: coverage jumps to 85.6% combined

- Continued disassembling per the user's request. First tried
  widening proven coverage: broadened the interrupt-vector-write
  scanner to registers other than `bx`, and re-checked for unresolved
  indirect jmp/call and unmapped far-call targets across the now much
  larger reachable set. All three came back empty/false-positive -
  the broadened IVT scan's hits turned out to be a shared utility
  storing a computed far pointer through ordinary scratch variables
  that happen to sit in the IVT's address range, not real vectors.
  Confirmed: 0 indirect jmp/call anywhere, 0 unmapped far-call targets
  anywhere. Growing *proven* coverage further needs a genuinely new
  kind of entry point, not more of the same techniques - that lever is
  exhausted for now.
- Instead applied the comm ROM's successful heuristic technique (scan
  for the `55 8B EC` push-bp/mov-bp,sp prologue) to the main ROM pair:
  found 216 unreached signatures in `160-3633` and 209 in `160-3532`.
  New `disasm/gen_disasm_mainrom_heuristic.py` seeds them, output to a
  separate `sysrom_3532_3633_heuristic.lst` (the official
  `sysrom_3532_3633.lst` stays proven-only, same confidence-separation
  principle as the comm ROM). Result: both main-ROM halves jumped from
  ~14-41% to **90.6% coverage each**.
- New `disasm/validate_all.py` NASM-validates everything (all four
  mapped regions, all heuristic layers) in one combined pass: **68,776
  instructions total, 85.6% of all mapped bytes** (196,372/229,376) -
  61,771 exact + 6,790 alt-encoding + 174 not-converted + only 41 real
  mismatches.
- Chasing those 41 mismatches down surfaced and fixed several more
  real `validate_nasm.py` bugs: `jcxz` doesn't accept the `short`
  qualifier the way other `jcc` mnemonics do (was crashing the whole
  batch for any file containing one); `cmpsb`/`cmpsw` have their
  source/dest operand order reversed from `movsb`/`movsw` in
  capstone's output; a whole class of alternate-encoding helpers
  didn't account for a leading segment-override prefix byte, so they
  misread the prefix itself as the opcode (added a shared
  `split_seg_prefix()`); a new alternate-encoding case (`mod=01`/
  `mod=10` with a zero displacement can also be encoded as `mod=00`);
  and a stray `0xF2`/`0xF3` prefix in front of a non-string
  instruction (legal on real hardware, no NASM syntax for it).
- The remaining ~39 mismatches cluster in one narrow region of
  `160-3633` (physical `0xEA1A0-0xEA615`) decoding as 386-only
  features (`fs`/`gs` prefixes, `popal`/`popaw`, `esi`) that can't be
  real on this confirmed 8086/8088 - genuine decode drift into
  non-code bytes. Traced: these addresses have no label at all (not a
  jump/call target, not a heuristic entry) - reached by pure
  sequential fallthrough across an undetected code/data boundary. Left
  as documented, not patched around - the validator's exact-match-only
  trust model already keeps it from affecting the buildable `.asm`.
- Re-verified the official proven-only files are unaffected (still 0
  mismatches) and regenerated all buildable `.asm` sources.

## NOP-aligned "readable" reconstruction, saved as a permanent artifact

- Tested and confirmed NASM's `CPU` directive does not resolve any of
  the encoding-choice ambiguities (direction bit, immediate/
  displacement width, zero-displacement collapse, duplicate opcode) -
  it only gates instruction-set availability, not encoding choice
  among legal alternatives for a given CPU level.
- Built `disasm/gen_source_readable.py`: emits every decoded
  instruction as real NASM text (no raw `db` fallback for anything
  actually understood), padding any NASM-preferred-shorter encoding
  back out to the original instruction length with explicit `nop`
  bytes so every following address is unchanged from the true
  original.
- Verified via independent reassembly: all three chips reassemble to
  their true original length exactly, with only 1,431 (`3633`) / 324
  (`3532`) / 108 (`2998`) bytes differing out of 65,536, all of them
  NASM's own equivalent encoding substituted for the original's.
- Per direct instruction, saved the assembled result permanently as
  `binary/aligned/160-XXXX-14_aligned.bin`, clearly marked **not
  original firmware** (`binary/aligned/README.md`), and adopted it as
  the reference binary for future checks going forward - flagged in
  `TODO.md`/`disasm/NOTES.md` to revisit that choice once the rest of
  the analysis is further along.
