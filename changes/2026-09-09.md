# 2026-09-09

## Identified the firmware and hardware

- Confirmed all six `binary/160-*.bin` files are Tektronix 2230
  oscilloscope firmware EPROM dumps: a comm/GPIB-RS232 option ROM
  (`160-2998`) and a two-chip main system ROM (`160-3532`/`160-3633`),
  each in two firmware revisions (`-13`/`-14`).
- Decoded the 10-byte self-ID header each ROM starts with (BCD part
  number + BCD revision + checksum byte + size/address field).
- Diffed revision pairs: `3532`/`3633` are byte-identical between `-13`
  and `-14` except the header; `2998` has real functional differences
  in two ~16KB-aligned regions.

## CPU identification (corrected mid-session)

- Initial hypothesis from opcode-frequency analysis was a Motorola
  6809 — wrong.
- Confirmed via TekWiki (w140.com/tekwiki/wiki/2230) and by testing
  candidate reset-vector interpretations that the CPU is actually an
  **Intel 8088/8086** (16-bit real mode). Verified independently by
  finding a fully valid, self-consistent x86 instruction stream at the
  real reset vector location.

## Memory map

- `160-3633` (silkscreen "sys_rom_0", socket U9109) = physical
  `0xE0000-0xEFFFF`.
- `160-3532` (silkscreen "sys_rom_1", socket U9110) = physical
  `0xF0000-0xFFFFF`, contains the CPU reset vector at `0xFFFF0`
  (`ljmp 0xE00B:1`, landing in the 3633 half).
- `160-2998` (comm ROM) not yet mapped — evidence of 16KB-aligned
  bank switching, unconfirmed whether driven by the same 8088.

## Disassembly tooling

- Built `disasm/gen_disasm.py`, a naive linear-sweep 6809 disassembler
  — obsoleted once the CPU was corrected, kept for history only.
- Built `disasm/gen_disasm_x86.py`, a recursive-descent x86-16
  disassembler (via `capstone`) seeded from the reset vector and two
  discovered entry points. Fixed two capstone operand-parsing bugs
  along the way (far call/jump operands render inconsistently with
  `:` vs `,` separators, and sometimes omit the `0x` prefix on small
  offsets).
- Current coverage: ~9,400 of 131,072 bytes (~7%) of the main ROM pair,
  producing legible code (POST/RAM-init, interrupt vector table setup,
  C-compiled-looking dispatch functions).
- Output: `disasm/sysrom_3532_3633.lst` (listing) and
  `disasm/sysrom_3532_3633.symbols.json` (address-based symbol table,
  ready for functional renaming).

## NASM round-trip validation

- Installed a portable NASM (2.16.03) to the session scratchpad
  (winget silently failed to persist an install in this sandboxed
  environment; the portable zip from nasm.us worked directly).
- Built `disasm/validate_nasm.py`: converts every decoded instruction
  to NASM syntax, assembles each into its own `section ... vstart=`
  (packed sequentially, so one instruction's length can't cascade into
  the next one's byte comparison), and diffs against the original ROM.
- Iteratively fixed real converter bugs surfaced by this process:
  - two capstone far-call/jmp operand-formatting inconsistencies
    (`:` vs `,` separator, and inconsistent `0x` prefixing) that had
    silently caused whole regions of code (including the actual reset
    routine!) to go untraced in the recursive-descent disassembler
    itself — fixed in `gen_disasm_x86.py`, which raised main-ROM
    coverage from ~280 to ~9,400 reached instructions.
  - segment-override placement (`es:[bx]` vs NASM's required
    `[es:bx]`) for indirect far calls.
  - `lodsb`'s implicit segment is DS (not ES like stos/movs's fixed
    destination side) — a wrong assumption here would have silently
    dropped a real 0x26 segment-override prefix byte.
- Identified and correctly classified 3 genuine x86 encoding
  ambiguities (same effect, different valid byte sequence) rather than
  treating them as errors: register-direction bit in ALU/MOV opcodes,
  sign-extended-imm8 vs explicit imm16, and disp8-vs-disp16 addressing.
  Also fixed capstone naming the 16-bit CBW/CWD opcodes after their
  32-bit (386+) identities (cwde/cdq), which under `BITS 16` would
  otherwise pick up a spurious 0x66 prefix.
- Final result: of 9,369 decoded instructions, 8,450 are byte-exact,
  915 are provably-equivalent alternate encodings, 0 are real
  mismatches, and 4 are left unverified (backward branches whose
  resolved target falls outside the mapped ROM - likely a decode
  misalignment worth revisiting, not a validator gap). Full
  methodology write-up in `disasm/NOTES.md` under "Validation status".

## Buildable source reconstruction

- Added `disasm/gen_source.py`, which emits `disasm/160-3633-14.asm`
  and `disasm/160-3532-14.asm`: real NASM source per chip, guaranteed
  (self-verified on every run) to reassemble byte-identical to the
  original `.bin` regardless of how much is understood - decoded
  instructions proven byte-exact appear as real code, everything else
  falls back to raw `db` bytes. These are now the canonical committed
  disassembly; `.lst` remains a secondary diagnostic view.

## Interrupt vector table tracing → 4 new entry points

- Traced `mov <reg>,imm` / `mov es,<reg>` / `mov word [es:bx(+disp)],
  <reg>` instruction triples through the already-decoded code to
  reconstruct real 8086 interrupt-vector-table writes (the reset
  routine and a later routine both install handlers this way, with
  `es=0` or `es=0x3F` whose paragraph base still lands inside the
  1KB IVT at physical `0x000-0x3FF`).
- Found 5 vector installs total; one (INT 2 at reset, `E5D1:0057`)
  was already-reached code, but 4 were previously-unreachable entry
  points: `INT1_HANDLER` (`E5D1:019D`), `INT255_HANDLER_EARLY`
  (`E5D1:0090`), and two later reprogrammings, `INT255_HANDLER_LATE`
  (`E60B:0005`) and `INT2_HANDLER_LATE` (`E60B:003A`) - the NMI and a
  software-only vector both get reassigned mid-run, hinting at
  distinct diagnostic-vs-normal operating states.
- Seeded these in `gen_disasm_x86.py`'s `ENTRY_POINTS`, raising
  coverage from 9,369 to 10,360 instructions (~8% of the 128KB main
  ROM). Re-ran the same vector-tracing search against the newly-
  reached code; found nothing further - this lead is exhausted for
  now. Re-validated with NASM (9,368 exact + 988 alt-encoding, 0
  mismatches) and regenerated the committed `.asm`/`.lst`/
  `.symbols.json` files.
- Confirmed there are currently 0 unresolved indirect jmp/call sites
  anywhere in the reached code, meaning jump-table dispatch isn't the
  right lever for further coverage (updated in `TODO.md`) - the next
  lever is finding more entry points nothing in-graph calls directly,
  the same way these 4 were found.
