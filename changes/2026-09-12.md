## Fully mapped the decimal-formatting and print-record character-cell-copy engines

`snapshot_index_and_format_number` (`SUB_ED0AE`) once the digit-
formatting engine's tail was fully traced: it appends a 1-or-2-
character units suffix after the digits, indexed by the same 6-byte
format-spec table entry that also holds the decimal-point position
(`[idx*6+0x63A]`=position, `+0x63C`/`+0x63D`=suffix chars) - almost
certainly how the firmware renders values like "1.23mV" or "500ns".
`copy_char_cell_template_and_sync` (`SUB_EF440`) similarly, once its
neighbors `SUB_EF346`/`SUB_EF393` were understood as a position-
wraparound-clamp preamble (same shape as `read_acq_sample_with_wrap`'s
buffer math, for a character-cell display context) - `SUB_EF440` is
independently callable, bypassing that preamble entirely, which is
what made it nameable while the preamble stays unrenamed.

**Reusable pattern identified**: when a function in an entangled/
ambiguous-entry region has its own independent, cleanly-formed
external call site (not just reached via the cluster's internal
fallthrough/jumps), that's often enough to name it confidently even
while its neighbors in the same cluster stay unnamed. Tried this same
lens on `SUB_EFBA5` and it didn't pan out - it has an independent call
site, but the call passes zero arguments while the function's own
opener implies stack content that isn't there, a genuine inconsistency
rather than just an odd-looking-but-fine prologue - left unrenamed.

## Investigation: what's in the uncovered ~9% of ROM bytes?

Direct request: look for lost test code, calibration data, wrong
address mappings, or compiled-but-never-called functions in the ROM
bytes neither the proven call graph nor the heuristic push-bp scanner
reaches. Built `disasm/compute_coverage.py` first (see below) to get
an accurate byte-level map, then classified every gap.

**The big find**: `init_far_pointer_table_sysrom` (renamed earlier,
but only from its 4-instruction driver loop) has its own embedded data
table - never actually decoded until now. It's a genuine 82-entry
`(dest_offset, far_ptr)` table targeting RAM `0x2090`-`0x21F0` under
`ES=0x209` - a real, separate variable region from the "flat" `DS=0`
space most tracked variables live in. **15 of its 82 targets were
never reached by proven or heuristic disassembly**, and every one
hand-verified as coherent, non-garbage x86. Added all 15 as new
`ENTRY_POINTS` and re-ran the recursive descent: proven coverage grew
from 13,510 to 14,799 instructions, still byte-identical end to end -
a genuine, verified expansion, not speculation.

What's in there: a plot-position/pen-drawing family (7 functions)
touching the exact same variables as `draw_pending_line_segment`/
`reset_plot_home_or_acq` - more entry points into that same multi-
entry plot module than the call graph alone ever revealed; a scale-
factor computation family (4 functions, new variables `[0x712]`-
`[0x724]`); 2 far pointers `[0x1DB8]`/`[0x1DBC]` sitting right next to
the still-unlocated stroke-font pointer `[0x1DB0]`; 3 cleanly-named
new functions (`merge_record_flags_if_changed`, `init_print_record_
fields`, `compute_print_cell_size`); and a **second, independent
instance of the `SUB_EAC86` mystery** - a completely unambiguous
compiled `LCALL` (`SUB_F173E` → `0xEA13B`) landing on a string table
instead of code, at a totally different address than the original
case. Finding this exact shape twice, independently, is strong
evidence the right explanation is dead/never-executed code left in
the build, not a decode-tooling bug.

**Still open**: no code anywhere in the entire corpus loads `ES`/`DS`=
`0x209` via a literal immediate, so how (or whether) these 15
functions actually get invoked in practice isn't proven - documented
as unresolved rather than asserted.

Also built `disasm/compute_coverage.py` along the way: the previously-
recorded "85.6%" combined coverage figure double-counted the comm ROM
(treating the `0x90000` address-decode alias as a 4th separate 64KB
region instead of the same underlying bytes as `160-2998`'s upper
half). Corrected numbers: proven-only coverage is 19.3% of all ROM
bytes; proven+heuristic combined reaches 90.7%.

## Investigation: are there jump tables (computed switch dispatch)?

Direct follow-up question. Swept both `.lst` files for any `jmp`/
`ljmp`/`call`/`lcall` through a register or memory operand. Found 2
already-understood, genuinely resolved dispatch tables (the task
scheduler's per-task entry table, and the per-item handler table at
`[0x1D10]`), plus 3 *more* instances of the "lands 1-4 bytes into a
legitimate instruction" landing-artifact anomaly already documented
for `SUB_E90A5`/`SUB_E92B0` - not real jump tables, just coincidentally
-valid jump/call opcodes formed by misaligned real `lcall`s.

One of them resolved an old loose end: `0x88729` (the exact target of
`SUB_E99DF`'s own garbage-looking `ljmp`, previously assumed
meaningless) is actually a real, isolated `ljmp [bp+di]` instruction -
just not statically resolvable, since it indexes off whatever the
caller (`SUB_F4150`) leaves in `bp`/`di`. This pushes the landing-
artifact count to 5+ independent instances across 2 unrelated code
neighborhoods - now the strongest evidence in the project that this is
a real stale-call-site defect in the shipped ROM (a tooling bug
couldn't explain 5 independent, unambiguous compiled call/jump targets
all landing a few bytes short), not dead code or a decoder problem.
Corrected an old, now-inaccurate "zero unresolved indirect jmp/call"
claim in `disasm/NOTES.md`'s coverage section.

Built `disasm/find_landing_artifacts.py` to search systematically for
more instances (any real call target whose own decoded instruction
overlaps byte-for-byte with another independently-reached instruction)
- found ~49 raw candidates, most matching already-documented/already-
named multi-entry functions from this and earlier sessions (expected -
that's the normal signature of every "shared entry point" case found
so far), a handful still unclassified. Investigation continuing.
