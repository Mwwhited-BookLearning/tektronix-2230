## Manual follow-up pass over 4 more `UNKNOWN_DATA.md` blocks not yet individually chased

Continuing the 2026-09-15 deep dive (`docs/decode-anomalies/
unknown-data-deep-dive-2026-09-15.md`), on request to keep working the
unknown-data backlog. One real finding, three smaller ones - full
detail in that doc's new "Follow-up, 2026-09-22" section:

- **`160-3633` `0xEFF99-0xEFFED` isn't data - it's genuine reachable
  code a coverage-tooling off-by-one orphaned.** Manually decoded all
  85 bytes; two branches converge cleanly back into code the heuristic
  disassembler already has at `0xFFEF`, proving real control flow, not
  coincidental clean decoding. Root cause: a `jmp` instruction's
  trailing byte falls 1 byte past this block's labeled end, and that
  orphaned byte is exactly what caused the heuristic listing's own
  "landing artifact" at this spot - not a compiler/linker quirk as
  previously assumed elsewhere in this project, just a boundary bug in
  how the block was measured. Also surfaced two new candidate
  RAM-pointer variables, `[0x1C94]`/`[0x1DDC]` (added to
  `VARIABLES.md`, purpose still unknown), and a possible systematic
  lead worth a follow-up automated pass: both jumps in this function's
  tail wrap past `0xFFFF` into `160-3532`'s file-offset space, so
  other spurious "unknown data" blocks may sit just upstream of other
  0xFFFF-crossing jumps.
- `160-3532`'s and `160-2998`'s final blocks (right before/after each
  chip's real fixed vectors) are confirmed as ordinary unprogrammed

- `160-3633` `0xE0205-0xE0269` (right after `boot_init`'s own final

- `160-2998` `0x88D1C-0x88D3D` (34 bytes of small 2-6 integers) was

## Used the emulator's own memory dumps, then a live watched run, to check the `[0x1c94]`/`[0x1ddc]` hypothesis above - it doesn't hold up

Asked whether anything useful could come from the emulator's existing
memory dumps (`scratchpad/dump/*`, `emulator/captured-notes/
SelectC1C2-Set/*`). First pass: cross-referenced today's two new
RAM-pointer candidates against all 6 existing `.mem` access logs and
reported `read=0` for both as if that meant "nothing ever reads these."
Wrong, and corrected by the user: `io_stubs.AccessCounter` only counts
memory *writes*/IO by default - memory *read* tracking is opt-in
(`watch`) because of the documented Unicorn 2.1.4 stack-corruption bug,
and none of those 6 existing dumps had it turned on, so `read=0` just
meant "this dump never watched reads," not "nothing reads this."

Re-checked properly: installed a narrow, 4-byte `install_watch_range`
on each cell and ran a fresh 5M-instruction boot trace. Real reads do
happen. That prompted grepping both ROMs' full disassembly for every
`les`/`lds` site referencing either address, which turned up something
the original single-call-site read had completely missed: `[0x1ddc]`
is loaded via `les` at **64 different call sites** (`di`/`bx`/`dx`),
not the one site found earlier. 24 of those 64 executed during the 5M-
instruction run (one, physical `0xE126C`, repeatedly - roughly every
10,000 instructions). Reading the actual far-pointer value at each hit
found it churns wildly - `0000:0000` most of the time, but also
`3020:2020`, `FF00:0400`, `4100:4107`, and one hit where the "pointer"
was literally leftover ASCII text bytes. That inconsistency directly
contradicts this morning's "fixed-stride record table" hypothesis for
`[0x1ddc]` - a real dedicated table pointer wouldn't resolve to
unrelated garbage from call to call. Revised conclusion: `[0x1ddc]` is
much more likely general-purpose/reused scratch RAM borrowed by many
unrelated routines, not a single owned table. `[0x1c94]`'s one known
call site never executed in this run, so it's still unverified either
way. Corrected `VARIABLES.md`'s entry to supersede the original
hypothesis rather than leave the wrong framing standing.

## Systematic follow-up on the block-20 wrapping-jump finding; found a second, differently-caused instance of hidden real code

Wrote `disasm/find_sandwiched_unknown_blocks.py` to test the "worth
checking as a next step" lead from earlier today's block-20 finding
(`docs/decode-anomalies/unknown-data-deep-dive-2026-09-15.md` finding
7): does the coverage/heuristic disassembler systematically fail to
follow any jump whose target wraps past a chip's own 64KB half, the
way it missed block 20? **Answer: no** - re-walking the full
proven+heuristic entry-point corpus and checking every jmp/call/
conditional-jump's unmasked Capstone target found exactly one such
instance project-wide (the already-known block 20 jumps). An earlier
draft of this check produced 16 false positives from Capstone
sign-extending backward jump displacements as 32-bit hex in `op_str`;
bounded the check to `0x10000-0x1FFFF` to fix it.

The script's weaker "sandwiched between covered code" signal (37 of
49 remaining unknown blocks match it - too common in a packed ROM to
mean much alone) was still useful for ranking candidates to check by
hand. That manual pass found:

- **A second confirmed real-code block, via a different mechanism**:
  `160-3633` physical `0xE956E-0xE95A0` (block 13) is two small,
  `retf`-terminated leaf subroutines - one writes a fixed byte to the
  already-confirmed front-panel A/D control latch (U6104) and
  far-calls a heuristic-only helper; the other reads the already-
  confirmed front-panel input register (`fp_intstat`) and, on both
  branches, copies a flat-DS variable into that same A/D latch. Unlike
  block 20, no wrapping jump is involved - and unlike block 20, no
  literal far-pointer bytes anywhere in any of the three ROM binaries
  reference either entry address, so whatever calls this is a
  still-unresolved computed/indirect far call. Documented as finding
  10 in the deep-dive doc.
- Confirmation that 7 of the "sandwiched" `160-3532` blocks
  (`0x1A86-0x213A`) aren't independent mysteries at all - they're
  uncovered pieces of the already-documented ~100-entry jump table
  (finding 1), consistent with that finding's own note that only 2 of
  its 4 real callers land cleanly on an entry.
- 7 more blocks that look like real code by eyeball (clean prologues,
  or direct references to already-tracked RAM/plot variables) but
  aren't rigorously confirmed the way the two above were - left as
  open leads rather than findings, listed in the deep-dive doc and
  `TODO.md`.
- A couple of the remaining candidates rule out code outright by
  containing instructions this 8088-class design can't execute at all
  (`fld`/`fdiv` x87 FPU opcodes, a reserved `int1`) - clear evidence of
  garbage/data, not a decode error worth chasing.

Updated `UNKNOWN_DATA.md`, `TODO.md`, and `STILL_PENDING_DECODE.md` to
reflect this (negative on the specific wrapping-jump mechanism,
positive on the broader "tooling misses real code" phenomenon
recurring via unresolved far-calls), and added finding 10 plus a
