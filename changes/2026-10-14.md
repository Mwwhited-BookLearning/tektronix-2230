# 2026-10-14

## Resolved the comm ROM's genuine incoming-UART-data path, end to end

Direct follow-up to the user's question "where in the code is a
message detected and decoded from the UART" - which traced straight
into the project's own long-standing open item (`TODO.md`,
`STILL_PENDING_DECODE.md`'s "Comm ROM / RS-232 command parsing"
section): where a real incoming byte first lands in `[6]`/`[0x580]`/
`[0x590]` from actual hardware, as opposed to the already-understood
tick-driven polling that merely *reaches* that code.

Picked up the one previously-unresolved thread: `[0x6D6]` (a far
pointer into the confirmed UART/GPIB register bank, physical
`0x406F0`-`0x406F7`) had only ever been traced as a *write* target
(baud/parity configuration). Following its *reads* instead resolved
the whole path - though, as a later same-day correction below
describes, part of this "resolution" turned out to already be on the
books under an aliased address.

- **`FUNC_2998_EF54`** (physical `0x8EF54`, comm ROM `160-2998`) is
  the producer. It reads a second far pointer, `[0x6DA]`, into the
  same register bank - the UART's status/interrupt-latch byte - and
  tests bit `0x80` (toggles the comm-status icon via `[0x732+0x97]` +
  `redraw_option_status_icon`) and bit `0x02` (data-ready). When bit
  `0x02` is set, it reads the actual received byte with a plain `mov
  dl, byte ptr es:[di]` on `[0x6D6]`'s target - confirming
  `STILL_PENDING_DECODE.md`'s prediction that the real receive read
  would be a memory-mapped `mov`, not an `in` instruction, since the
  comm ROM has no genuine port I/O at all - plus two more register
  bytes at `[0x6D6]+1` and `+3`. All 4 bytes (data, reg+1, reg+3,
  status) are packaged into one record and written into a ring
  buffer: write pointer `[0x464]`/`[0x466]`, base `0x46C`, size `0x80`
  (32 four-byte records), with correct wraparound - the RX-side
  counterpart of the already-documented TX queue (`[0x448]`/`[0x44A]`/
  `[0x44C]`, base `0xAF`, 1-byte records - simpler since TX doesn't
  need per-byte status).

- **`FUNC_2998_F12B`** (`0x8F12B`) is the consumer: drains the ring
  buffer by comparing `[0x468]`/`[0x46A]` (read) against `[0x464]`/
  `[0x466]` (write), and for each record calls `SUB_9754C` (`0x8F54C`)
  on the record's `+1` status/class byte (masked `0x9F`) to get a
  translated event-type byte, dispatching further on specific result
  bits (`0x80` -> `SUB_97253`, `0x10` -> `SUB_97583`), advancing the
  read pointer by 4 with wraparound, then servicing the TX queue once
  drained.

- **Closes the loop into the already-known parser**: a second,
  closely-related dispatcher, `FUNC_2998_F5AC` (`0x8F5AC`), keyed on
  `[0x598]` (the raw status byte saved during capture), calls
  bit-by-bit `SUB_976C0` (`0x20`), `SUB_9785B` (`0x10`), and - bit
  `0x04` - `parse_next_gpib_command_byte` (`0x8F905`) directly, the
  function already known to read the staged byte out of `ds:0x586`/
  `ds:0x590` into `[0x580]` and feed it onward into
  `process_gpib_command_byte`'s classification/dispatch path.

Full chain, hardware to parser: `[0x6D6]`/`[0x6DA]` (UART registers)
-> `FUNC_2998_EF54` -> RX ring buffer (`[0x464]`/`[0x468]`, base
`0x46C`) -> `FUNC_2998_F12B` / `FUNC_2998_F5AC` ->
`parse_next_gpib_command_byte` -> `[0x580]`/`[6]` -> the command
dispatch machinery already documented elsewhere in `docs/comm-rom/`.

## Correction, same day: part of the above was a duplicate rediscovery

Regenerated the Ghidra decompiled-C exports
(`decompile/export_decompiled_c.py`) while doing a general docs-
consistency pass, and cross-checking against them immediately
surfaced a problem: `FUNC_2998_EF54` above (native address `0x8EF54`)
**is** `FUNCTIONS.md`'s existing `poll_comm_status_tick` (raw/alias
`0x96F54`), already documented - including the same `[0x6DA]`/`[0x6D6]`
reads and the same RX ring buffer - before this session. The producer
side of the "found" write-up above is a rediscovery under the comm
ROM's `0x90000` alias, not new ground.

Also wrong: the claim that `[0x740]/[0x742]` was a *third* scheduler
default-handler pointer pair "not yet matched to one of the 12 dumped
slot entries." `FUNCTIONS.md` already resolved `[0x740]` as `run_
continuous_selftest_tick`'s per-tick hook (the `INT255`/`INTR`
hardware-interrupt chain, confirmed 2026-09-13) - an unrelated
mechanism, not a 13th entry in `switch_to_next_task`'s 12-slot table.

What survives as genuinely new, confirmed directly against `init_comm_
dispatch_table`'s raw bytes (`disasm/sysrom_3532_3633.lst` lines
10745-10780): task slot 5's actual target. `docs/interrupts/task-
scheduler.md` had long left this as "`[0x73c]`, not yet traced."
`[0x73C]/[0x73E]` is set *conditionally* on `[0x1BFA]` (the already-
documented COMM_LOOPBACK self-test readback flag, set only when that
probe reads exactly `0xD0`): zero (the common case) -> `FUNC_2998_
F12B`; nonzero -> `FUNC_2998_F5AC`. The consumer/dispatcher *behavior*
of `FUNC_2998_F12B`/`FUNC_2998_F5AC` themselves is also new -
`poll_comm_status_tick`'s existing writeup only covered the producer.

Corrected in `docs/comm-rom/rs232-flow-control-and-open-puzzle.md`
(its "Found, 2026-10-14" section now carries the correction inline),
`FUNCTIONS.md`'s `poll_comm_status_tick` row, `docs/interrupts/task-
scheduler.md`, `TODO.md`, and `STILL_PENDING_DECODE.md`.

**Lesson for next time**: when two ROMs share an alias/mirror address
range (here, comm ROM `0x80000` native vs. `0x90000`-`0x97FFF` alias,
`native = raw - 0x8000`), always check whether a function "just found"
at one address already has an entry under its aliased counterpart
before writing up a "breakthrough" - a quick regenerate-and-diff of
the Ghidra decompile exports is what caught this.

**Left for a follow-up pass** (tracked in `TODO.md`): functional
naming of `FUNC_2998_F12B`/`FUNC_2998_F5AC` and the RX ring-buffer's
consumer-side variables (`SUB_9754C`, `[0x598]`) via `gen_disasm_
x86.py`'s `FUNCTIONAL_NAMES`.

## Found the genuine incoming RS-232 RX message buffer (same-day, later pass)

Follow-up to this same day's earlier pass, which had left
`consume_comm_rx_ring_buffer`'s two dispatch targets (`SUB_97253`
bit `0x80`, `SUB_97583` bit `0x10`) and `dispatch_comm_rx_status_
bits`'s two (`SUB_976C0` bit `0x20`, `SUB_9785B` bit `0x10`)
explicitly flagged "not yet independently analyzed."

**Tooling gap found**: none of the four had a disassembled body in
any committed listing. Not `160-2998-14.lst` - `gen_disasm_2998.py`'s
`render_comm_only()` only renders the native `0x80000`-`0x8FFFF`
range, and these are reached only through the `0x90000`-alias window
from the comm ROM's own heuristic entry points (the recursive-descent
engine does queue/visit them internally, per `gen_disasm_x86.py`'s
`lcall`/`ljmp` handling, but the render filter drops them). Not
`sysrom_3532_3633.lst` either - that listing's own separate
`gen_disasm_x86.py` run only starts from `ENTRY_POINTS`, the proven
main-ROM entries, and nothing in the main ROM literally calls these
four. Worked around with a one-off direct capstone disassembly of
`binary/160-2998-14.bin`'s raw bytes at native file offsets (`native
- 0x80000`).

**`0x8F253` (now `process_comm_rx_data_byte`, alias `0x97253`)**:
the real RS-232 RX byte pipeline - parity strip via `[0x4ED]`,
XON (`0x11`)/XOFF (`0x13`) detection setting/clearing a new RX-paused
flag `[0x45D]` and, on XON, a new pending-resume flag `[0x45A]`,
CR/LF line-boundary detection via `[0x4EF]` updating new pointer
pairs `[0x440]`/`[0x442]` and `[0x444]`/`[0x446]`, and enqueuing the
byte into a new RX **message** buffer (`[0x434]`/`[0x436]` write ptr,
`[0x43C]` base/read ptr, wraps to offset `0xF` at bound `0xAF`,
overflow sets `[0x451]` + error `0x19` at `[0x68C]`). This directly
resolves `docs/comm-rom/rs232-flow-control-and-open-puzzle.md`'s
"Direction correction" section's own explicitly-stated open question
("no genuine incoming-data ring buffer has been identified yet") -
confirmed via grep that none of the new `[0x434]`-`[0x458]` cluster
was already documented anywhere, so this is a genuine new finding,
not a rediscovery.

**`0x8F583` (now `resume_comm_tx_queue_if_pending`, alias `0x97583`)**:
a short dispatcher - if `[0x45A]` is set, calls `service_comm_tx_
queue`. The RX-side half of XON/XOFF flow control, completing the
loop with `get_xon_xoff_byte`/`service_comm_tx_queue`'s already-
documented TX-side half.

**`0x8F6C0`/`0x8F85B` (`dispatch_comm_rx_status_bits`'s own targets,
`SUB_976C0`/`SUB_9785B`)**: only partially traced the same way -
lower confidence, left unnamed. `SUB_976C0` looks like a lazy-init/
bus-reset-detection routine, touching `[0]` as a sentinel, capturing
UART status bits from `[0x6D6]+2` into new fields `[0x452]`/`[0x453]`,
reinitializing the TX queue (setting new flag `[0x454]`) when found
empty, and writing `0x83` to the `[0x6D6]` bank's `+3` register when
the new RX-buffer-full flag `[0x451]` is set (plausibly RTS-deassert
hardware flow control, not confirmed against a schematic).
`SUB_9785B` closely parallels `service_comm_tx_queue`'s own dequeue-
and-transmit logic (same `[0x448]`/`[0x44A]`/`[0x44C]` queue, same
`0xAF`+`0x383` wraparound bound) behind an unexplained priority-
ordered flag chain `[0x455]`-`[0x458]`. Documented as a tracked open
lead (`STILL_PENDING_DECODE.md`, `TODO.md`, `VARIABLES.md`) rather
than guessed at, per the project's "mark unconfirmed findings as
such" convention.

Added `process_comm_rx_data_byte`/`resume_comm_tx_queue_if_pending`
as dual-keyed (native + alias) `gen_disasm_x86.FUNCTIONAL_NAMES`
entries, following the same precedent as the earlier pass's four.

## Found the RX message buffer's consumer chain - proved it feeds the real parser (even later pass, same day)

Picked up the open question from the previous pass: does the new RX
message buffer actually feed the real SCPI/GPIB command parser for
ordinary traffic, or only for the overflow-error case already traced?
Chased every reference to `[0x43C]` (the buffer's read pointer) across
`disasm/160-2998-14.lst` - all of it already rendered in the native
`0x80000`-`0x8FFFF` range, no tooling workaround needed this time -
and traced six previously-unexamined heuristic-entry functions in the
native range `0x8E597`-`0x8ECE9`.

Found a new pointer, `[0x438]`/`[0x43A]`, distinct from the write ptr
`[0x434]` and read ptr `[0x43C]` already documented: the buffer's true
**consumption cursor**. This immediately explained the previous pass's
unresolved "odd non-zero wrap origin of `0xF`" - it's simply the
buffer's base offset, since `init_comm_rx_message_pipeline` (native
`0x8E597`, the pipeline's reset function) initializes all three
pointers to `0xF`, not an anomalous wrap target.

The key proof came from `fetch_next_comm_rx_char` (native `0x8E99B`):
grepping the full listing for `[4]` (the byte it writes the consumed
value into) turned up roughly a dozen call sites for this same
function scattered across `FUNC_2998_1731` through `FUNC_2998_519A` -
the argument/character lexer used throughout the SCPI/GPIB command
parser (digit and alpha range checks, `hex_digit_to_nibble`, quote/
comma/semicolon delimiter handling, and directly inside
`normalize_and_validate_arg_char`, which calls it then immediately
masks/range-checks the result). Every one of those call sites reads
`byte ptr [4]` right after calling it. Since `fetch_next_comm_rx_char`
is also confirmed to be the function `process_comm_rx_data_byte`'s
overflow-error path forces a call into (via `process_gpib_command_
byte`), this ties today's and the previous pass's findings together:
the same function serves both the error path and ordinary per-
character reads, and `[4]` is the hand-off point into the parser.

Also traced and named: `sync_comm_rx_read_ptr_and_release_hold`
(native `0x8E8A2` - resyncs the read ptr to the consume cursor once
room frees up, and conditionally calls the already-confirmed
`release_comm_hold(1)` once >= `0x28` bytes are free, independently
cross-validating this session's buffer-fullness tracking against
pre-existing, separately-confirmed code); `rearm_comm_rx_consume_
cursor` (native `0x8ECE9` - re-arms the consume cursor against newly
arrived data); `finalize_comm_rx_line_boundary` (native `0x8EAAF` -
promotes a pending line-boundary marker and releases the critical
flag at the end of a parsed line); and `set_comm_rx_busy_for_mode`
(native `0x8EA89` - a tiny RS-232-vs-GPIB dispatch wrapper around the
already-named `set_comm_flow_hold`/`set_comm_queue_busy`).

Added all six as dual-keyed `gen_disasm_x86.FUNCTIONAL_NAMES` entries
(plus a `PARAMETER_NAMES` entry for `set_comm_rx_busy_for_mode`'s
`engage` argument) and regenerated `disasm/160-2998-14.lst`/
`.symbols.json`; confirmed all six names render with full bodies and
that 54 call sites across the listing now resolve to real names
instead of raw `SUB_<addr>` labels.

Updated `FUNCTIONS.md` (six new rows), `VARIABLES.md` (resolved the
`[0x434]`/`[0x436]`/`[0x43C]` row's wrap-origin/consumer-side caveats,
new rows for `[0x438]`/`[0x43A]`, `[0]`-`[3]`, and `[4]`),
