# 2026-10-14

## Resolved the comm ROM's genuine incoming-UART-data path, end to end

Direct follow-up to the user's question "where in the code is a
message detected and decoded from the UART" - which traced straight
into the project's own long-standing open item (`TODO.md`,
`STILL_PENDING_DECODE.md`'s "Comm ROM / RS-232 command parsing"
section): where a real incoming byte first lands in `[6]`/`[0x580]`/
`[0x590]` from actual hardware, as opposed to the already-understood
tick-driven polling that merely *reaches* that code.

Picked up the one previously-unresolved thread: `[0x6D6]` (a far
pointer into the confirmed UART/GPIB register bank, physical
`0x406F0`-`0x406F7`) had only ever been traced as a *write* target
(baud/parity configuration). Following its *reads* instead resolved
the whole path:

- **`FUNC_2998_EF54`** (physical `0x8EF54`, comm ROM `160-2998`) is
  the producer. It reads a second far pointer, `[0x6DA]`, into the
  same register bank - the UART's status/interrupt-latch byte - and
  tests bit `0x80` (toggles the comm-status icon via `[0x732+0x97]` +
  `redraw_option_status_icon`) and bit `0x02` (data-ready). When bit
  `0x02` is set, it reads the actual received byte with a plain `mov
  dl, byte ptr es:[di]` on `[0x6D6]`'s target - confirming
  `STILL_PENDING_DECODE.md`'s prediction that the real receive read
  would be a memory-mapped `mov`, not an `in` instruction, since the
  comm ROM has no genuine port I/O at all - plus two more register
  bytes at `[0x6D6]+1` and `+3`. All 4 bytes (data, reg+1, reg+3,
  status) are packaged into one record and written into a
  **previously-unidentified RX ring buffer**: write pointer
  `[0x464]`/`[0x466]`, base `0x46C`, size `0x80` (32 four-byte
  records), with correct wraparound. This is the RX-side counterpart
  of the already-documented TX queue (`[0x448]`/`[0x44A]`/`[0x44C]`,
  base `0xAF`, 1-byte records - simpler since TX doesn't need
  per-byte status).

- **Scheduler wiring**: `init_comm_dispatch_table` (`0xE6D4D`, main
  ROM `160-3633`) turns out to set up *three* default-handler far
  pointer pairs, not the two already documented in
  `docs/interrupts/task-scheduler.md`'s 2026-10-09 section
  (`[0x738]/[0x73A]` -> task slot 4 -> `comm_call_main_rom`;
  `[0x73C]/[0x73E]` -> task slot 5 -> `SUB_975AC`/`SUB_9712B`). The
  third, **`[0x740]/[0x742]`, is set to offset `4` segment `0x96F5` -
  physical `0x96F54`, i.e. `FUNC_2998_EF54` itself**. Whichever task
  slot's default handler does `lcall [0x740]` is therefore the real
  tick-driven UART poll; not yet matched to one of the 12 dumped slot
  entries (slots 0 and 10 were still "not traced this session" as of
  the 2026-10-09 dump, and are the likeliest candidates).

- **`FUNC_2998_F12B`** (`0x8F12B`) is the consumer: drains the ring
  buffer by comparing `[0x468]`/`[0x46A]` (read) against `[0x464]`/
  `[0x466]` (write), and for each record calls `SUB_9754C` (`0x8F54C`)
  on the record's `+1` status/class byte (masked `0x9F`) to get a
  translated event-type byte, dispatching further on specific result
  bits (`0x80` -> `SUB_97253`, `0x10` -> `SUB_97583`), advancing the
  read pointer by 4 with wraparound, then servicing the TX queue once
  drained.

- **Closes the loop into the already-known parser**: a second,
  closely-related dispatcher, `FUNC_2998_F5AC` (`0x8F5AC`), keyed on
  `[0x598]` (the raw status byte saved during capture), calls
  bit-by-bit `SUB_976C0` (`0x20`), `SUB_9785B` (`0x10`), and - bit
  `0x04` - `parse_next_gpib_command_byte` (`0x8F905`) directly, the
  function already known to read the staged byte out of `ds:0x586`/
  `ds:0x590` into `[0x580]` and feed it onward into
  `process_gpib_command_byte`'s classification/dispatch path.

Full chain, hardware to parser: `[0x6D6]`/`[0x6DA]` (UART registers)
-> `FUNC_2998_EF54` -> RX ring buffer (`[0x464]`/`[0x468]`, base
`0x46C`) -> `FUNC_2998_F12B` / `FUNC_2998_F5AC` ->
`parse_next_gpib_command_byte` -> `[0x580]`/`[6]` -> the command
dispatch machinery already documented elsewhere in `docs/comm-rom/`.

Documented in full in `docs/comm-rom/rs232-flow-control-and-open-
puzzle.md`'s "Found, 2026-10-14" section; `TODO.md` and
`STILL_PENDING_DECODE.md` updated to match.
