# 2026-10-13

## `[0x73E]`/`[0x746]`/`[0x742]`/`[0x74A]` resolved as the lettered reference-memory (`REFA`-`REFZ`) record array; strong `REFProt`/`REFStat? PROTect` identification

The prior session's `[0x702]` investigation surfaced a large,
undocumented structure (`[0x73E]`/`[0x746]`, each referenced 85-105
times across physical `0x8B1E8`-`0x8CD94`+) with no owning command
identified. Picked this up directly.

Found a cluster of small sibling functions with no static callers
(`FUNC_2998_B1E8` through `FUNC_2998_B622`) - the same
no-caller-found/register-indirect-dispatch shape already seen for
other comm-ROM sibling clusters ("block 7," the dense-cluster
functions). Tracing them resolved the structure:

- **`[0x73E]`** is a far pointer to a **12-byte-stride, 26-record
  array** - one record per lettered reference memory `REFA`-`REFZ`.
  Confirmed via `FUNC_2998_C85B`, a separate entry point that takes a
  raw ASCII lowercase letter argument and derives the record index
  directly as `letter - 'a'` (landing in `0..25`), using that same
  index against both `[0x73E]` (stride `0xC`) and `[0x742]` (stride
  `0x4E`) - proving both arrays share the same 26-record indexing.
- **`[0x5F8]`** is the command-level selector: `1..4` = numbered
  references `REF1`-`REF4`; `5..30` = lettered references `REFA`-
  `REFZ`. Resolved into the zero-based array index via
  `SUB_93B1C` -> `SUB_93B7E` -> `SUB_96126`, consistent with
  `[0x5F8] - 5` once resolved - matching `FUNC_2998_C85B`'s
  independent `letter - 'a'` math exactly (letter `'a'` = lettered
  reference #1 = `[0x5F8]` value `5`).
- Record field **`+0xA`** of `[0x73E]`'s per-letter record is a
  **write-protection flag byte**. `FUNC_2998_B3A3` (GET/query-side)
  tests bit `0x04` first -> keyword-table-1 `"UNLock"`; else bit
  `0x40` -> `"PERM"`; else -> `"LOCk"`. It special-cases `[0x5F8]` in
  `1..4` (numbered references) to return `"UNLock"` directly without
  touching the array - numbered references have no protection state.
  `FUNC_2998_B339` (SET-side) only accepts `[0x5F8]` in `5..30`,
  rejecting `1..4` as an error, and ORs `0x44` (bits `0x04`+`0x40`
  together) into the record on success - since the GET-side checks
  bit `0x04` first, this is the "unlock" write pattern; the
  corresponding "lock"/"perm" write patterns elsewhere in the sibling
  cluster weren't individually traced.
- **Candidate real-world identity (strong, not 100% proven by a
  direct string/ID trace): `REFProt REF{A-Z}:{LOCked, PERM, or
  UNLocked}` and its query `REFStat? PROTect`**
  (`docs/programming-manual.md` lines ~852-865, ~882). The three
  decoded keywords are exactly `REFProt`'s three documented states;
  `REFProt` is documented as applying only to the lettered references
  (never the numbered ones), matching the SET-side's `1..4` rejection;
  and `REFStat? PROTect` is documented as returning a **thirty**-
  character `U`/`L`/`P` string "from REF1 to REFZ" - `4` numbered
  (always `U`, matching the GET-side's hardcoded `1..4` path) `+ 26`
  lettered `= 30`, exactly matching `[0x5F8]`'s full range.
- A separate, simpler 2-state mechanism (`FUNC_2998_B1E8`/`B1FC`/
  `B227`, driven by byte flag `[0x4F6]`) does **not** touch the
  `[0x73E]` array at all - it reports keyword-table-1 `"ACQ"` (if
  `[0x4F6]==0`) or `"REF"` (otherwise, from `[0x5F8]`'s low byte).
  Tentative candidate: `DATa SOUrce`, whose manual example response
  literally reads `DAT SOU:ACQ,TAR:REF1,...`; `REFOrmat TARget`/
  `CURSor TARget` remain alternative candidates. Not confirmed.
- **`[0x742]`** is a parallel **78-byte (`0x4E`)-stride, 26-record
  array**, indexed in lockstep with `[0x73E]`. Its fields include
  far-pointer pairs (`+0x36`/`+0x38`, `+0x3C`/`+0x3E`) and length
  words (`+0x3A`, `+0x40`) manipulated via `memcpy_far` in
  `FUNC_2998_C85B` and its continuation (physical `0x8C7AB`-
  `0x8CD94`+) - consistent with storing each lettered reference's
  actual saved waveform curve data/length, distinct from `[0x73E]`'s
  protection flag. Not characterized field-by-field.
- **`[0x746]`** is a small far-pointer pool-header struct (fields at
  `+0`/`+2`/`+4`/`+6`/`+8`) managing a shared waveform-data heap that
  `[0x742]`'s per-letter offsets point into; **`[0x74A]`** is a second
  far pointer used alongside `[0x746]+8` in the same compaction code,
  its distinct role not pinned down.

Wrote up the full mechanism in `docs/comm-rom/command-keyword-table.md`
section 11 (replacing the prior session's "still-unresolved" stub in
section 10), added `VARIABLES.md` rows for all six variables
(`[0x73E]`, `[0x742]`, `[0x746]`, `[0x74A]`, `[0x5F8]`, `[0x4F6]`), and
updated `STILL_PENDING_DECODE.md`/`TODO.md`'s forward pointers.

Remaining open within this subsystem: `[0x742]`'s individual fields
beyond the far-pointer/length pairs; `[0x746]`/`[0x74A]`'s exact
pool-management semantics; the lock/perm SET-side write patterns
(only the unlock case was traced); and firm confirmation of the
"ACQ"/"REF" 2-state resolver's owning command.

## `REFProt`'s SET-side siblings traced; `FUNC_2998_B339` re-identified; a genuine bit-mapping inconsistency found and left open

Continued tracing the sibling cluster around the lettered
reference-memory record array above.

- **`FUNC_2998_B252`** and **`FUNC_2998_B2BC`** are the `REFProt`
  SET-side functions: both validate `[0x5F8]` in `5..30` (lettered
  only, rejecting `1..4` like the GET-side). `B252` does
  `and [+0xA], 0xBB` (clears bits `0x04` and `0x40` together) -
  candidate `REFProt REF{A-Z}:LOCked`. `B2BC` does `and [+0xA], 0xBF`
  then `or [+0xA], 4` (clears `0x40`, sets `0x04`) - candidate
  `REFProt REF{A-Z}:UNLocked`. No sibling function was found that sets
  bit `0x40` alone (`PERM`) - its SET-side, if remotely accessible at
  all, wasn't located in this cluster.
- **`FUNC_2998_B339`** (`or [+0xA], 0x44`, setting both bits
  unconditionally with no clearing) was tentatively tagged "unlock" in
  the first round above, but re-identified here: it's a poor fit next
  to `B252`/`B2BC`'s clean two-function LOCked/UNLocked pair (it would
  be redundant with `B2BC`), and the programming manual's `REFDisp
  REF{A-Z}:EMPTY` - "erases the named reference if it is not
  protected," lettered-only, distinct from the numbered-ref `ALL`-model
  `REFDisp REF{1-3}:{ON,OFF,EMPTY}` line - is a better structural match:
  same lettered-only validation shape, and plausibly touches the
  protection-adjacent bits as a side effect of erasing.
- **An unresolved inconsistency** was found while cross-checking the
  GET side. `FUNC_2998_D067` (physical `0x8D067`, the real resolved
  target of `SUB_95067` once the comm ROM's `0x9000`-`0x9800` segment
  alias rule is applied) takes a raw ASCII letter and returns the
  record's raw `+0xA` byte unmodified. It's called from
  `FUNC_2998_B568` (physical `0x8B568`), which builds `REFStat?
  PROTect`'s documented 30-character `U`/`L`/`P` string: `'U'` hardcoded
  for the 4 numbered-reference slots, then for each of the 26 lettered
  refs, the raw byte is ANDed with `0x44` and mapped `0`->`'U'`,
  `4`->`'L'`, else(`0x40`/`0x44`)->`'P'`. This is the **opposite**
  mapping from `FUNC_2998_B3A3` (candidate `REFProt?`) for two of the
  three states: `B3A3` says clear-byte->`"LOCk"`, bit-`0x04`-only
  ->`"UNLock"`; `B568` says clear-byte->`'U'`(Unlocked),
  bit-`0x04`-only(`==4`)->`'L'`(Locked). Both agree only on
  bit-`0x40`->PERM/`'P'`. Re-verified both readings directly from the
  listing to rule out a transcription error - the discrepancy is real
  as disassembled. Documented as an open question rather than guessed,
  per this project's hedge-the-unconfirmed convention; resolving it
  would need live hardware testing (lock a lettered ref, then check
  what `REFProt?`/`REFStat? PROTect` each actually report).
- **`FUNC_2998_B600`** (physical `0x8B600`): divides `[0x746]+6` by
  `1024` and prints it as signed decimal - read as a "KB free" readout
  over the `[0x742]` waveform-data heap's free-space field.
- **`FUNC_2998_B622`** (physical `0x8B622`): cross-checks `[0x4F6]` and
  `[0x5F8]` against each other and against fixed values `0`/`1`/`4`,
  gated by the device-variant byte `[0x732]+0x1F` (the already-confirmed
  `[0x1B83]`) and a new, previously-undocumented byte `[0x5F7]`. On one
  variant path it force-defaults `[0x5F8]=4`/`[0x4F6]=0`
  (numbered-ref-4/ACQ) - consistent with the manual's "REF4 is the only
  available reference memory for the 2220 and 2221 instruments,"
  weakly corroborating the `DATa SOUrce`/`TARget` candidate identity
  for `[0x4F6]`/`[0x5F8]` from the first round above. `[0x5F7]` itself
  is only characterized as one of `B622`'s comparison inputs here.
- Ruled out: `FUNC_2998_B440` is an unrelated date/time or numeric
  formatter (divides by `1024` via `sar`, builds a quoted-string output
  via serial print calls) - not part of this subsystem.

Updated `docs/comm-rom/command-keyword-table.md` section 11 (new
