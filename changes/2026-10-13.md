# 2026-10-13

## `[0x73E]`/`[0x746]`/`[0x742]`/`[0x74A]` resolved as the lettered reference-memory (`REFA`-`REFZ`) record array; strong `REFProt`/`REFStat? PROTect` identification

The prior session's `[0x702]` investigation surfaced a large,
undocumented structure (`[0x73E]`/`[0x746]`, each referenced 85-105
times across physical `0x8B1E8`-`0x8CD94`+) with no owning command
identified. Picked this up directly.

Found a cluster of small sibling functions with no static callers
(`FUNC_2998_B1E8` through `FUNC_2998_B622`) - the same
no-caller-found/register-indirect-dispatch shape already seen for
other comm-ROM sibling clusters ("block 7," the dense-cluster
functions). Tracing them resolved the structure:

- **`[0x73E]`** is a far pointer to a **12-byte-stride, 26-record
  array** - one record per lettered reference memory `REFA`-`REFZ`.
  Confirmed via `FUNC_2998_C85B`, a separate entry point that takes a
  raw ASCII lowercase letter argument and derives the record index
  directly as `letter - 'a'` (landing in `0..25`), using that same
  index against both `[0x73E]` (stride `0xC`) and `[0x742]` (stride
  `0x4E`) - proving both arrays share the same 26-record indexing.
- **`[0x5F8]`** is the command-level selector: `1..4` = numbered
  references `REF1`-`REF4`; `5..30` = lettered references `REFA`-
  `REFZ`. Resolved into the zero-based array index via
  `SUB_93B1C` -> `SUB_93B7E` -> `SUB_96126`, consistent with
  `[0x5F8] - 5` once resolved - matching `FUNC_2998_C85B`'s
  independent `letter - 'a'` math exactly (letter `'a'` = lettered
  reference #1 = `[0x5F8]` value `5`).
- Record field **`+0xA`** of `[0x73E]`'s per-letter record is a
  **write-protection flag byte**. `FUNC_2998_B3A3` (GET/query-side)
  tests bit `0x04` first -> keyword-table-1 `"UNLock"`; else bit
  `0x40` -> `"PERM"`; else -> `"LOCk"`. It special-cases `[0x5F8]` in
  `1..4` (numbered references) to return `"UNLock"` directly without
  touching the array - numbered references have no protection state.
  `FUNC_2998_B339` (SET-side) only accepts `[0x5F8]` in `5..30`,
  rejecting `1..4` as an error, and ORs `0x44` (bits `0x04`+`0x40`
  together) into the record on success - since the GET-side checks
  bit `0x04` first, this is the "unlock" write pattern; the
  corresponding "lock"/"perm" write patterns elsewhere in the sibling
  cluster weren't individually traced.
- **Candidate real-world identity (strong, not 100% proven by a
  direct string/ID trace): `REFProt REF{A-Z}:{LOCked, PERM, or
  UNLocked}` and its query `REFStat? PROTect`**
  (`docs/programming-manual.md` lines ~852-865, ~882). The three
  decoded keywords are exactly `REFProt`'s three documented states;
  `REFProt` is documented as applying only to the lettered references
  (never the numbered ones), matching the SET-side's `1..4` rejection;
  and `REFStat? PROTect` is documented as returning a **thirty**-
  character `U`/`L`/`P` string "from REF1 to REFZ" - `4` numbered
  (always `U`, matching the GET-side's hardcoded `1..4` path) `+ 26`
  lettered `= 30`, exactly matching `[0x5F8]`'s full range.
- A separate, simpler 2-state mechanism (`FUNC_2998_B1E8`/`B1FC`/
  `B227`, driven by byte flag `[0x4F6]`) does **not** touch the
  `[0x73E]` array at all - it reports keyword-table-1 `"ACQ"` (if
  `[0x4F6]==0`) or `"REF"` (otherwise, from `[0x5F8]`'s low byte).
  Tentative candidate: `DATa SOUrce`, whose manual example response
  literally reads `DAT SOU:ACQ,TAR:REF1,...`; `REFOrmat TARget`/
  `CURSor TARget` remain alternative candidates. Not confirmed.
- **`[0x742]`** is a parallel **78-byte (`0x4E`)-stride, 26-record
  array**, indexed in lockstep with `[0x73E]`. Its fields include
  far-pointer pairs (`+0x36`/`+0x38`, `+0x3C`/`+0x3E`) and length
  words (`+0x3A`, `+0x40`) manipulated via `memcpy_far` in
  `FUNC_2998_C85B` and its continuation (physical `0x8C7AB`-
  `0x8CD94`+) - consistent with storing each lettered reference's
  actual saved waveform curve data/length, distinct from `[0x73E]`'s
  protection flag. Not characterized field-by-field.
- **`[0x746]`** is a small far-pointer pool-header struct (fields at
  `+0`/`+2`/`+4`/`+6`/`+8`) managing a shared waveform-data heap that
  `[0x742]`'s per-letter offsets point into; **`[0x74A]`** is a second
  far pointer used alongside `[0x746]+8` in the same compaction code,
  its distinct role not pinned down.
