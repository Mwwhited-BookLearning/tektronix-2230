# 2026-10-13

## `[0x73E]`/`[0x746]`/`[0x742]`/`[0x74A]` resolved as the lettered reference-memory (`REFA`-`REFZ`) record array; strong `REFProt`/`REFStat? PROTect` identification

The prior session's `[0x702]` investigation surfaced a large,
undocumented structure (`[0x73E]`/`[0x746]`, each referenced 85-105
times across physical `0x8B1E8`-`0x8CD94`+) with no owning command
identified. Picked this up directly.

Found a cluster of small sibling functions with no static callers
(`FUNC_2998_B1E8` through `FUNC_2998_B622`) - the same
no-caller-found/register-indirect-dispatch shape already seen for
other comm-ROM sibling clusters ("block 7," the dense-cluster
functions). Tracing them resolved the structure:

- **`[0x73E]`** is a far pointer to a **12-byte-stride, 26-record
  array** - one record per lettered reference memory `REFA`-`REFZ`.
  Confirmed via `FUNC_2998_C85B`, a separate entry point that takes a
  raw ASCII lowercase letter argument and derives the record index
  directly as `letter - 'a'` (landing in `0..25`), using that same
  index against both `[0x73E]` (stride `0xC`) and `[0x742]` (stride
  `0x4E`) - proving both arrays share the same 26-record indexing.
- **`[0x5F8]`** is the command-level selector: `1..4` = numbered
  references `REF1`-`REF4`; `5..30` = lettered references `REFA`-
  `REFZ`. Resolved into the zero-based array index via
  `SUB_93B1C` -> `SUB_93B7E` -> `SUB_96126`, consistent with
  `[0x5F8] - 5` once resolved - matching `FUNC_2998_C85B`'s
  independent `letter - 'a'` math exactly (letter `'a'` = lettered
  reference #1 = `[0x5F8]` value `5`).
- Record field **`+0xA`** of `[0x73E]`'s per-letter record is a
  **write-protection flag byte**. `FUNC_2998_B3A3` (GET/query-side)
  tests bit `0x04` first -> keyword-table-1 `"UNLock"`; else bit
  `0x40` -> `"PERM"`; else -> `"LOCk"`. It special-cases `[0x5F8]` in
  `1..4` (numbered references) to return `"UNLock"` directly without
  touching the array - numbered references have no protection state.
  `FUNC_2998_B339` (SET-side) only accepts `[0x5F8]` in `5..30`,
  rejecting `1..4` as an error, and ORs `0x44` (bits `0x04`+`0x40`
  together) into the record on success - since the GET-side checks
  bit `0x04` first, this is the "unlock" write pattern; the
  corresponding "lock"/"perm" write patterns elsewhere in the sibling
  cluster weren't individually traced.
- **Candidate real-world identity (strong, not 100% proven by a
  direct string/ID trace): `REFProt REF{A-Z}:{LOCked, PERM, or
  UNLocked}` and its query `REFStat? PROTect`**
  (`docs/programming-manual.md` lines ~852-865, ~882). The three
  decoded keywords are exactly `REFProt`'s three documented states;
  `REFProt` is documented as applying only to the lettered references
  (never the numbered ones), matching the SET-side's `1..4` rejection;
  and `REFStat? PROTect` is documented as returning a **thirty**-
  character `U`/`L`/`P` string "from REF1 to REFZ" - `4` numbered
  (always `U`, matching the GET-side's hardcoded `1..4` path) `+ 26`
  lettered `= 30`, exactly matching `[0x5F8]`'s full range.
- A separate, simpler 2-state mechanism (`FUNC_2998_B1E8`/`B1FC`/
  `B227`, driven by byte flag `[0x4F6]`) does **not** touch the
  `[0x73E]` array at all - it reports keyword-table-1 `"ACQ"` (if
  `[0x4F6]==0`) or `"REF"` (otherwise, from `[0x5F8]`'s low byte).
  Tentative candidate: `DATa SOUrce`, whose manual example response
  literally reads `DAT SOU:ACQ,TAR:REF1,...`; `REFOrmat TARget`/
  `CURSor TARget` remain alternative candidates. Not confirmed.
- **`[0x742]`** is a parallel **78-byte (`0x4E`)-stride, 26-record
  array**, indexed in lockstep with `[0x73E]`. Its fields include
  far-pointer pairs (`+0x36`/`+0x38`, `+0x3C`/`+0x3E`) and length
  words (`+0x3A`, `+0x40`) manipulated via `memcpy_far` in
  `FUNC_2998_C85B` and its continuation (physical `0x8C7AB`-
  `0x8CD94`+) - consistent with storing each lettered reference's
  actual saved waveform curve data/length, distinct from `[0x73E]`'s
  protection flag. Not characterized field-by-field.
- **`[0x746]`** is a small far-pointer pool-header struct (fields at
  `+0`/`+2`/`+4`/`+6`/`+8`) managing a shared waveform-data heap that
  `[0x742]`'s per-letter offsets point into; **`[0x74A]`** is a second
  far pointer used alongside `[0x746]+8` in the same compaction code,
  its distinct role not pinned down.

Wrote up the full mechanism in `docs/comm-rom/command-keyword-table.md`
section 11 (replacing the prior session's "still-unresolved" stub in
section 10), added `VARIABLES.md` rows for all six variables
(`[0x73E]`, `[0x742]`, `[0x746]`, `[0x74A]`, `[0x5F8]`, `[0x4F6]`), and
updated `STILL_PENDING_DECODE.md`/`TODO.md`'s forward pointers.

Remaining open within this subsystem: `[0x742]`'s individual fields
beyond the far-pointer/length pairs; `[0x746]`/`[0x74A]`'s exact
pool-management semantics; the lock/perm SET-side write patterns
(only the unlock case was traced); and firm confirmation of the
"ACQ"/"REF" 2-state resolver's owning command.

## `REFProt`'s SET-side siblings traced; `FUNC_2998_B339` re-identified; a genuine bit-mapping inconsistency found and left open

Continued tracing the sibling cluster around the lettered
reference-memory record array above.

- **`FUNC_2998_B252`** and **`FUNC_2998_B2BC`** are the `REFProt`
  SET-side functions: both validate `[0x5F8]` in `5..30` (lettered
  only, rejecting `1..4` like the GET-side). `B252` does
  `and [+0xA], 0xBB` (clears bits `0x04` and `0x40` together) -
  candidate `REFProt REF{A-Z}:LOCked`. `B2BC` does `and [+0xA], 0xBF`
  then `or [+0xA], 4` (clears `0x40`, sets `0x04`) - candidate
  `REFProt REF{A-Z}:UNLocked`. No sibling function was found that sets
  bit `0x40` alone (`PERM`) - its SET-side, if remotely accessible at
  all, wasn't located in this cluster.
- **`FUNC_2998_B339`** (`or [+0xA], 0x44`, setting both bits
  unconditionally with no clearing) was tentatively tagged "unlock" in
  the first round above, but re-identified here: it's a poor fit next
  to `B252`/`B2BC`'s clean two-function LOCked/UNLocked pair (it would
  be redundant with `B2BC`), and the programming manual's `REFDisp
  REF{A-Z}:EMPTY` - "erases the named reference if it is not
  protected," lettered-only, distinct from the numbered-ref `ALL`-model
  `REFDisp REF{1-3}:{ON,OFF,EMPTY}` line - is a better structural match:
  same lettered-only validation shape, and plausibly touches the
  protection-adjacent bits as a side effect of erasing.
- **An unresolved inconsistency** was found while cross-checking the
  GET side. `FUNC_2998_D067` (physical `0x8D067`, the real resolved
  target of `SUB_95067` once the comm ROM's `0x9000`-`0x9800` segment
  alias rule is applied) takes a raw ASCII letter and returns the
  record's raw `+0xA` byte unmodified. It's called from
  `FUNC_2998_B568` (physical `0x8B568`), which builds `REFStat?
  PROTect`'s documented 30-character `U`/`L`/`P` string: `'U'` hardcoded
  for the 4 numbered-reference slots, then for each of the 26 lettered
  refs, the raw byte is ANDed with `0x44` and mapped `0`->`'U'`,
  `4`->`'L'`, else(`0x40`/`0x44`)->`'P'`. This is the **opposite**
  mapping from `FUNC_2998_B3A3` (candidate `REFProt?`) for two of the
  three states: `B3A3` says clear-byte->`"LOCk"`, bit-`0x04`-only
  ->`"UNLock"`; `B568` says clear-byte->`'U'`(Unlocked),
  bit-`0x04`-only(`==4`)->`'L'`(Locked). Both agree only on
  bit-`0x40`->PERM/`'P'`. Re-verified both readings directly from the
  listing to rule out a transcription error - the discrepancy is real
  as disassembled. Documented as an open question rather than guessed,
  per this project's hedge-the-unconfirmed convention; resolving it
  would need live hardware testing (lock a lettered ref, then check
  what `REFProt?`/`REFStat? PROTect` each actually report).
- **`FUNC_2998_B600`** (physical `0x8B600`): divides `[0x746]+6` by
  `1024` and prints it as signed decimal - read as a "KB free" readout
  over the `[0x742]` waveform-data heap's free-space field.
- **`FUNC_2998_B622`** (physical `0x8B622`): cross-checks `[0x4F6]` and
  `[0x5F8]` against each other and against fixed values `0`/`1`/`4`,
  gated by the device-variant byte `[0x732]+0x1F` (the already-confirmed
  `[0x1B83]`) and a new, previously-undocumented byte `[0x5F7]`. On one
  variant path it force-defaults `[0x5F8]=4`/`[0x4F6]=0`
  (numbered-ref-4/ACQ) - consistent with the manual's "REF4 is the only
  available reference memory for the 2220 and 2221 instruments,"
  weakly corroborating the `DATa SOUrce`/`TARget` candidate identity
  for `[0x4F6]`/`[0x5F8]` from the first round above. `[0x5F7]` itself
  is only characterized as one of `B622`'s comparison inputs here.
- Ruled out: `FUNC_2998_B440` is an unrelated date/time or numeric
  formatter (divides by `1024` via `sar`, builds a quoted-string output
  via serial print calls) - not part of this subsystem.

## `FUNC_2998_B622` re-examined via Ghidra decompiled C: it's the real `DATa SOUrce`/`TARget` SET-side/copy-executor, not a simple cross-check

The previous two rounds above mischaracterized `FUNC_2998_B622` as a
passive "cross-check [0x4F6]/[0x5F8] against fixed values and
force-default" function. Re-read it through Ghidra's decompiled C
(`decompile/exports/160-2998-14.c` line 9471, `FUN_0008_b622`) rather
than the raw `.lst` listing alone, cross-checked line-by-line against
the disassembly to confirm (the decompiler's `*"B"` string-literal
artifacts are a known segment-addressing quirk -
`docs/architecture/ghidra-project.md` - and resolve to `[0x5F7]`).
It's a much larger, more substantive function than previously credited:

- **`[0x4F6]` holds the full `0..30` source-reference selector**, not
  a 2-state `ACQ`/`REF` boolean as `FUNC_2998_B1E8`/`B1FC`/`B227`'s
  narrower report path had suggested. `B622` resolves `[0x4F6]`
  through the exact same `SUB_93B1C` call already confirmed for
  `[0x5F8]` in the `REFProt` writeup - proving both use identical
  encoding and the identical resolver. `B227`'s report just collapses
  that range down to a boolean (`"ACQ"` vs `"REF"`) for its own
  purposes; it doesn't define `[0x4F6]`'s real domain.
- **Validates `[0x5F8]`/`[0x5F7]` together against the device-variant
  byte `[0x1B83]`**: when the variant is `0x1E`, requires
  `[0x5F7]==4` and the full `1..30` range (erroring `0x15`, or `7` if
  `[0x5F7]==0`); on any other variant, if in range (or if
  `[0x5F7]==0`, skipping the check entirely), it **unconditionally
  force-defaults `[0x5F8]=4`/`[0x4F6]=0`** (target=`REF4`,
  source=`ACQ`) regardless of what was requested - an exact match for
  the manual's "REF4 is the only available reference memory for the
  2220 and 2221 instruments." This re-characterizes **`[0x5F7]`** from
  "an uncharacterized comparison input" to a **lettered-reference
  feature-gate byte**: `4` (paired with variant `0x1E`) enables the
  full range; `0` appears to mean "no reference-selection option
  installed" (skips validation, still forces the `ACQ`/`REF4`
  default, reports error `7` instead of `0x15` when the variant byte
  would otherwise have demanded `[0x5F7]==4`).
- **Rejects the specific source/target pairing `{REF1, REF4}` in
  either order** with error `0x15` - a hardware/format constraint
  between those two specific numbered references, not yet explained.
- **Performs an actual waveform copy**, not just validation: for
  `ACQ` source (`[0x4F6]==0`), requires a numbered target (`1..4`,
  lettered targets rejected) and calls
  `draw_pending_line_segment`/`SUB_93925`/`reset_plot_home_or_acq`
  (the first and third already-named display/plot-sync functions used
  elsewhere for redraw bookkeeping) to copy the live acquisition into
  the target and update the on-screen trace. For a reference source
  (numbered or lettered), it fetches the source's waveform pointer
  (`SUB_9471C`+`SUB_94D9C` for lettered, a capability-bit check against
  a per-reference table for numbered) and calls `FUNC_2998_7609` to
  perform the actual reference-to-reference copy, gated by a `1`-or-`4`
  "category" value (plausibly a record-length class, not confirmed)
  that must match between source and target whenever either one is
  `REF1` or `REF4` specifically. On success it also sets a
  "redraw/refresh pending" bit (`0x200`) in a word at far pointer
  `[0x736]`.
- This reinforces the `DATa SOUrce`/`DATa TARget` candidate identity
  for `[0x4F6]`/`[0x5F8]` from "weak corroboration" to a strong match -
  the function's entire shape (validate source+target selectors,
  enforce the documented model limitation, then execute an immediate
  copy) is exactly what setting `DATa SOUrce`/`TARget` on a live
  instrument would need to do, consistent with GPIB commands on this
  instrument taking effect immediately rather than being queued.

## Ground-truth re-trace of the `SUB_93B1C`/`SUB_93B7E`/`SUB_96126` resolver chain: corrected the arithmetic, and `SUB_96126` turned out to be an interlock, not an index resolver

The previous two rounds' writeups described `[0x5F8]`/`[0x4F6]`'s
resolution through `SUB_93B1C -> SUB_93B7E -> SUB_96126` as a single
blended "arithmetic consistent with `[0x5F8] - 5`," inferred from the
chain's overall input/output behavior rather than from reading each
function's body. Went back and read all three directly from
`disasm/160-2998-14.lst`, plus the two functions found immediately
following `SUB_96126` in the listing, to pin down the real mechanics.

- **`SUB_93B1C`** (physical `0x8BB1C`) is a plain switch on its one
  word argument: `0`/`1`/`2`/`3` pass through unchanged, `4` (`REF4`)
  maps to `1` (**the same output as `REF1`** - confirmed directly, not
  explained), and anything else (the raw `5..30` lettered range)
  computes `(input + 0x5C) & 0xFF`, which for `5..30` lands exactly on
  ASCII `'a'..'z'`. It converts the selector to a **letter character**,
  not to an array index - a genuine correction to the prior "does the
  `-5` math" characterization.
- **`SUB_93B7E`** (physical `0x8BB7E`, immediately following
  `SUB_93B1C` in the listing) is the actual letter-to-index step:
  takes a byte, and if it's in `0x61..0x7A` (`'a'..'z'`) returns
  `byte - 0x61` (the `0..25` record index); otherwise returns sentinel
  `0xFFFF`. This is the function doing the `-5`-equivalent math, and it
  operates on `SUB_93B1C`'s *output*, not on `[0x5F8]` directly.
- **`SUB_96126`** (physical `0x8E126`, = `FUNC_2998_E126`) takes **no
  arguments** and does nothing with the resolved index. It disables
  interrupts, reads far pointer `[0x746]`'s pointed-to structure's
  words at `+0`/`+2`/`+4`: if all three are zero, writes status code
  `0x6D9` to a newly-identified variable `[0x690]`, sets that
  structure's `+0` word to `1`, and returns `0`; otherwise writes
  `0x6E4` to `[0x690]` and returns `1`. It's a simple test-and-set
  **interlock/busy flag** over the `[0x746]`-pointed pool-header
  structure, unrelated to letter/index resolution despite sitting
  third in the call sequence at every site seen (`FUNC_2998_B252`/
  `B2BC`/`B339`).
- Each of those three callers gates its whole operation on
  `SUB_96126`'s return: `0` (interlock was free) lets it proceed to use
  the `SUB_93B7E`-resolved `0..25` index against `[0x73E]`'s `+0xA`
  flag byte; anything else (already busy) skips straight to error code
  `0x21`. On success, all three explicitly reset the structure's `+0`
  word back to `0` (releasing the interlock they'd just claimed) and
  `or`-set bit `0x01` of `[0x603]` - a dirty/redraw-style flag distinct
  from `FUNC_2998_B622`'s `[0x736]` bit `0x200`.
- `[0x746]` itself is confirmed to be a plain 4-byte far-pointer
  *variable* (every access is `les reg, ptr [0x746]` then
  `es:[reg+N]`), not the pool-header struct directly as the prior
  phrasing implied. `FUNC_2998_E1AF` (physical `0x8E1AF`), read right
  after `SUB_96126` in the listing, `memcpy_far`s all 14 (`0xE`) bytes
  of that pointed-to structure into a caller buffer - a "read the pool
  header" accessor, pinning the structure's total size at 14 bytes (7
  words, `+0` through `+0xC`) and consistent with (not contradicting)
  the already-documented `+6`/`+8` free-space-count/pool-base fields.

## `FUNC_2998_E1E9` found: a stronger `REFDisp REF{A-Z}:EMPTY` candidate than `FUNC_2998_B339`, reopening `B339`'s identity

While reading the two functions immediately following `SUB_96126` in
the listing (`FUNC_2998_E1AF`, already covered above, and the one
right after it), found `FUNC_2998_E1E9` (physical `0x8E1E9`, same
no-static-caller/register-indirect-dispatch shape as the rest of this
cluster). Given a single `0..25` record-index argument, it:

- Zeroes `[0x73E]`'s record words at `+0`/`+2`/`+4`/`+6`/`+8`, then
  sets the record's `+0xA` byte to the literal value `1` - a fourth
  distinct value for that byte, not matching any of the `0x04`/`0x40`/
  `0x44` protection-state masks `FUNC_2998_B3A3`/`B568` decode.
- Then `memset_far`s the *entire* corresponding 78-byte `[0x742]`
  record to zero.

This is a full wipe of both per-letter records, not a protection-bit
toggle - a better structural fit for `REFDisp REF{A-Z}:EMPTY` ("erases
the named reference if it is not protected") than `FUNC_2998_B339`,
which only ever sets protection bits `0x44` and never touches
`[0x742]`'s waveform data. `FUNC_2998_B339`'s own real identity is
accordingly reopened rather than settled; no caller/trigger has been
traced for either function yet, so neither is 100% confirmed as the
`EMPTY` implementation. Also newly pins `[0x73E]`'s record as having
at least 5 more word fields beyond the already-documented `+0xA` flag
byte - their normal (non-wiped) meaning isn't characterized.

Updated `docs/comm-rom/command-keyword-table.md` section 11,
`VARIABLES.md`'s `[0x73E]` row, `STILL_PENDING_DECODE.md` (seventh
follow-up), and `TODO.md`.
