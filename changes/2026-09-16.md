## Started `emulator/`: a headless Unicorn-Engine firmware tracer

User request: "what would it take to start building an emulator for
the rom?" followed by "create a .\emulator folder... stand with
.\emulator\docs for a design phase." Wrote `emulator/docs/design.md`
(scope, memory-map wiring, I/O stub strategy, milestones), then
continued past design-only once Unicorn was confirmed installable:
`memory_map.py`/`timer.py`/`emu.py` now boot the real firmware from
the genuine reset vector and drive a synthetic scheduler tick.

Found and fixed 4 real, non-obvious emulation gotchas along the way
(documented in `design.md`'s "Findings and gotchas" section):
`0x88000-0x8FFFF` is RAM not ROM continuation; INT 2 is the real NMI
and must never be gated on `IF`; a genuine 8086 wraps addresses above
1MB back to the bottom of memory and Unicorn doesn't do this
automatically; a naive "IVT slot nonzero" check for "vector installed"
fires on transient boot-time RAM-test fill patterns.

**The payoff - resolved the stroke-font glyph-table hunt for this
project's real hardware.** Instrumented `draw_readout_char` directly
and watched it render the real power-up self-test banner (`" POWE"`,
confirmed against `STRINGS.md`) live. Confirmed dynamically (not just
by hand computation) that `[0x1DB0]=E9A3:0000` produces incoherent
per-character far pointers - and surfaced a much bigger, previously-
unconsidered question: `draw_readout_char` checks the comm-option-
detected flag (`[0x1B83]`, set by `detect_comm_option_hw`) first and
returns immediately, drawing nothing, when it's set. Both of this
project's real physical test units have the RS-232 option installed.

Built `emulator/io_stubs.py`'s `CommPresenceProbe` to stub the
hardware-presence probe as "installed" and confirmed it directly:
caught a real, pre-existing typo in `MEMORY_MAP.md`'s own address
table along the way (`0x4007DE`, an extra digit, versus the correct
`0x407DE` its own body text already stated) that made the first
version of the stub silently target the wrong address with zero
effect. With the typo fixed, `[0x1B83]` reads `0x14` exactly as
predicted, and `draw_readout_char` returns immediately on every single
one of ~48 calls made while rendering the full self-test banner - the
emulator also runs cleanly to 60,000,000 instructions with zero
crashes this way, versus reliably crashing inside the broken glyph
walk under the default stub. Separately confirmed
`print_string_far`/`write_readout_port_byte` fire **unconditionally**
regardless of comm-detection status (33 calls happen even without the
stub), carrying the complete real diagnostic text live - captured
byte-for-byte by hooking the far-pointer string argument:
`'2230/2220 boot : 160-3633-14'`, `'POWER UP FAILURES'`, `'PRESS MENU
KEYS TO CONTINUE'`, `'Display controller : TIMEOUT'`, `'ACQ_AB
read-back 0 <> 2'` (the last two are genuine self-test failures caused
by this emulator run's unstubbed hardware, not firmware bugs).

**Conclusion**: on this project's real physical test units, the
vector-stroke-font path is dead code for this diagnostic text -
`write_readout_port_byte`'s `0x40000+0x6F0` port write is the only
channel that ever carries it. This resolves `MEMORY_MAP.md`'s
long-standing "Puzzle: `write_readout_port_byte`'s address overlaps
the comm-option UART register bank" section for the practical question
(marked resolved there), and explains why the stroke-font glyph table
was never found in a live hardware capture: the code path that would
use it never runs on these units. Full detail, including the exact
disassembly and live-captured values, in `docs/display/vector-display-
and-stroke-font.md`'s "Live emulation confirms..." section;
`STILL_PENDING_DECODE.md` updated to match.
