## Started `emulator/`: a headless Unicorn-Engine firmware tracer

User request: "what would it take to start building an emulator for
the rom?" followed by "create a .\emulator folder... stand with
.\emulator\docs for a design phase." Wrote `emulator/docs/design.md`
(scope, memory-map wiring, I/O stub strategy, milestones), then
continued past design-only once Unicorn was confirmed installable:
`memory_map.py`/`timer.py`/`emu.py` now boot the real firmware from
the genuine reset vector and drive a synthetic scheduler tick.

Found and fixed 4 real, non-obvious emulation gotchas along the way
(documented in `design.md`'s "Findings and gotchas" section):
`0x88000-0x8FFFF` is RAM not ROM continuation; INT 2 is the real NMI
and must never be gated on `IF`; a genuine 8086 wraps addresses above
1MB back to the bottom of memory and Unicorn doesn't do this
automatically; a naive "IVT slot nonzero" check for "vector installed"
fires on transient boot-time RAM-test fill patterns.

**The payoff - resolved the stroke-font glyph-table hunt for this
project's real hardware.** Instrumented `draw_readout_char` directly
and watched it render the real power-up self-test banner (`" POWE"`,
confirmed against `STRINGS.md`) live. Confirmed dynamically (not just
by hand computation) that `[0x1DB0]=E9A3:0000` produces incoherent
per-character far pointers - and surfaced a much bigger, previously-
unconsidered question: `draw_readout_char` checks the comm-option-
detected flag (`[0x1B83]`, set by `detect_comm_option_hw`) first and
returns immediately, drawing nothing, when it's set. Both of this
project's real physical test units have the RS-232 option installed.

Built `emulator/io_stubs.py`'s `CommPresenceProbe` to stub the
hardware-presence probe as "installed" and confirmed it directly:
caught a real, pre-existing typo in `MEMORY_MAP.md`'s own address
table along the way (`0x4007DE`, an extra digit, versus the correct
`0x407DE` its own body text already stated) that made the first
version of the stub silently target the wrong address with zero
effect. With the typo fixed, `[0x1B83]` reads `0x14` exactly as
predicted, and `draw_readout_char` returns immediately on every single
one of ~48 calls made while rendering the full self-test banner - the
emulator also runs cleanly to 60,000,000 instructions with zero
crashes this way, versus reliably crashing inside the broken glyph
walk under the default stub. Separately confirmed
`print_string_far`/`write_readout_port_byte` fire **unconditionally**
regardless of comm-detection status (33 calls happen even without the
stub), carrying the complete real diagnostic text live - captured
byte-for-byte by hooking the far-pointer string argument:
`'2230/2220 boot : 160-3633-14'`, `'POWER UP FAILURES'`, `'PRESS MENU
KEYS TO CONTINUE'`, `'Display controller : TIMEOUT'`, `'ACQ_AB
read-back 0 <> 2'` (the last two are genuine self-test failures caused
by this emulator run's unstubbed hardware, not firmware bugs).

**Conclusion**: on this project's real physical test units, the
vector-stroke-font path is dead code for this diagnostic text -
`write_readout_port_byte`'s `0x40000+0x6F0` port write is the only
channel that ever carries it. This resolves `MEMORY_MAP.md`'s
long-standing "Puzzle: `write_readout_port_byte`'s address overlaps
the comm-option UART register bank" section for the practical question
(marked resolved there), and explains why the stroke-font glyph table
was never found in a live hardware capture: the code path that would
use it never runs on these units. Full detail, including the exact
disassembly and live-captured values, in `docs/display/vector-display-
and-stroke-font.md`'s "Live emulation confirms..." section;
`STILL_PENDING_DECODE.md` updated to match.

## Named function parameters for ~90 functions, applied to Ghidra, and made the Ghidra project fully rebuildable from git

User request: "can you start naming the parameters for functions based
on what they do" / "keep going" (several rounds). Built
`disasm/gen_disasm_x86.PARAMETER_NAMES`, a per-function `{stack
offset: name}` table rendered as a `-> name` comment on every matching
`[bp+N]` reference in the `_readable.asm` output (comment-only, never
affects `binary/aligned/`'s NASM reassembly - verified after every
batch). Named parameters for ~90 functions across 6+ batches, roughly
half already had an informal signature hint in `FUNCTIONS.md` (mostly
just formalized, catching several real argument-order bugs along the
way - `memset_far`, `ack_comm_hw_status_bits`, `validate_gpib_device_
records`, `ram_pattern_test`, and `array_index_16`, all fixed in both
`FUNCTIONS.md` and the code); the rest had no existing signature at
all (genuinely new documentation).

User request: "update ghidra with what you've discovered... is there
anything in ghidra that can help you improve your disassembly?"
Applied all confirmed parameters to the live Ghidra project as real
stack `Parameter` objects (not just comments), calibrating the
`ParameterImpl` API on one function first. Along the way, built
`decompile/export_decompiled_c.py` (dumps every function's decompiled
C to a text file, ~1-2s per program) and found it's a genuinely useful

## Integrated the user's own service-manual schematic trace of the RS-232 option board

User request: reviewed the service manual's RS-232 option board
schematics directly (component-level, not just the Theory of
Operation prose already used elsewhere in this project) and added
notes to `TODO.md` under "Architect Notes" - a full chip list for two
physically separate boards (a shared "Option Memory" board and the
RS-232-specific riser), the `U1245` (74F548) address decoder's full
pin-out, the Parameter/State buffer bit maps, and the `U1235`/`U1236`
Interrupt Mask Latch's `Q0`-`Q3` output mapping. Cross-referenced
against every existing related finding and integrated properly (raw
notes removed from `TODO.md` once absorbed, per this project's own
TODO-hygiene convention):

- **UART part number confirmed**: `U1251` = **82C52** - previously
  only known by schematic designator.
- **Resolved the Interrupt Mask Latch's last open output.** This
  project's own code trace (`docs/comm-rom/rs232-early-investigation.md`)
  had already confirmed `0D`=`DR` mask, `1D`=`TBRE` mask, `3D`=
  diagnostic strobe, leaving `2D` as "no reference found anywhere,
  possibly `RLSD`/`DCD`-related." The new schematic trace's `Q0`-`Q3`
  mapping confirms `2D`=`Q2`=`RLSO` (buffered to the RS-232 DCE
  connector's DCD pin) exactly - all 4 outputs now agree between two
  fully independent methods (code trace vs. schematic trace), zero
  contradictions.
- **Explained a previously-unexplained live-hardware discrepancy.**
  `comm_param`'s last bit had been observed differing between the two
  physical scopes at an identical DIP-switch setting, flagged as
  "unexplained." The new Parameter Buffer bit map shows that bit is
  the UART's own live serial-data-output line, not a switch mirror at
  all - it was never a discrepancy, just a live signal sampled at two
  different instants.
- **New primary-source hardware documentation**: the Option Memory
  board's 4-chip physical RAM layout (`U118`/`U128`/`U138`/`U148`,
  each 8KB, confirming `MEMORY_MAP.md`'s already-known `0x88000-
  0x8FFFF` address range down to the individual chip), and the full
  2-board component list, added to `HARDWARE.md`.
- **Found and fixed a stale, self-contradicting note**: one section
  of `STILL_PENDING_DECODE.md` still said the `write_readout_port_
  byte`/UART theory "doesn't hold up... back to genuinely unresolved"
  based on an old live-listener test seeing zero bytes, while another
  section of the same file already recorded the emulator's later
  confirmation that this channel demonstrably does carry real
  diagnostic text. Reconciled honestly - the *mechanism* is confirmed,
  what's still open is only whether the zero-byte live test was
  checking the same code path this project's dynamic finding covers.
- Still open, narrowed but not closed: which *specific* DIP switch
  number (beyond the confirmed baud-rate nibble) controls which
  *specific* decoded RS-232 setting - the new trace confirms *where*
  each switch lands (which buffer, which bit) but not each switch's
  individual semantic meaning.

**Follow-up same day**: identified the Option Memory board's 2
previously-unidentified support chips - `U1122` = **ICL8212**
(programmable comparator/detector) and `U1132` = a hex inverter, part

by similar comparator circuits (not yet individually traced). Not yet
