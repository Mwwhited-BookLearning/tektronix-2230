## Re-verified Table 3-1 against a clean scan, and stress-tested the ROM address-mapping model

User request: provided a clean 2-page scan of the service manual's
Table 3-1 (`docs/Memory Map.pdf`) and asked for it to be OCR'd. Every
row matches what `MEMORY_MAP.md` already had from the earlier, messier
partial OCR - no changes needed there, just re-confirmation.

**Then a real scare, resolved by testing rather than assuming.** Read
literally, the table's own row structure says `System ROM 0` (`U9109`)
occupies `E0000-E7FFF` (low half) *and* `F0000-F7FFF` (high half),
while `System ROM 1` (`U9110`) occupies `E8000-EFFFF`/`F8000-FFFFF` -
i.e. each chip's two halves are non-adjacent, which would mean this
project's two main ROM files (`160-3633`, `160-3532`) are actually
*interleaved* across those 4 windows rather than each one flat and
contiguous, as every function name, jump map, and Ghidra segment in
this project currently assumes. User request: "use this to fix some of
the assumptions and the ghidra data and then do a pass to see if the
method names need fixed or if jump locations can be corrected."

Tested directly against real bytes before changing anything - and the
current flat-per-file model held up on every check: `merge_record_
flags_if_changed` (`0xE9472`) decodes as clean, meaningful code under
the current model but lands mid-table (an unrelated small lookup
table) under the table-implied alternate mapping; the `SUB_EAC86`-
pattern far-call's target (`0xEA13B`) is the exact, already-catalogued
string `"or POST\0Display formatting\0..."` under the current model but
garbage under the alternate one; and `reset_plot_home_or_acq` contains
a literal immediate far-call (`9a 0d 00 d7 e7` = `lcall 0xE7D7:0x000D`
= physical `0xE7D7D`) matching the already-confirmed address of
`update_plot_position` exactly, independent of either hypothesis.

**Conclusion after the first pass: no fix needed** - but the user
pushed back, reasonably, since the table's wording really does read
that way literally. Took the pushback seriously: built the user's exact
reading as a real competing Ghidra project (`Tek2230_remap_test`,
throwaway/scratch, real project untouched) - `160-3633`/`160-3532`
recombined into the table's own interleave and imported at the same
segments. Result: the alternate mapping finds **48 fewer functions**
overall (521 vs. 569), and forced decompilation at the exact literal,
Tektronix-hard-coded pointer-table addresses (`0xE9472`, `0xF0A4A` -
read directly from ROM bytes, not chosen by this project) produces
textbook decompiler garbage under the alternate model (repeated
untracked-register pointer arithmetic, a software-interrupt byte
decompiled as an indirect function-pointer call) while the current
model already has real, coherent instructions immediately adjacent to
both.

**Final conclusion**: the addressing model, function names, and jump
targets are unchanged - now confirmed via two independent, escalating
rounds of adversarial testing (manual capstone spot-checks, then a full
competing Ghidra project with its own independent decompiler). The
manual's Table 3-1 "low half/high half of U9109/U9110" wording is most
likely a mistake or transcription ambiguity in the service manual
itself, not a real fact about how these two `.bin` files' content maps
onto CPU address space. Documented the full test, the forced-
decompilation comparison, and this conclusion in `MEMORY_MAP.md`'s ROM
segment section so it doesn't get re-litigated from scratch next time
the same table wording is re-read.
