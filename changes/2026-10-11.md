# 2026-10-11

## Corrected `SUB_EFDC2`'s framing: found a third landing-artifact mechanism (inherited-`bp` + `mov sp,bp` exit collapses the caller's own frame)

Followed up on yesterday's open third case, `SUB_EFDC2` (3 external
callers at `0xE9620`/`0xE9669`/`0xE968B`, all inside a dispatcher
function `FUNC_3633_9611`). Yesterday's tentative framing - "a clean
shared-frame secondary entry point, same class as `0xF4CE8`" - was
wrong. Traced the exact stack arithmetic instead of going by the byte
decode alone, and found a mechanism distinct from either of this
project's two established landing-artifact categories.

`FUNC_3633_9611`'s own prologue (`push bp`/`mov bp,sp`/`sub sp,6`)
never changes before reaching any of the 3 call sites, each of which
pushes `word[bp+8]` then `word[bp+6]` immediately before the far
`lcall`. Working through the stack depth precisely: by the time
`SUB_EFDC2`'s first instruction executes, `sp` sits exactly at
`bp-0xe` - and since `SUB_EFDC2` has no prologue of its own, `bp` is
still `FUNC_3633_9611`'s own `bp`. So `SUB_EFDC2`'s
`mov di, word ptr [bp-0xe]` reads the just-pushed far return address's
own IP half as "di" - not a channel index, confirming the garbage-read
suspicion from yesterday.

The more interesting half: both of `SUB_EFDC2`'s internal branches
converge on the same exit, `mov sp,bp`/`pop bp`/`retf 2`. Because `bp`
was never reanchored, this `mov sp,bp` collapses the stack back to
*`FUNC_3633_9611`'s own frame base*, `pop bp` restores
*`FUNC_3633_9611`'s caller's* `bp`, and `retf 2` returns to
*`FUNC_3633_9611`'s own caller* - never back to the `add sp,2`
instruction immediately following the `lcall`. Every instruction
after each of the 3 `lcall`s inside `FUNC_3633_9611` - the stack
cleanup, the `shl`/`imul` index math, `SUB_E962C`'s `out 0xd1`/
`out 0xd1`/`out 0x8a` hardware shift-register writes, the `[0x502]`
table reads, and the final `jmp L_E972C` - is dead code along this
path, regardless of which way `SUB_EFDC2` branches internally.

This is a third mechanism worth distinguishing from the other two
documented so far: a landing point whose target function is real and
runs to completion without a trap instruction or obviously-bogus
decode, but whose `mov sp,bp`-based exit against an inherited, wrong
frame's `bp` silently discards the *calling* function's own frame and
returns past it. Flagged a general lesson from this: on any future
candidate with a `mov sp,bp`-based exit reached without a fresh
prologue, trace where the inherited `bp` actually points rather than
trusting a clean byte decode alone.

Noted (plausible, not confirmed) that `0xE951A`'s still-unresolved
stack-accounting mismatch ("14 bytes pushed by every caller, only 12
cleaned") has the same 2-byte asymmetry signature this mechanism
produces - worth revisiting with this specific check before re-
deriving its identity from scratch.

Left unresolved: `FUNC_3633_9611`'s `ax=5..14` dispatch path (via
`SUB_EFFEE`, whose own landing point decodes into a confusing region
that appears to cross into the `160-3532` ROM's address space - not
pinned down this round), and whether `FUNC_3633_9611` itself
(`ref_count: 0`, no confirmed callers of its own anywhere) is a real,
reachable function at all. Left unnamed rather than guessed at.

Updated `STILL_PENDING_DECODE.md` and `TODO.md` (corrected the
`SUB_EFDC2` bullets from 2026-10-10) and
`docs/decode-anomalies/landing-artifacts-and-jump-tables.md` (new
"Follow-up, 2026-10-11" section). No renames this round - no
`disasm/gen_disasm_x86.py`/regeneration changes needed.

## Resolved SUB_EFFEE by hand - not dead garbage, a landing artifact into previously-undiscovered code; surfaced a possible disassembler jump-arithmetic bug

The Ghidra probe's degenerate zero-length `CreateFunctionCmd` result
for `SUB_EFFEE` had been read as pointing toward the dead/incoherent-
garbage category. Traced the actual bytes by hand instead of trusting
that summary, and found the opposite: the region starting at
`0xEFF99` (well before `SUB_EFFEE`'s landing point) is real, coherent
code - a `[x+0x57c]` per-channel-settings-table read matching the
neighboring, fully-traced `FUNC_3633_FE2A`. It's an untraced tail of
`FUNC_3633_FF72` (`0xEFF72`) that neither the heuristic scanner nor
Ghidra's own auto-analysis reaches via normal flow tracing (verified
directly against Ghidra's live function/instruction tables - both
empty for this whole stretch), which is why `CreateFunctionCmd`
returned a degenerate body rather than real evidence of garbage.

`SUB_EFFEE`'s landing point (`0xEFFEE`) sits exactly 2 bytes into the
real `jmp rel16 +0x27` instruction at `0xEFFEC`, reinterpreting the
jump's own displacement high byte as a fresh opcode - the same
mechanism as `SUB_EDDE2`/`SUB_EFD99`, not a new case.

New open question surfaced along the way: that `jmp`'s own target (and
`FUNC_3633_FF72`'s own earlier `jmp L_F0019`) doesn't resolve
sensibly. The displacement arithmetic overflows the 16-bit IP; the
heuristic scanner's convention carries that overflow into the next
64 KB of physical address space (landing in `160-3532`), but a real
near jump can't change segments that way, and the alternative (true
16-bit wraparound within the current segment) lands inside
`160-3633`'s own copyright-string header, not code. Flagged as a
possible systemic bug in the disassembler's cross-64 KB jump-target
computation - worth auditing other `L_F0xxx`-labeled near-jump targets
project-wide, and a good job for the emulator (single-stepping real
execution) rather than more static reasoning.

Updated `STILL_PENDING_DECODE.md`, `TODO.md`, and `docs/decode-
anomalies/landing-artifacts-and-jump-tables.md`. No renames - both
`FUNC_3633_FF72` and `SUB_EFFEE` stay unnamed.

## Identified and named `FUNC_3532_B529`/`FUNC_3532_AA08` - the sample-to-position-record helper flagged as "next candidate" across several prior sessions

Picked up the longstanding `FUNC_3532_B529` lead (10 confirmed callers,
`ref_count: 10`, called twice from `FUNC_3633_FC94` and repeatedly
flagged in `TODO.md`). Traced its full body: it reads 2 bytes from a
far-pointer source record, packs an 11-bit value out of them (bits
`[7:5]` of byte 0 OR'd with byte 1 shifted left 3), then takes one of
two paths on a byte "mode" parameter - either overriding that value via
a call to the sibling function at `0xFAA08`, or just adding
`sample-0x14` to it directly - and writes the combined result into a
destination far-pointer record via the already-named
`set_position_record_3532`.

The sibling at `0xFAA08` turned out to be a generic "multiply by a
selectable fraction" helper: a 5-bit code picks one of several fixed
chains of `shr`/`add` that sum shifted copies of an offset into a
binary-fraction approximation (the classic shift-add trick for
multiplying by a constant that doesn't fit one instruction), adds it to
a base value, and clamps the result non-negative. It has exactly one
caller - `FUNC_3532_B529` itself.

Checked the `sample` parameter's real origin by reading the one call
site with a self-describing local-variable prologue nearby (`0xFB2EE`,
just before the `0xFB309` call): it's set from `read_acq_sample_with_
wrap` (or a cached value, when a hold-mode flag in the source record is
set) immediately before the call - confirming this is genuinely part of
the acquired-waveform-sample pipeline, not a coincidental match. All 10
call sites share the identical push shape (far source record, far dest
record, a word value, a zero-extended mode byte), so named both
functions and regenerated:
- `0xFAA08` -> `scale_offset_by_code`
- `0xFB529` -> `compute_sample_position_value`

Left unconfirmed: the exact fraction each of `scale_offset_by_code`'s
`code` values (1/2/4/8/9/other) encodes, and the identity of the
specific source/destination records at each of the other 9 call sites
beyond the one directly traced. The "position record" framing borrows
`set_position_record_3532`'s own established name, but that sink is
otherwise only seen from the print/report subsystem (`build_print_
record_3532`) - plausible this is a shared coordinate-record format
reused for a channel-trace display position, not confirmed as the same
"print record" concept.

Added both to `disasm/gen_disasm_x86.FUNCTIONAL_NAMES`/
`PARAMETER_NAMES` and regenerated `sysrom_3532_3633_heuristic.lst`/
`.symbols.json`. **Could not regenerate `disasm/*_readable.asm` or
`binary/aligned/*_aligned.bin`** this round - `nasm` is not installed/on
`PATH` in this session's environment (`gen_source_readable.py` failed
with `FileNotFoundError` on the `nasm` subprocess call before writing
any output, so the tracked `_readable.asm`/aligned-bin files were left
untouched rather than partially regenerated - confirmed via `git
status` showing no changes to either). Needs a re-run of
`gen_source_readable.py` once `nasm` is available again to pick up
these two new names in the `[bp+N] -> name` comments and aligned
reconstructions. Added matching entries to `FUNCTIONS.md`.

## Resolved `0xE951A`'s stack-accounting mismatch - 3rd confirmed instance of the inherited-bp/mov-sp,bp frame-collapse mechanism

Went back to `0xE951A`'s "14 bytes pushed, only 12 cleaned" mismatch
(open since 2026-10-09, flagged in both `TODO.md` and `STILL_PENDING_
DECODE.md` as worth re-checking with the frame-collapse mechanism
discovered later for `SUB_EFDC2`/`SUB_ECE82`).

It fits exactly. All 6 real callers `lcall` straight to `SUB_E951A`
(`0xE951A`), 0x1A bytes past `FUNC_3633_9500`'s real `push bp`/`mov
bp,sp`/`sub sp,6` prologue. Both of its internal branches converge on
a shared exit, `mov sp,bp`/`pop bp`/`retf 2` - and since the call
skipped the real prologue, that `bp` is never `FUNC_3633_9500`'s own,
it's whatever the *calling* function was using. Checked two of the 6
callers directly (`FUNC_3532_19DF`, `FUNC_3532_1A05`): both have the
identical shape immediately after their own `lcall`+`add sp,0xa` -
their *own* exit is `mov sp,bp`/`pop bp`/`retf 4`. So `SUB_E951A`'s
borrowed exit collapses the stack to exactly the same point the
caller's own exit would have, and returns to *the caller's own
caller* - except via `retf 2` instead of the caller's own `retf 4`, a
2-byte shortfall. That's exactly the "missing" 2 bytes from the
2026-10-09 count (`0xa` + `2` = `0xc`, 2 short of the `0xe` pushed) -
fully explained now, not a new or unexplained bug.

This means `SUB_E951A` is a genuine silent stack-corruption bug in the
original firmware (every one of its 6 callers' own callers gets its
stack left 2 bytes short after the call chain returns) - not a
disassembly artifact. Third confirmed instance of this exact
mechanism, after `SUB_EFDC2` and `SUB_ECE82`. Left open, same as
before: whether there was ever a distinct intended call target, or all
6 sites share one coincidentally-decodable byte offset from a common
source-level expansion (now better supported, since the *mechanism*
is identical across all 6, not just the byte pattern).

Updated `STILL_PENDING_DECODE.md`, `TODO.md`, and `docs/decode-
anomalies/landing-artifacts-and-jump-tables.md`. No renames -
`FUNC_3633_9500`/`SUB_E951A` stay unnamed.

## Exhausted the static-reference search for `FUNC_3633_9611` - no literal reference to it exists anywhere in either ROM

Followed up on `FUNC_3633_9611`'s own open status (`ref_count: 0`,
flagged repeatedly as a "next candidate" since its `SUB_EFDC2`/
`SUB_EFFEE` sub-labels got resolved above): is it genuinely dead code,
or reached indirectly through some table not yet connected to it? The
most plausible candidate was the neighboring `[0x1D10]` per-item
handler table (`VARIABLES.md`), whose `[+6]` field is a far-pointer
handler taking a small command code - superficially similar to
`FUNC_3633_9611`'s own shape (dispatches on a small integer in
`[bp+8]`).

Four checks, all negative:

1. Grepped the full heuristic disassembly for the literal value `9611`
   in any form - the only hit is the label's own definition. No
   `lcall`/`call`/`mov`-immediate anywhere references this address.
2. Byte-pattern-searched both raw ROM binaries for a stored far
   pointer encoding `0x9611` + any of 256 plausible segment words
   (`0xE000`-`0xE970`) - zero hits in either ROM.
3. Searched both raw ROMs for a bare 2-byte near-offset encoding
   `0x9611` with no segment-word constraint at all (in case a table
   stores near offsets under one shared segment rather than full far
   pointers) - also zero hits.
4. Confirmed against `STILL_PENDING_DECODE.md`'s existing 2026-10-10
   finding that `[0x1D10]`'s own boot-init table has no entry at the
   `dest_offset` that would correspond to record 0's `[+6]` handler
   field in the first place - so even the single most plausible
   table candidate doesn't get a ROM-data-driven far pointer there at
   all, let alone one matching this address.

Combined with the existing Ghidra cross-check (also no caller found by
either tool), `0xE9611` does not appear anywhere in either ROM binary
except at its own definition, under every static-reference encoding
this project knows how to construct. This can't rule out a
dynamically-computed call target (built at runtime from a register
plus a computed index, which no static byte search can find) - that
would need the emulator to settle definitively - but given the
exhaustive negative result, the working (hedged, not certain)
conclusion is that `FUNC_3633_9611` is most likely genuinely
unreferenced in this ROM revision: real, well-formed, Ghidra-confirmed
code that nothing in either ROM actually calls.

`FUNC_3633_9611`/`SUB_E962C` stay unnamed.

## Traced the last untraced multi-caller landing-artifact candidate (`SUB_F6DC9`, 4 callers) - found a new wrinkle: a conditional branch inside the misdecoded garbage, not just inert filler

Re-ran `disasm/find_landing_artifacts.py` and checked every 3+-caller
candidate against the existing docs. All were already resolved except
one that had never been mentioned anywhere: `SUB_F6DC9` (`0xF6DC9`, 4
callers).

It's the same landing-1-byte-early mechanism as the rest of this
class: the byte at `0xF6DC9` is the disp8 tail of a real instruction
(`mov word ptr [bp-0x20], di`) belonging to the already-confirmed
`find_item_table_indices` (`0xF6CEA`), and that byte (`0xe0`) also
happens to be a valid opcode (`LOOPNE rel8`) on its own. Read fresh,
it decodes as a 2-byte `loopne` that - if not taken - lands exactly on
the real next instruction, the usual clean reconvergence.

The new wrinkle: `loopne`'s *taken* path is genuinely conditional on
`cx`/`ZF`, unlike every previous instance of this class, whose
misdecoded garbage either always reconverged or was dead regardless of

- none of them ever writes `cx` before reaching `SUB_F6DC9`, so its

resolvable from static reading alone. If the branch were ever taken,

Left open, flagged as needing the emulator: whether `loopne` is ever
actually taken at runtime, and therefore whether this instance is
purely cosmetic (like the rest of the class) or a genuine latent
control-flow hazard. No renames - `find_item_table_indices` already

tail of the "Landing-artifact phenomenon" TODO item: every multi-

## Resolved `[0x6F2]`/`[0x6F4]` (comm ROM) and renamed `flag_value_to_keyword_ptr` - caught and corrected a mid-session alias-delta arithmetic error along the way

Followed up on `command-keyword-table.md` section 4's "block 6" dispatch
table (`FUNC_2998_C411`/`C424`/`C437`/`C44A`/`C45D`/`C470`, flagged
2026-10-09 as "most likely a query-response stringifier for boolean
settings like `SMOoth`/`VECtors`/`GRAticule`/`AUTo`/`FLOw`"). Traced
their shared helper (`SUB_944D5`, comm ROM) fully: it calls
`get_comm_config_flag(index)` (special case: raw `index==0x58` with a
nonzero flag forces the dispatched value to `3`), then returns a far
pointer computed as one of 4 fixed literal offsets (`+6`/`+0x29`/
`+0x145`/`+0x19b`) added to a single base far pointer at `[0x6F2]`/
`[0x6F4]` - not an array-of-4-pointers lookup as initially assumed.

Mid-trace, mis-re-derived the comm ROM's `0x90000-0x97FFF` alias delta
as `-0x10000` instead of the already-documented, correct `-0x8000`
(`docs/comm-rom/address-map-and-cpu.md`). This produced a false "new,
uncovered code region at native `0x80A50`" claim when the wrong target
address force-disassembled with `capstone` into plausible-looking
function prologues. Caught it by reading the actual listing at that
address, which showed the region was already fully, legitimately
disassembled, unrelated code (`FUNC_2998_0A3A`/`FUNC_2998_0A6A`, a
decimal-print trampoline) - a coincidental byte-pattern match, not a
real function. Recomputed with the correct `-0x8000` delta and got
native `0x88A58`, which resolved the apparent contradiction entirely:
that address is the exact start of the already-documented table 1 (the
argument/value keyword table), confirming the original identification
was right all along.

With the correct delta, confirmed `[0x6F2]`/`[0x6F4]` is simply the
base pointer to table 1 (initialized by the comm ROM's own
`init_far_pointer_table` entry `dest_offset=0x22`), and confirmed all 4
of the helper's offset landings byte-for-byte against the raw ROM:
`+6`->`ACCpeak`, `+0x29`->`AVErage`, `+0x145`->`PEAkdet`, default
`+0x19b`->`SAMple`. Three of the four are textbook Tek acquisition-mode
keywords, which corrects the 2026-10-09 "boolean stringifier" framing -
this looks more like an acquisition-mode-style setting selector (hedged,
not proven; `ACCpeak` doesn't cleanly fit a known Tek mode name, and
which of the 6 callers' flag-index constants - `0x3a`/`0x41`/`0x48`/
`0x50`/`0x58`, plus one computed - maps to which real setting is still
open).

Renamed the helper `flag_value_to_keyword_ptr` (key `0x944D5`, the
alias-address call-site label; its native definition site stays
`FUNC_2998_C4D5`/unrenamed, the same native/alias-address split already
established for `get_comm_config_flag`) via `disasm/
gen_disasm_x86.FUNCTIONAL_NAMES`/`PARAMETER_NAMES` and regenerated
`160-2998-14.lst`/`.symbols.json` - verified all 6 call sites now read
`lcall flag_value_to_keyword_ptr`. Updated `FUNCTIONS.md`, `VARIABLES.md`
(new `[0x6F2]`/`[0x6F4]` entry), `docs/comm-rom/command-keyword-
table.md` (replaced the old "working hypothesis" with a dated
correction), `docs/acquisition-and-plotting/ram-far-pointer-table.md`
(follow-up note refining, not overturning, its existing "didn't yield
new functions" conclusion about this same init table - some of its
targets are legitimate data-table pointers, not code, so they were
never going to force-disassemble as sensible instructions), and
`STILL_PENDING_DECODE.md` (correction to the 2026-10-09 "boolean
stringifier" entry).

General lesson flagged from the self-caught error: `capstone` producing
plausible-looking instructions from force-disassembled bytes is not, by
itself, evidence of a real function - always cross-check the candidate

## Decoded "block 7" as a large shared function-reference table; found the SET-side counterpart of the acquisition-mode-style flag family

Fixed an internal inconsistency in `command-keyword-table.md` section 4
(introduced 2026-10-09): its per-record table showed far pointer A's raw
bytes under a column labeled for far pointer B, while crediting it with
far pointer B's actual resolution target. Both pointers are now decoded
and labeled correctly - far pointer A (`907c:xxxx`) resolves into
"block 7", far pointer B (`941f:xxxx`) resolves to the 6 known handler
functions directly.

Decoded "block 7" itself (file offset `0x872B`-`0x8A57`, previously
flagged as unidentified in `UNKNOWN_DATA.md`): it's a second shared
table of 6-byte records (`[1-byte id][1-byte marker][2-byte offset]
[2-byte segment]`). Found that the segment field needs **two different
resolution rules** depending on its own value - `>=0x9000` uses the
already-confirmed `0x90000`-`0x97FFF` alias (`-0x8000`), `<0x9000`
resolves directly with no alias correction (the comm ROM's lower half,
`0x80000`-`0x87FFF`, was never aliased) - a wrinkle not previously
documented, and the reason an earlier pass at this table (assuming one
fixed segment) stalled at only 18 resolved targets. Re-walked the table
from each of block 6's 6 known starting offsets with the corrected
per-record rule: 6 of the 7 starting points only cycle through a short
shared ~6-record window (confirming they're entry points into one array,
not separate tables), but the 7th continues linearly for at least 39
consecutive records - **35 distinct targets total**, every single one a
real, already-disassembled function entry point (`push bp`), all with
`ref_count: 0`/`functional_name: null` in `160-2998-14.symbols.json`.
This table looks like the actual, previously-unrecognized reference
mechanism for a meaningful slice (~11%) of the comm ROM's 310 total
orphan functions.

Traced 8 of the 35 (`FUNC_2998_C1FA`/`C22F`/`C264`/`C2A6`/`C2E8`/`C301`/
`C31B`/`C356`) as the **SET-side** counterpart of the GET-side flag
family already documented (`flag_value_to_keyword_ptr`'s 5 flag indices
`0x3a`/`0x41`/`0x48`/`0x50`/`0x58`) - they call `set_comm_config_flag`
with these same indices, mostly deriving the stored 0-3 value from a
brand-new raw byte `[0x5fe]` via comparisons against `7`/`1`/`0x43`
(`'C'`)/`0x35` (`'5'`). Two more functions in the same family
(`SUB_94559`/`0x8C559`, `SUB_945CF`/`0x8C5CF`) reveal new fields of the
already-documented `[0x732]`/`[0x734]` command-context record (`+0x28`,
`+0xf`, `+0x17`) and - the headline find - tie the family directly to
the real `LONg` command (`[0x732]+0x1F == 0x14`, the confirmed dispatch
ID for `LONg`, cross-checked against `rs232-live-session-2026-09-14.md`'s
live-hardware trace and `docs/programming-manual.md`/`docs/options.md`'s
description of what `LONg` actually does). A third function
(`SUB_946C2`/`0x8C6C2`) mirrors the GET side's `0x58`-is-narrower special
case on the SET side. Full writeup with mechanism detail in
`docs/comm-rom/command-keyword-table.md`'s new "## 5." section.

Updated `VARIABLES.md` (`[0x732]`/`[0x734]` entry: new fields, cross-ref
to `0x85367`'s dual role; new `[0x5fe]` entry) and
`STILL_PENDING_DECODE.md`. No renames made yet for any of the newly
traced functions - deferred until the real-world meaning of the flag
indices and `LONg`'s exact tie-in are clearer, per the project's
existing "settings-byte-translator family" precedent. Still open: the
table's true start/end boundaries (stopped at 39 records in a region
sized for roughly 135), the `id`/`marker` byte semantics, and what code
actually reads a record's `id`/`marker` to select it at runtime - that
dispatch-selection code has not been found.

## Decoded `init_far_pointer_table`; resolved the `[0x6EA]`/`[0x6F6]` "zero comm-ROM writes" dead end from 2026-10-09

Still hunting block 7's reader, decoded `init_far_pointer_table` (comm
ROM, `0x80133`) fully: 31 `(dest_offset, far_ptr)` entries, copied into
`ES:[DI]` via a `movsw`-pair loop (`ES=0x8fed`), convertible to this
project's `[0x6xx]`/`[0x7xx]`-under-`DS=0x8f80` convention via `+0x6D0`
(verified exactly against the already-known `[0x6F2]` entry). Found
`[0x6FA]` (`dest_offset=0x2a`) initialized to `0x887C4` - block 7's own
confirmed start address - but, unlike every other entry checked, no
static reader for it exists anywhere in the disassembly (grepped for
both the literal text and the raw byte pattern, both empty). Still
genuinely open.

While decoding the other entries, found `dest_offset=0x1a` (`[0x6EA]`)
and `0x26` (`[0x6F6]`) among them - **directly contradicting**
`command-keyword-table.md`'s 2026-10-09 conclusion (and
`STILL_PENDING_DECODE.md`'s matching note) that tracing every reference
to these two addresses found "zero comm-ROM writes to either address."
That conclusion came from a literal-displacement-instruction grep
(`mov [0x6ea], ...` etc.) and was correct as far as it went - it simply
couldn't see this write, which happens register-indirectly through
`ES:DI` inside `init_far_pointer_table`'s generic copy loop, with the
destination offset sitting in a data table rather than an instruction
operand.

Decoding both targets: `[0x6EA]` → `0x88D4A`, which turns out to be
`command-keyword-table.md` section 2's own 26-entry dispatch/index
table, byte-for-byte - not a second table at all. This also fixed a
separate, independent bug in that section: its documented start address
(`0x8D3E`) was wrong by 2 phantom records (bytes there don't match the
`0xFF`-marker/`0x90xx`-segment record shape at all); the real start,
`0x8D4A`, matches both `init_far_pointer_table`'s pointer and the exact
`26*6`-byte span down to the table's already-correct end boundary.
`[0x6F6]` → `0x889BC`, a genuinely new, previously-undocumented second
26-entry table in the identical format, indexing into table 1 (the
argument/keyword table) instead of table 3.

Confirmed both tables' first-letter-bucket structure directly by
decoding all 26 slots of each: non-empty slot `N`'s resolved text
starts with `chr(0x41+N)` in every case (`A`→`ACQuisition`/`ABOrt`,
`B`→`BYTe`/`BASegain`, ... `Z`→`ZZZZ`/empty), with each table's empty
slots sharing one sentinel address. This resolves `FUNC_2998_5115`/
`FUNC_2998_519A`'s "real letter-table base is still unknown" status
from 2026-10-09 - they are table 2 and this new table, respectively.
One minor loose end on the table-1 side: several slots (`D`/`L`/`R`/
`S`/`U`/`V`/`Y`) resolve 2-3 bytes before their keyword's actual length
byte, landing in table 1's still-undecoded per-entry metadata gap
rather than exactly on it.
