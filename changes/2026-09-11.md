## Found and resolved the L_EDA0A long-jump mystery

Built `disasm/analyze_loops_vs_functions.py` per a direct request to
"compare loops to functions": classifies every bare `L_` branch target
as local control flow (loop/goto) vs. `cross-fn` (reached from a
*different* function's address range - shared code that never got a
proper label). Found 15 `cross-fn` targets, matching most of the
already-documented "un-prologued entry" cluster (good independent
validation), plus a follow-up suggestion to weight by raw jump
*distance* - which singled out `L_EDA0A` as a 15,226-byte outlier (16x
the next-largest).

Chasing it down resolved the mystery: `L_EDA0A` is `SUB_F1581` landing
2 bytes into `compute_and_draw_scale_marker`'s (`SUB_ED9BC`, newly
named - the timebase/frequency scale-marker label builder for the
readout graticule) own `mov [0x1BEC],0x20` instruction - the same
landing-mid-instruction-then-reconverging class already documented for
`SUB_E90A5`/`SUB_E92B0`. This also closed an old thread that had
guessed `SUB_F156E`/`SUB_F1581` landing inside another function meant
"cross-ROM code sharing" - it's this landing-artifact class instead.
Manually verifying the `cross-fn` list also found 2 heuristic false
positives (boundary/self-loop artifacts, not real cross-function
sharing) and one genuine new find: `sync_shift_register_output` (was
`SUB_F750A`), a real secondary entry point into `update_display_mode_
flags` - which turned out to be the function that *sets* the
`[0x1BEC]` bound `compute_and_draw_scale_marker` reads.

## The "un-prologued entry" theory evolved through 3 rounds of self-correction

1. Hypothesized several `lcall`s might share *one open frame* across
   multiple never-returning steps (`SUB_F750A`/`SUB_F7603`, `SUB_
   EFBA5`).
2. **Found counter-evidence and corrected it**: their actual caller
   invokes both as ordinary sibling subroutines, not sequential steps
   of one chain - weakening that literal claim.
3. **Refined it, then confirmed it with a traceable example**: `SUB_
   F750A`/`SUB_F7603` both end with a bare `retf` (caller-cleans-
   stack, unlike almost every other function in the codebase), and
   their real caller uses a completely ordinary push-args-then-`lcall`
   - most likely a compiler code-size optimization that "outlined"
   tightly-coupled helper code out of its caller's body without giving
   it its own frame. Then found direct proof: `SUB_ED0AE` never
   touches `bp` at all (2 global moves + an `lcall`), and the function
   *it* calls (`SUB_F5184`) also has no prologue but reads `bp`-
   relative locals - those locals can only belong to `SUB_F4150`'s own
   frame, 2 calls up the chain, since neither intermediate function
   ever pushed its own `bp`.

This let several more functions in the cluster be named confidently
once their *mechanism* was understood, even without a conventional
prologue: `apply_pending_position_delta` (`SUB_F7603`), `compute_and_
format_sample_delta_readout` (`SUB_F4150`), `snapshot_index_and_
format_number` (`SUB_ED0AE`, only fully named the next session once
its formatter's tail was mapped), `dispatch_item_handler_if_enabled`/
`tag_position_marker_and_dispatch` (`SUB_EDFFD`/`SUB_F5D89`), and
`clear_readout_attrs_for_item` (`SUB_EEA58`). Also documented (not
renamed) the decimal-formatting engine `SUB_F5184`/`L_F50FA` sits in -
a clear `itoa`-style loop with a per-item configurable decimal-point
position, entangled enough that its own entry-point boundaries stayed
ambiguous even once its behavior was understood.
