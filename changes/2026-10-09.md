## Found (the hard way) that the documented disasm-regen recipe was missing a required step for the comm ROM

While regenerating `.asm` output after the rename above, `git diff
--stat` showed `disasm/160-2998-14.asm` with a wildly disproportionate
diff (~26000 lines) versus the main ROMs' expected few-line diffs -
previously-decoded real instructions (`FUNC_2998_0233` and hundreds of
others) had turned into raw undecoded `db` byte dumps. Root cause:
`gen_source.py`'s bare CLI invocation (`python gen_source.py <nasm>`,
exactly what `TODO.md`'s own regen recipe said to run) defaults
`entry_points=None`, i.e. *proven-reachable entries only* - correct
for `160-3633`/`160-3532`, but the comm ROM's committed `.asm` has
always included ~20000 additional instructions reached only via `gen_
disasm_2998.py`'s heuristic push-bp prologue scan. `TODO.md`'s recipe
listed `gen_disasm_x86.py`, `gen_disasm_mainrom_heuristic.py`,
`gen_source.py`, `gen_source_readable.py` - it never mentioned the
comm-ROM-specific driver needed to preserve that heuristic layer.

Found the actual intended driver already exists and had simply gone
unused this session: `disasm/gen_source_2998.py`. It regenerates
*only* `160-2998-14.asm`, with entry points = `g.ENTRY_POINTS +
gen_disasm_2998.build_entry_points()[1]` (comm-ROM heuristic only).
Running it reproduced the committed file byte-for-byte (zero diff) -
confirming it's the right recipe and that the rename itself never
touched the comm ROM at all, as expected.

Along the way, tried a plausible-looking alternative first - borrowing
`validate_all.py`'s entry-point formula (`g.ENTRY_POINTS + comm-
heuristic + main-ROM-heuristic`, used there for a one-shot NASM round-
trip check across every chip at once) and feeding *that* into `gen_
source.py` instead. It also round-tripped byte-identical, but left a
~150-instruction cosmetic artifact: the diagnostic comment after `;`
on some jump/call lines showed a wrong operand value, because the
extra main-ROM heuristic entries alias into the same physical
addresses the comm-ROM walk visits, and the single `visited[phys]`
dict entry gets overwritten by whichever walk visits last - the real
emitted instruction (derived separately, from NASM's own label
resolution) stayed correct throughout; only the trailing human-readable
comment was affected. Confirmed via an address-keyed diff against the
previous committed file that every real instruction byte and address
matched exactly before and after. Not worth chasing further once the
real `gen_source_2998.py` driver was found - recorded here, and in
`TODO.md`'s corrected recipe, so nobody reaches for `validate_all.py`'s
formula for this purpose again.

## Closed out the "unknown data" deep-dive's last 6 unconfirmed leads - one new function found, five gaps explained

Picked up exactly where `TODO.md`'s own "next step if picked up" note
left this long-running thread: 6 `UNKNOWN_DATA.md` blocks that looked
like real code by eyeball (clean prologues, or references to already-
tracked RAM variables) but hadn't been rigorously confirmed the way
2 earlier blocks (findings 7 and 10, from the 2026-09-22 sessions)
already were - no caller/far-pointer search, no control-flow
convergence check. Traced all 6 the same way, one at a time. None
turned out to be false leads.

**`160-3633` `0xE77F8-0xE783C` (69B) is a brand-new standalone
function**, not previously represented anywhere in the symbol table.
Manually disassembling the full range (through its own `retf 4`
epilogue, ending exactly 1 byte before `udiv32`'s own entry at
`0xE783D`) found a complete function with its own `push bp; push bx;
push cx; mov bp,sp` prologue - structurally identical to the already-
named `sdiv32` (`0xE77AE`) except for exactly one difference: `sdiv32`
saves `dx XOR [bp+0xc]` (the XOR of both operands' sign bits) before
computing `abs()` of each operand and reapplying that saved sign at
the end; this new function instead saves plain `dx` (the dividend's
sign alone) - so the divisor's sign never affects the final result,
only its magnitude does. It also calls a different point inside
`udiv32` (`0xE7866`, `+0x29` into `udiv32`'s body - a secondary entry,
not `udiv32`'s own primary entry at `0xE783D` that `sdiv32` calls; not
reconciled further). Named `sdiv32_unsigned_divisor`.

Root-caused *why* neither existing discovery mechanism had ever found
it: no literal far-pointer bytes reference `0xE000:77F8` anywhere in
any of the 3 ROMs (checked directly - the caller is still genuinely
unresolved, the same "confirmed code, caller not found" category as
the `0xE956E` pair from finding 10), and the mainrom heuristic's
push-bp prologue scanner (`gen_disasm_mainrom_heuristic.py`'s
`PROLOGUE = b"\x55\x8b\xec"`) structurally cannot match it either -
that signature requires `mov bp,sp` *byte-adjacent* to `push bp`, and
this function has `push bx; push cx` in between. Wrote a one-off scan
for that exact "delayed prologue" shape across both main ROMs: only 3
instances exist project-wide - `ashr32` and `sdiv32` themselves (both
already known, both missed by the same scanner for the same reason)
and this one.

Adding the name to `gen_disasm_x86.FUNCTIONAL_NAMES` alone changed
nothing - confirmed by checking the regenerated symbol table found no
`E77F8` key at all. A `FUNCTIONAL_NAMES` entry only renames an address
the walker is *already* visiting; since neither the proven entry
points nor the heuristic scanner ever reaches `0xE77F8`, it also needed
a manual `(0xE77F, 0x0008, "sdiv32_unsigned_divisor")` tuple added to
`ENTRY_POINTS` to actually make it appear. Regenerated the full
pipeline (`gen_disasm_x86.py` -> `gen_disasm_mainrom_heuristic.py` ->
`gen_source.py` -> `gen_source_readable.py` -> `gen_source_2998.py`,
per `TODO.md`'s corrected recipe) and confirmed the resulting `git
diff --stat` touched only `160-3633`'s own files (`.asm`,
`_readable.asm`, both `.lst`/`.symbols.json` pairs, and its aligned
bin) - `160-3532` and the comm ROM were untouched, as expected for a
single-chip rename.

**The other 5 blocks are all gaps *inside* already-reached functions,
not new functions:**

- `160-3633` `0xE9180-0xE91EF` (112B) is the shared, no-own-frame tail
  of an existing switch/case dispatcher - falls through cleanly from 4

- `160-3633` `0xE9404-0xE9471` (110B) bridges an already-reached-but-

## Built the `ACQ_AB` coupling stub - emulator now passes this self-test, found 2 new ones behind it

Picked up right where the first `ACQ_AB` entry above left off (write
side deliberately left unstubbed, "guessing one would misrepresent
understanding"). Re-read `step_acq_ab_addr_walk`'s and
`update_menu_position`'s full disassembly by hand to pin down two
things that session's analysis hadn't nailed down: the exact position-
to-pattern formula (confirmed: `pattern = (0xFFE >> (0xB-p)) & 0xFFE`
for `p<0xB`, else `(0xFFE << (p-0xB)) & 0xFFE`), and - new this
session - that `p` is **0-indexed**, not 1-indexed: `update_menu_
position`'s case-1 init call sets the position byte to `-1`, and every
case-3 step call increments it *before* returning it, so the first
step call returns `0` (a trivial, always-passing `0`-vs-`0` comparison
against plain RAM's default), the second returns `1`, and so on. This
is why the captured failure sequence has only 11 entries starting from
`2` (position 1) rather than 12 starting from `0` (position 0) - a
detail worth recording since it's easy to misread as "the loop starts
at position 1," which the `update_menu_position(1, 0x15, 0)` call's
literal `1` argument encourages but is actually unrelated (that `1` is
the *selector/mode* argument, not a position).

First implementation of `io_stubs.AcqAbAddrWalkStub` copied
`CommPresenceProbe`'s shape exactly: hook `UC_HOOK_MEM_WRITE` on the
Acquisition Mode Register's address (`0x437BE`), keep a step counter,
increment it on every write, compute the pattern, write it into
`0x4377E`. A live boot trace immediately showed this was wrong - junk
like `ACQ_AB : read-back 7E <> 0` (the stub's "actual" output running
far ahead of, and uncorrelated with, the real "expected" value) instead
of the failures just disappearing. Root cause: **other, unrelated self-
tests earlier in the dispatcher's sibling list also write `0` to this
same physical register for their own purposes**, so a plain address-
keyed write hook fires several extra times before `selftest_acq_ab_
addr_walk` ever gets its own turn, desyncing the counter from the very
first real step. Fixed by hooking `UC_HOOK_CODE` on the *exact
instruction address* instead (`0xE300C`, the `mov byte ptr es:[di], 0`
inside `step_acq_ab_addr_walk` itself) - the same "hook the specific
instruction, not every access to an address that might mean several
different things" technique `io_stubs.DiagnosticTextCapture` already
documents and uses, for the same underlying reason.

Verified end-to-end with a scripted `debugger_core.Debugger` run
(`interactive.py`'s and `tui.py`'s shared engine - not `emu.py`, which
doesn't carry the richer self-test-coupling stubs): a full boot trace

## Traced `HS_ACQ`/`TBD hs/2` - both are the same acquisition-memory-address-buffer register as `ACQ_AB`, read instead of address-walked

Picked up the "not yet investigated" `HS_ACQ`/`TBD hs/2` failures left
behind by the `ACQ_AB` coupling-stub work above. Traced the call chain
(`run_adc_selftest`/`wait_stable_measurement`/`verify_pattern_with_

Reading that function's full disassembly body

a plain busy-flag+value read instead of `ACQ_AB`'s address-line walk.

`"acq_mem cntr"` = *acquisition-memory counter*, not "ADC counter."

not a counter/PROM as first guessed mid-session - though nothing in
this call chain ever writes the incrementing-ramp pattern `verify_
pattern_with_report` later checks there, so what fills it (real
hardware during a capture cycle, or untraced firmware) is still open.

## Built the `HS_ACQ`/`TBD hs/2` coupling stub - resolved the `acq_mem cntr` mismatch for both

Continued directly from the above: re-derived `run_adc_selftest`'s
full parameter map byte-exact against `selftest_hs_acq`'s actual
pushed arguments (previously only partially mapped), by reading its
whole body end-to-end alongside the live push-order disassembly at
`0xE28FE`-`0xE2936` - correcting a discrepancy flagged mid-derivation
(a prior guess had `[bp+0x14]`/`[bp+0x16]` backwards, which would have
implied an implausible zero-fill count for `TBD hs/2`).

**Full map**: `bp+6`/`bp+8` = far-ptr report label; `bp+0xa` = zero-
fill start-offset component (`(buffer+0x1000)-[bp+0xa]`), also
forwarded to `configure_measurement_hw`; `bp+0xc` = zero-fill count
component (`[bp+0xc]+[bp+0xa]`), also forwarded to `configure_
measurement_hw`, *also* reused as one of the two final-comparison
thresholds; `bp+0xe`/`bp+0x10`/`bp+0x12` = forwarded straight through
to `configure_measurement_hw`'s remaining 3 register-write params, no
other local use; `bp+0x14` = busy-wait retry-count limit; `bp+0x16` =
the other final-comparison threshold; `bp+0x18` = failure-message flag
bits, only read on the busy-timeout-never-cleared path - `selftest_hs_
acq`'s call doesn't even supply it (9 pushes total, not 10), which is
harmless only because that path is never reached when the busy bit
already reads clear. Confirmed against the live capture: `bp+0xc=0xa2`
+ `bp+0x16=9` = `0xAB`, exactly matching `"HS_ACQ : acq_mem cntr 800 <>
0AB"`.

The key realization that made a general stub possible rather than a
per-self-test hack: `run_adc_selftest`'s comparison code is the *same*
code for every caller, so a stub that reads `[bp+0xc]`/`[bp+0x16]`
live off the stack at the exact read instruction (`0xE137A`) resolves
`TBD hs/2` too, without ever decoding `run_indexed_adc_selftest`'s own
`[0x1DCC]` device table. Added `io_stubs.AdcSelftestReadbackStub`
(hooked `UC_HOOK_CODE` at that one instruction, same "hook the
instruction, not the address" reasoning `AcqAbAddrWalkStub` already
established, since a plain address hook on `0x4377E` would also catch
the busy-wait loop's own earlier reads and `verify_adc_calibration`'s
unrelated `ACQ_AB` read of the same physical register) and wired it
into `debugger_core.py`'s `_setup_stubs` alongside `AcqAbAddrWalkStub`.

**Verified live**: a full boot trace (`Debugger.run(60_000_000)`) no
longer prints either `"acq_mem cntr"` mismatch line; the `"fill @"`
ramp-pattern mismatch (the separate, still-open `[0x31E]`/`0x48000`
question) persists unchanged for both, and the run now continues one
self-test further into a third, previously-unreached, still-unnamed
`"TBD ps/2"` failure with the same `"fill @"` shape. Ran an A/B
comparison (same trace with the stub reverted via `git stash`) to
confirm the run's eventual `halt_cpu` panic stop at physical `0xF1611`
happens identically either way (5513062 vs. 5519061 instructions -
the tiny difference being only the new hook's own overhead) - a
pre-existing stopping point unrelated to this change, not a regression
introduced by it.

## Built the `verify_pattern_with_report` "fill @" coupling stub - resolved it for `HS_ACQ`, `TBD hs/2`, and `TBD ps/2`, then found a fourth, structurally different self-test failure

Picked up exactly where the above left off: re-read `verify_pattern_
with_report`'s (`0xE1116`) full body to pin down its loop mechanics
before writing anything, per this project's "derive the mechanism
fully before building a stub" standing practice. Two things not
previously documented fell out of that re-read: (1) the running
"expected" value, tracked in a local (`[bp-0xe]`, seeded from
`[bp+0x12]`), is updated *after* each comparison by adding `[bp+0x16]`
or `[bp+0x14]` depending on the loop index's parity relative to the
starting index, then masked `&0xFF` - it wraps mod 256, not a 16-bit
running sum; (2) mismatch *printing* silently stops once the loop
index exceeds `6` (`cmp [bp-0xa],6; jg <epilogue>`), even though the
comparison loop itself keeps running the full `[bp+0xe]`..`[bp+0x10]-1`
range - this is why every captured failure only ever showed a handful
of `"fill @"` lines regardless of window size, previously (incorrectly)
chalked up to capture truncation rather than a real print-suppression
branch.

The key realization, same shape as the previous stub's: since the
firmware already computes its own "expected" value as a local, there's
no need to synthesize real hardware content from nothing - just mirror
`[bp-0xe]`'s current value into the buffer byte about to be read, one
instruction before the comparison executes (`0xE113A`, `mov dl, byte
ptr es:[bx+di]` - by this point `es:bx+di` already holds the correct
target address, computed by the two instructions just before it).
Added `io_stubs.AdcRampFillStub` (hooked on that exact instruction
address, same anti-ambiguity reasoning as every other stub in this
file) and wired it into `debugger_core.py`'s `_setup_stubs` right after
`AdcSelftestReadbackStub`.

**Verified live**: a full boot trace no longer shows `HS_ACQ` or `TBD
hs/2` *at all* - both self-tests now pass completely. The previously-
unreached `TBD ps/2` is fixed the same way with no further changes,
confirming it shares the exact same code path. The run progresses
further still, into a **fourth, previously-unreached failure**:
`MM_ACQ` (`selftest_mm_acq`, `0xE26D6` - already named from an earlier
session's string-reference pass, but not previously traced in any
depth). Reading its body showed it does *not* call `verify_pattern_
with_report` at all - it has its own inline loop, index `[bp-8]`
stepping by 2 from `0` to `0x1e`, that loads two *adjacent* scratch-
buffer bytes and checks whether their difference equals one of two
fixed allowed values (`0xFF` or `0xC7`); anything else is a mismatch,
reported as `"MM_ACQ : fill @ <offset> : <delta> <> C7"` (only `0xC7`
is ever shown, even though `0xFF` is also accepted). It reuses the
same "stop printing past loop index 6" idiom found above, landing on
the identical last-printed index (`6`) despite the different step.

Deliberately did **not** write a stub for this one: unlike `verify_
pattern_with_report`, there's no single already-computed "expected
value" local here to mirror - satisfying the check means picking
specific byte *content* (two adjacent bytes whose difference happens
to be `0xFF` or `0xC7`), which would be guessing at what real
acquisition hardware produces (plausibly some DAC/ramp rollover
characteristic) rather than deriving it from the self-test's own
logic. Left open, following the same "don't guess" practice that's
governed every stub in this file so far.

## Built the `wait_stable_measurement` ready-bit coupling stub - resolved `CDT`'s `"PRE-DETRIG"` failure, then found a different, still-open numeric-range failure behind it

Continuing past `MM_ACQ` in the boot trace, the next-reached self-test
failure was `CDT` (`selftest_cursor_delta_time`, `0xE2CEC`), reporting
`"CDT : PRE-DETRIG <hex arg>"`. Traced the full call chain:

- `measure_cursor_delta_time` (`0xE2CFB`) calls `wait_stable_

  `0x8e,0x8a`, takes `delta = result1 - result2`, then separately
  range-checks `result1` against `[0x55, 0x73]` and `delta` against
  `[0xc8, 0xd2]` - printing `"uncaled : min = <value>"` / `"uncaled :
  delta = <value>"` via `format_decimal_word` on failure, independent

- `wait_stable_measurement` polls a byte at `[0x32A]` (physical
  `0x437F7`) for 2 consecutive identical reads (countdown from `0x200`;
  times out to the `0xFFFF` failure sentinel with `"TIME-OUT"` if it
  never stabilizes). Once stable, it reads `[0x322]` (physical
  `0x4377E` - the *same* Acquisition Memory Address Buffer register
  `verify_adc_calibration`/`run_adc_selftest` already use) twice more:
  once to fold a soft status bit (`0x100`) into the return value if bit
  `0x4000` is set (no failure path, just extra info bits), once to
  check bit `0x2000` - if clear, prints `"<label> : PRE-DETRIG <hex
  arg>"` and forces the return value to `0xFFFF` too.

executes. Deliberately left bit `0x4000` untouched - plain RAM's
default already keeps it clear, which must hold, since setting it
would fold an extra `0x100` into the return value and corrupt
`measure_cursor_delta_time`'s subsequent *raw-value* range checks.
Confirmed the new bit is mutually non-overlapping with every other
stub already read-modify-writing this same register (`AcqAbAddrWalk
Stub`/`AdcSelftestReadbackStub` use bits 0-11, `CommPresenceProbe` uses

halted (hlt) at 0x0F1611` without today's stubs vs. `16 5211100 halted
(hlt) at 0x0F1611` with all of them - same halt address, confirming no
regression.

`"uncaled : min = 0"` / `"uncaled : delta = 0"`. `wait_stable_
measurement` now successfully returns the real (stabilized) value of

both `measure_cursor_delta_time`'s expected windows (`[0x55,0x73]` for
the raw value, `[0xc8,0xd2]` for the delta of two such reads). Unlike
the ready-bit check, there's no single branch-implied target value to

calibration constant, which looks like it needs either more hardware
documentation or a derivable internal formula, not a guess. Left open

## Traced `ROMS`'s `"MISMATCH,14,4C,14"` fully - genuinely resolved, not an emulator gap at all

Continuing down the trace past `FP_a2d`, `ROMS` (`selftest_rom_
checksum`, `0xE16EA`) was the next unidentified failure. Despite its
`"MISMATCH"` string, this isn't a computed checksum - it's a
cross-chip *revision-byte* consistency check:

- Reads a one-byte "revision" field (offset `+4` of a small embedded
  ROM header - an id word, 2 BCD-packed part-number digit bytes, the
  revision byte, a fixed `0xEB` sentinel, then a `"Copyright..."`
  string) via two far pointers, `[0x1DD4]` and `[0x1DD8]`, pointing at
  literal `0xE000:0000` and `0xE800:0000` - i.e. physical `0xE0000`
  and `0xE8000`, the start of `160-3633`'s own low and high 32KB
  halves. If the two bytes differ, it jumps straight to the
  mismatch-message path (the `check_comm_installed_gate`-gated
  third-compare branch below it only runs when they're *equal*). The
  message's 3rd value always comes from a separate, fixed literal far
  pointer `0x8000:0000` - physical `0x80004`, `160-2998`'s own header
  - regardless of which branch is taken.
- Read the real bytes directly from `binary/160-3633-14.bin` and
  `binary/160-2998-14.bin`: `0xE0004 = 0x14` (matches the `-14`
  revision this exact dump's own header *and* filename agree on),
  `0xE8004 = 0x4C`, `0x80004 = 0x14`. This reproduces the live
  `"ROMS : MISMATCH,14,4C,14"` trace exactly, byte for byte, using
  nothing but real ROM content the emulator already maps correctly -
  **no stub needed or possible here; this isn't an emulator-fidelity
  question at all**.
- This also corrected a mistake from earlier in the same investigation
  this session: I'd initially gone looking for where `[0x1DD4]`/
  `[0x1DD8]` get initialized, concluded the only known candidate
  (`init_far_pointer_table_sysrom`'s already-documented 82-entry
  table) didn't cover them, by comparing the table's dest-offsets
  directly against `0x1DD4`/`0x1DD8`. That comparison was wrong - the
  table's dest-offsets are relative to its own `ES=0x209` base, while
  `[0x1DD4]`/`[0x1DD8]` are flat-space offsets under `DS=0x41`; once
  converted through both base segments (`0x2090+0x154 = 0x21E4 =
  0x410+0x1DD4`), entries 68/69 of the table turn out to be exactly
  this pair, storing the `E000:0000`/`E800:0000` far pointers. The
  table *does* cover every variable it was always documented to -
  this was a conversion mistake on my part this session, not a gap in
  the table or in the earlier documentation of it.
- **One open question left, genuinely open rather than guessed**:
  whether physical `0xE8000` is supposed to be a second physical
  EPROM chip's own header - i.e. whether `160-3633`'s logical 64KB
  range is actually built from two separately revision-stamped 32KB
  chips (which would partially vindicate the service manual's Table
  3-1 "low/high half of U9109"/"U9110" chip-pair language that
  `MEMORY_MAP.md` had set aside, for an unrelated question about
  address-space interleaving with `160-3532` that remains correctly
  rejected) - or whether `0x4C` is just an incidental code/data byte
  with no real header at that location, making the self-test's check
  spurious on this particular dump. The actual bytes at `0xE8000`
  don't contain a recognizable `"Copyri"` run the header at `0xE0000`
  has, which leans toward "incidental byte," but isn't conclusive.

## Traced `COMM_ROM`'s `"0C8F <> 2BA3"` checksum too - also genuinely resolved, not an emulator gap

Last fully-uninvestigated diagnostic line in the trace. `selftest_
comm_rom` (`0xE1E3E`) calls the already-partially-documented generic
engine `verify_rom_checksum_and_report` (`0xE1816`) with concrete
args this session nailed down exactly by reading its far-pointer
pushes at the call site:

- Stored/expected value location: physical `0x80000` - `160-2998`'s
  (the comm ROM) own first 2 bytes, read big-endian.
- Two chained ranges fed to `compute_range_checksum` (`0xE45A6` - a
  shift-left-then-add-with-carry running checksum, 1 byte at a time,
  inclusive bounds; already generically documented in `FUNCTIONS.md`
  but not previously tied to concrete addresses for this caller):
  physical `0x80002-0x87FFF` (the comm ROM's low 32KB, deliberately
  starting 2 bytes in to exclude its own checksum header), chained
  into `0x90000-0x97FFF` (the upper 32KB via its real, independently-
  confirmed address - not the "RAM alias" misreading this project
  corrected away from in `MEMORY_MAP.md` back in September).

Reimplemented the exact same algorithm directly over `binary/160-
2998-14.bin` in Python: computed chained result = `0x0C8F`, stored
expected (`rom[0]<<8|rom[1]`) = `0x2BA3` - **reproduces the live
`"comm_rom_0 0C8F <> 2BA3"` trace exactly, byte for byte**, using
nothing but real ROM content. Like `ROMS` above, this is conclusively
not an emulator-fidelity gap - the entire computation is deterministic

dumped `160-2998-14.bin` simply doesn't satisfy its own embedded
checksum; there's no further emulator-side work possible here, only
a possible-but-unconfirmed hypothesis that this and `ROMS` are related
(both are content-consistency checks this specific set of ROM dumps
fails).

## Traced `COMM_LB`'s `"FGET NOT SET"`/`"FGET NOT CLEAR"` too - a real stub candidate this time, not another resolved-ROM-content finding

Correction to the paragraph just above: `COMM_LB` was not actually
traced yet at that point, only identified by name from an earlier
session - it was the real last fully-uninvestigated diagnostic line,
not `COMM_ROM`.

`selftest_comm_fget_flag` (`0xE1FBC`, called once from `selftest_comm_
loopback_b`, `0xE1DB3`) runs two sequential subtests, gated on
`[0x1BFA]`/`[0x1B7A]` both being nonzero (confirmed true in the live
trace, since both messages print). Each subtest writes a literal
command byte to physical `0x406F3` (`es:[0x6F0+3]`, `ES=0x4000`) -
the 4th register of the comm option's 8-register UART/GPIB bank
(`0x406F0`-`0x406F7`) - then checks `comm_stat` (`0x4067C`) bit `0x4`
and `comm_param` (`0x406BC`) bit `0x80`. Subtest 1 writes `0x86`,
needs *both* bits SET to pass; subtest 2 writes `6`, needs *both*
bits CLEAR to pass.

Cross-referencing `MEMORY_MAP.md`'s already-settled bit maps for
these two registers (found in an earlier, September session, not
re-derived today): `comm_stat` bit `0x4` is `TBRE` (UART transmit-
buffer-empty, per Table 7-36 of the Options manual), and `comm_param`
bit `0x80` is the UART's own live serial-data-output line (not a DIP
switch, per a 2026-09-16 schematic trace) - so this self-test really
is exercising real UART transmitter state, just via a 3rd register
(`0x406F3`) this project's UART model doesn't cover.

Traced why both subtests fail deterministically in the live emulator
rather than guessing: `io_stubs.InteractiveUartMock` only models the
standard 8251 data/control pair at `0x406F0`/`0x406F1` - nothing
updates the i8251 core's `command` register (which gates `txrdy_r()`,
mirrored onto `comm_stat` bit `0x4`) from a write to `0x406F3`, so
that bit reads permanently `0`, failing subtest 1's SET requirement
every time. `comm_param` bit `0x80` is a plain `COMM_OPTION_STUBS`
fixed baseline (`0xF8`, bit `0x80` = `1`) with no dynamic coupling to
anything at all, so it reads permanently `1`, failing subtest 2's
CLEAR requirement every time too. Neither failure depends on RAM
garbage or instruction-count timing - both are structural, given the
current stub set.

**Deliberately left unstubbed**, matching this project's standing
"don't guess real hardware content" practice: `MEMORY_MAP.md` already
flags `0x406F1`-`0x406F3` as plausibly TMS9914A (GPIB chip) register
space rather than confirmed UART registers (the `init_readout_port_
config`/`write_readout_port_byte` puzzle - the manual's TMS9914A has
"eight internal registers," an exact count match for this 8-register
bank). There's no independently-confirmed real semantics for
`0x406F3` to derive a stub from; building one would mean fabricating
how it's really supposed to couple into `comm_stat`/`comm_param`,
which this project has no source for yet.

Updated `FUNCTIONS.md`'s `selftest_comm_loopback_b` entry, added a new
"Comm-board loopback flag check" section to `STILL_PENDING_DECODE.md`,
and extended the same running `TODO.md` item. **This really is the
last diagnostic line reached by a full boot trace** - every one is now
traced to a known cause: 4 are genuine stub candidates deliberately
left unstubbed pending real hardware content (`MM_ACQ`, `FP_a2d`'s
`"gnd"`, `CDT`'s `"uncaled"`, `COMM_LB`), and 2 are genuine ROM-content

## Jumper hunt follow-up: `P9104` IS a real jumper after all, `P9105` is actually two jumpers, `P9107` now has a traced (partial) destination

Picked up the hardware-jumper-hunt `TODO.md` item's own stated next
step from an earlier session: re-read service-manual page 65 (Diagram
14, "Microprocessor and Store Panel Controls," board A10) for what the
`P9107` ON/OFF and `P9105` TEST/NORM labels actually connect to,
since the first survey pass had only confirmed the jumpers' existence
and printed labels, not their circuitry. Rotated the raw page image
for legible orientation (`im.rotate(-90, expand=True)` via PIL) and
read 3 cropped, 2x-upscaled close-ups of the relevant clusters.

**Found a standing documentation error and corrected it**: the prior
survey's conclusion that "`P9104` is NOT a jumper - it's the clock/
oscillator IC itself" was wrong. The close-up crop around `U9104`'s
own `RES` pin 11 and its `R9107`/`C9107` RC reset-timing network shows
a real 2-position jumper explicitly printed **`P9104`**, labeled
`RESET`/`NORM` - matching `docs/theory-of-operation.md` line 597's
already-OCR'd text ("Manually moving jumper P9104 to the RESET
position forces a reset of the Microprocessor and the Display
Controller") essentially word for word. That primary-source text had
been sitting in the repo, correct, the whole time; the schematic
survey's first pass just missed the small label in a visually dense
cluster and wrongly concluded the designator didn't exist at all,
rather than flagging it as unconfirmed. `U9104` (the clock IC) and
`P9104` (this jumper) are two different parts that happen to sit next
to each other and share adjacent numbers - not a "P9104 is really
P9105/P9107" aliasing as previously speculated.

**Found a second standing error**: what the first pass logged as one
jumper, "`P9105`" (TEST/NORM), is actually **two separate connectors**
on the same page:
- `P9105A` - a 3-pin header printed "**REMOVE FOR TEST**", feeding
  `NMI` through pull-up `R9113H`, with its own note that the earliest
  board revision has pins 1 and 3 swapped (this note belongs to
  `P9105A`, not to a generic `P9105` as previously filed).
- `P9105C` - the actual TEST/NORM-labeled jumper, feeding the `EN`
  pin of decoder `U9106` (74LS139), whose outputs are `BLK0`-`BLK3`
  and `RAM SEG`/`TO SEG`/`COM SEG` - CRT/storage segment-timing
  signals, giving this jumper a concrete destination for the first
  time (previously "very plausibly a diagnostic strap," now narrowed
  to "a display-segment-decoder enable strap," though which specific
  outputs change between TEST and NORM is still untraced).

**`P9107` partially traced**: its wiper feeds one input of OR gate
`U9102C`, ORed with `U9104`'s own `RESET` output, combined output
going to "RESET TO U9208-9" (`U9208` already independently identified

## RS-232 PARAMETERS DIP switch - full switch-to-setting bit map resolved

Went back to `STILL_PENDING_DECODE.md`'s long-standing open item on the
comm ROM's RS-232 DIP switch decode: the physical register layout
(switches 1-7 in the Parameter Buffer, 8-10 in the State Buffer) and
bit polarity (active-LOW) were already confirmed in prior sessions,
but which *specific* switch controlled which *specific* decoded
setting - beyond the already-known baud-rate nibble - was not.

Read `read_dip_switches_serial_config` (`0x966E7`-`0x96780`,
`disasm/sysrom_3532_3633.lst`) instruction-by-instruction rather than
guessing from a generic calling-convention assumption. The function is
short and falls into four clean pieces:

1. `les di,[0x6de]; mov dl,es:[di]; not dl` - loads and inverts the
   Parameter Buffer byte (switches 1-7), then `and dx,0xf` for the
   baud nibble (switches 1-4) into `[0x4ec]`, with one explicit special
   case: `cmp dx,0xf` / `mov bl,0x1f` remaps the all-four-ON pattern to
   sentinel `0x1F` rather than storing the literal value `0xF`.
2. `and dl,0x10` (switch 5, bit4) gates the next block: if clear,
   `[0x4ed]=0` outright; if set, `and dx,0x60; sar dx,1` (x5); `inc dx`
   extracts switches 6-7 as a 2-bit field and adds 1, storing `1-4`
   into `[0x4ed]`.
3. `les di,[0x6da]; mov dl,es:[di]; and dx,8` (switch 8, bit3 of the
   *State* Buffer, **read raw, no `not`**) branches to store `1` or `0`
   into `[0x4ef]` - functionally still the inverted sense (switch
   ON -> `1`), just implemented via compare-and-branch instead of a
   `not` instruction. (First pass at tracing this branch got the
   `jne`/fall-through backwards and briefly looked like a genuine
   raw-vs-inverted polarity anomaly versus the rest of the function;
   re-reading the branch targets carefully showed it isn't - the net
   polarity is the same as everywhere else, just coded differently.)
4. `mov bl,es:[di]; not bx; sar bx,1` (x4); `and bx,3` extracts bits
   4-5 of the (now inverted) State Buffer byte into `[0x461]`.

Cross-referenced every piece against `docs/options.md`'s OCR'd Tables
7-7 ("RS-232-C PARAMETERS Switch", switch-section-to-function map),
7-8 ("Baud Rate", confirms the all-ON->"Off Line" special case is a
real, manual-documented switch combination, not firmware-internal
trivia), and 7-9 ("Parity Selection", ODD/EVEN/MARK/SPACE per
switch-6/7 combination), plus the Table 7-36 State Buffer bit map
already on record in `MEMORY_MAP.md` (which already established
switches 9/10 are bit-swapped: bit4=switch10, bit5=switch9). Every
formula checks out cleanly against the manual with no leftover
contradiction:

- Switches 1-4 -> `[0x4ec]` baud index (Table 7-8), sentinel `0x1F`
  for "Off Line".
- Switch 5 -> parity enable/disable, gating `[0x4ed]`.
- Switches 6-7 -> parity type when switch 5 is ON: `[0x4ed] =
  (switch7<<1 | switch6) + 1` gives `1`=ODD, `2`=MARK, `3`=EVEN,
  `4`=SPACE - note this is genuinely a *different* internal order than
  Table 7-9's own ODD/EVEN/MARK/SPACE listing, because switch 7 (not
  switch 6, despite the table's column header "Switch Position (6 7)"
  listing switch 6 first) turns out to be the higher-weight bit of the
  firmware's 2-bit code. This isn't a contradiction once worked through
  per-combination - both tables agree on what every individual
  switch-6/7 combination means, they just assign a different 1-4
  *number* to each combination.
- Switch 8 -> `[0x4ef]` CR vs CR-LF line terminator.
- Switches 9-10 -> `[0x461]` printer/plotter device select (HP-GL /
  ThinkJet / Epson EPS7-EPS8), with the switch-9/10 bit swap now fully
  explained rather than just observed.

Updated `STILL_PENDING_DECODE.md` (closed the open item),
`MEMORY_MAP.md`'s "RS-232 option board" section (full per-switch
formulas, this is the canonical writeup), `FUNCTIONS.md`'s
`read_dip_switches_serial_config` entry, and `TODO.md`'s
runtime-menu-vs-DIP-switch bullet (narrowed to a pure precedence
question now that the mapping itself is resolved).

**Deliberately left open** (at the time): the exact physical/DS-segment
address of `[0x4ec]`/`[0x4ed]`/`[0x4ef]`/`[0x461]` (comm-ROM
flat-variable offsets) - whether they collide with the main ROM's own
unrelated `[0x4EC]`-named front-panel cluster in `VARIABLES.md`
depends on which data segment this function runs under.

## DIP-switch-vs-runtime-menu precedence for RS-232 parameters, mostly resolved

Picked up `TODO.md`'s remaining RS-232 open item: whether the `COMM`
menu's `STOP BITS`/`FLOW` (and by extension baud/parity/terminator/
printer-plotter) can override the rear-panel PARAMETERS DIP switch,
and if so which one wins.

First check: does `STOP BITS`/`FLOW` even have a DIP switch
counterpart? No. `docs/options.md`'s own `COMM` menu tree lists `DATA`,
`STOP BITS` (Option 12 only), and `FLOW` (Option 12 only) as
independent top-level submenu items, and nothing in the PARAMETERS
switch tables (7-7/7-8/7-9) or State Buffer bit map (Table 7-36)
decodes either one. So half of this TODO item's premise - an apparent
conflict - doesn't actually exist for these two settings.

For the settings the switch really does decode (baud, parity,
terminator, printer/plotter - today's earlier full bit-mapping work),
grepped every reference to `[0x4EC]`/`[0x4ED]`/`[0x4EF]`/`[0x461]` in
both ROMs (10 hits total). All of them are either
`read_dip_switches_serial_config` itself writing them, or firmware
code *reading* them live at the point of use:

- `poll_dip_switch_change` applies `[0x4EC]`/`[0x4ED]` immediately via
  `reinit_comm_channel` right after the switch-decode call returns.
- `enqueue_comm_char` (`0x974E1`) checks `[0x4ED]` per character
  enqueued, to mask bit 7 for 7-bit framing or set it for space
  parity.
- `send_serial_newline` (`0x96CB5`) checks `[0x4EF]` per line, to
  choose a bare CR vs. CR+LF.
- A printer/plotter-format dispatch block (`0x96815`-`0x96857`) checks
  `[0x461]` per invocation to pick the output format case.
- One more hit (`0xED9D9`, main ROM) turned out to be the already-
  documented unrelated `[0x4EC]`-numbered front-panel-cluster byte
  (different ROM/DS segment, confirmed in `VARIABLES.md` as a
  coincidental offset collision, not the comm-ROM variable) - not
  relevant here.

No second writer to any of these four addresses was found anywhere -
i.e. no separate "menu override" write site exists in this firmware
for baud/parity/terminator. This matches the manual's own asymmetric
wording: `docs/options.md` line 492 describes baud/parity/terminator
as selected "using the RS-232-C PARAMETER switch" with no software

`EPS7`/`EPS8`/`HPGL`/`TJET` format-name strings noted as the likely
entry point for next time.

Also worth recording: since all four variables are read live at the
point of use rather than cached into a separate "effective settings"
copy, *if* a menu-override writer is ever found, no extra precedence
logic would be needed to explain how it wins - it would just overwrite

## Traced the GPIB PARAMETERS switch mapping, and resolved `[0x629]`'s origin as a side effect

Followed up on the GPIB caveat left in the previous entry by reading
`read_dip_switches_gpib_config` (`0x96781`-`0x967FF`) in full and
cross-referencing it against `docs/options.md`'s Table 7-6 ("GPIB
PARAMETERS Switch") and Table 7-5 (GPIB connector pinout, confirming
IFC is a GPIB-bus-specific signal).

Confirmed, with high confidence:
- Switches 1-5 -> 5-bit GPIB primary address -> `[0x4F0]`, direct
  binary weights, no reordering - a clean match to Table 7-6.
- Switches 9-10 -> printer/plotter select -> `[0x461]` - the exact
  same formula and destination variable as the RS-232 decode, matching
  Table 7-6's footnote (identical to RS-232's).

Traced but explicitly flagged as unconfirmed:
- Switches 6-8 (terminator/LON/TON) -> `[0x4F1]`. The bit *positions*
  match Table 7-6/Table 7-35 exactly, but switch 8 (TON) is tested
  from the **raw, non-inverted** State Buffer byte - unlike every
  other switch bit in either DIP-switch decode function, which are
  all tested from an explicitly-inverted copy. Rather than assume the
  RS-232 side's "inverted everywhere" convention transfers bit-for-bit
  to a different physical buffer read without that same inversion,
  flagged this specific bit's physical ON/OFF-to-table-position
  correspondence as not independently confirmed - this unit is
  RS-232-equipped, not GPIB-equipped, so there's no live hardware
  photo to check against (unlike RS-232's switches 9-10, which did
  have one).

While tracing `read_dip_switches_gpib_config`'s only caller,
`poll_dip_switch_change`, found it does something unexpected: it isn't
just "the RS-232 boot-time caller" as previously assumed - it's the
shared GPIB/RS-232 **option-board-type detector**. It reads the
GPIB-config State Buffer (`[0x6DA]`) once, toggles the Option
Interrupt Mask Latch's `3D` output (`[0x6E2]+3`, physical `0x406FB`),
reads the State Buffer again, and XORs the two reads to see which bits
changed. Cross-referencing Table 7-35 (GPIB Status Buffer) against
Table 7-36 (RS-232 Status Buffer) explains why: the `DIAG` bit driven
by that same latch output `3D` sits at **bit 6** for RS-232's buffer
but **bit 7** for GPIB's - so toggling `3D` and checking which bit
position actually moved cleanly distinguishes which option board is
physically installed. The function sets `[0x629]` to `0` (RS-232) or
`0xFF` (GPIB) based on this, with a third, not-yet-characterized
fallback when neither bit toggles.

This resolves `STILL_PENDING_DECODE.md`'s old "`[0x629]` (GPIB/RS-232
mode select) still isn't confirmed as switch-sourced" item outright:
it's now confirmed **not** switch-sourced at all - it's an
auto-detected board-type flag, set exactly once at boot (since
`poll_dip_switch_change` has only the one caller, `comm_rom_boot_init`,
itself only reached via the single non-reentrant boot path already
established). `[0x629]` turns out to be read pervasively throughout
the comm ROM (`enqueue_comm_char`, `send_serial_newline`,
`compute_response_format_flags`, `parse_next_gpib_command_byte`,
`poll_comm_status_tick`, and others) to pick the RS-232-vs-GPIB code
path at each of those sites - consistent with it being a simple,
boot-time-fixed hardware-identity flag rather than anything
switch-configurable.

Updated `MEMORY_MAP.md` (new "GPIB option board" section, under the
comm-ROM part of the memory map), `FUNCTIONS.md` (`read_dip_switches_
gpib_config` and `poll_dip_switch_change` entries), `VARIABLES.md`
(new `[0x4F0]`/`[0x4F1]` and `[0x629]` entries), and
`STILL_PENDING_DECODE.md` (resolved the `[0x629]` item).

## Found and named two unreachable GPIB LON/TON-test functions, then found and fixed a mislabeled `comm_call_main_rom`

While searching for every other reader of `[0x732]+0x95` (the flag
gating the GPIB LON/TON logic touched on above), found two small,
near-identical functions sitting right next to each other in the comm
ROM's own native listing, immediately before the function then known
as `comm_call_main_rom`: `test_gpib_lon_or_ton_active` (`0x8392B`) and

discoverable call site (direct `lcall` or literal pointer-table entry)
anywhere in either ROM. Renamed both via `gen_disasm_x86.FUNCTIONAL_

GPIB option board section and `FUNCTIONS.md`.
