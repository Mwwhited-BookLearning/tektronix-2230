## Found (the hard way) that the documented disasm-regen recipe was missing a required step for the comm ROM

While regenerating `.asm` output after the rename above, `git diff
--stat` showed `disasm/160-2998-14.asm` with a wildly disproportionate
diff (~26000 lines) versus the main ROMs' expected few-line diffs -
previously-decoded real instructions (`FUNC_2998_0233` and hundreds of
others) had turned into raw undecoded `db` byte dumps. Root cause:
`gen_source.py`'s bare CLI invocation (`python gen_source.py <nasm>`,
exactly what `TODO.md`'s own regen recipe said to run) defaults
`entry_points=None`, i.e. *proven-reachable entries only* - correct
for `160-3633`/`160-3532`, but the comm ROM's committed `.asm` has
always included ~20000 additional instructions reached only via `gen_
disasm_2998.py`'s heuristic push-bp prologue scan. `TODO.md`'s recipe
listed `gen_disasm_x86.py`, `gen_disasm_mainrom_heuristic.py`,
`gen_source.py`, `gen_source_readable.py` - it never mentioned the
comm-ROM-specific driver needed to preserve that heuristic layer.

Found the actual intended driver already exists and had simply gone
unused this session: `disasm/gen_source_2998.py`. It regenerates
*only* `160-2998-14.asm`, with entry points = `g.ENTRY_POINTS +
gen_disasm_2998.build_entry_points()[1]` (comm-ROM heuristic only).
Running it reproduced the committed file byte-for-byte (zero diff) -
confirming it's the right recipe and that the rename itself never
touched the comm ROM at all, as expected.

Along the way, tried a plausible-looking alternative first - borrowing
`validate_all.py`'s entry-point formula (`g.ENTRY_POINTS + comm-
heuristic + main-ROM-heuristic`, used there for a one-shot NASM round-
trip check across every chip at once) and feeding *that* into `gen_
source.py` instead. It also round-tripped byte-identical, but left a
~150-instruction cosmetic artifact: the diagnostic comment after `;`
on some jump/call lines showed a wrong operand value, because the
extra main-ROM heuristic entries alias into the same physical
addresses the comm-ROM walk visits, and the single `visited[phys]`
dict entry gets overwritten by whichever walk visits last - the real
emitted instruction (derived separately, from NASM's own label
resolution) stayed correct throughout; only the trailing human-readable
comment was affected. Confirmed via an address-keyed diff against the
previous committed file that every real instruction byte and address
matched exactly before and after. Not worth chasing further once the
real `gen_source_2998.py` driver was found - recorded here, and in
`TODO.md`'s corrected recipe, so nobody reaches for `validate_all.py`'s
formula for this purpose again.

## Closed out the "unknown data" deep-dive's last 6 unconfirmed leads - one new function found, five gaps explained

Picked up exactly where `TODO.md`'s own "next step if picked up" note
left this long-running thread: 6 `UNKNOWN_DATA.md` blocks that looked
like real code by eyeball (clean prologues, or references to already-
tracked RAM variables) but hadn't been rigorously confirmed the way
2 earlier blocks (findings 7 and 10, from the 2026-09-22 sessions)
already were - no caller/far-pointer search, no control-flow
convergence check. Traced all 6 the same way, one at a time. None
turned out to be false leads.

**`160-3633` `0xE77F8-0xE783C` (69B) is a brand-new standalone
function**, not previously represented anywhere in the symbol table.
Manually disassembling the full range (through its own `retf 4`
epilogue, ending exactly 1 byte before `udiv32`'s own entry at
`0xE783D`) found a complete function with its own `push bp; push bx;
push cx; mov bp,sp` prologue - structurally identical to the already-
named `sdiv32` (`0xE77AE`) except for exactly one difference: `sdiv32`
saves `dx XOR [bp+0xc]` (the XOR of both operands' sign bits) before
computing `abs()` of each operand and reapplying that saved sign at
the end; this new function instead saves plain `dx` (the dividend's
sign alone) - so the divisor's sign never affects the final result,
only its magnitude does. It also calls a different point inside
`udiv32` (`0xE7866`, `+0x29` into `udiv32`'s body - a secondary entry,
not `udiv32`'s own primary entry at `0xE783D` that `sdiv32` calls; not
reconciled further). Named `sdiv32_unsigned_divisor`.

Root-caused *why* neither existing discovery mechanism had ever found
it: no literal far-pointer bytes reference `0xE000:77F8` anywhere in
any of the 3 ROMs (checked directly - the caller is still genuinely
unresolved, the same "confirmed code, caller not found" category as
the `0xE956E` pair from finding 10), and the mainrom heuristic's
push-bp prologue scanner (`gen_disasm_mainrom_heuristic.py`'s
`PROLOGUE = b"\x55\x8b\xec"`) structurally cannot match it either -
that signature requires `mov bp,sp` *byte-adjacent* to `push bp`, and
this function has `push bx; push cx` in between. Wrote a one-off scan
for that exact "delayed prologue" shape across both main ROMs: only 3
instances exist project-wide - `ashr32` and `sdiv32` themselves (both
already known, both missed by the same scanner for the same reason)
and this one.

Adding the name to `gen_disasm_x86.FUNCTIONAL_NAMES` alone changed
nothing - confirmed by checking the regenerated symbol table found no
`E77F8` key at all. A `FUNCTIONAL_NAMES` entry only renames an address
the walker is *already* visiting; since neither the proven entry
points nor the heuristic scanner ever reaches `0xE77F8`, it also needed
a manual `(0xE77F, 0x0008, "sdiv32_unsigned_divisor")` tuple added to
`ENTRY_POINTS` to actually make it appear. Regenerated the full
pipeline (`gen_disasm_x86.py` -> `gen_disasm_mainrom_heuristic.py` ->
`gen_source.py` -> `gen_source_readable.py` -> `gen_source_2998.py`,
per `TODO.md`'s corrected recipe) and confirmed the resulting `git
diff --stat` touched only `160-3633`'s own files (`.asm`,
`_readable.asm`, both `.lst`/`.symbols.json` pairs, and its aligned
bin) - `160-3532` and the comm ROM were untouched, as expected for a
single-chip rename.

**The other 5 blocks are all gaps *inside* already-reached functions,
not new functions:**

- `160-3633` `0xE9180-0xE91EF` (112B) is the shared, no-own-frame tail
  of an existing switch/case dispatcher - falls through cleanly from 4

- `160-3633` `0xE9404-0xE9471` (110B) bridges an already-reached-but-

## Built the `ACQ_AB` coupling stub - emulator now passes this self-test, found 2 new ones behind it

Picked up right where the first `ACQ_AB` entry above left off (write
side deliberately left unstubbed, "guessing one would misrepresent
understanding"). Re-read `step_acq_ab_addr_walk`'s and
`update_menu_position`'s full disassembly by hand to pin down two
things that session's analysis hadn't nailed down: the exact position-
to-pattern formula (confirmed: `pattern = (0xFFE >> (0xB-p)) & 0xFFE`
for `p<0xB`, else `(0xFFE << (p-0xB)) & 0xFFE`), and - new this
session - that `p` is **0-indexed**, not 1-indexed: `update_menu_
position`'s case-1 init call sets the position byte to `-1`, and every
case-3 step call increments it *before* returning it, so the first
step call returns `0` (a trivial, always-passing `0`-vs-`0` comparison
against plain RAM's default), the second returns `1`, and so on. This
is why the captured failure sequence has only 11 entries starting from
`2` (position 1) rather than 12 starting from `0` (position 0) - a
detail worth recording since it's easy to misread as "the loop starts
at position 1," which the `update_menu_position(1, 0x15, 0)` call's
literal `1` argument encourages but is actually unrelated (that `1` is
the *selector/mode* argument, not a position).

First implementation of `io_stubs.AcqAbAddrWalkStub` copied
`CommPresenceProbe`'s shape exactly: hook `UC_HOOK_MEM_WRITE` on the
Acquisition Mode Register's address (`0x437BE`), keep a step counter,
increment it on every write, compute the pattern, write it into
`0x4377E`. A live boot trace immediately showed this was wrong - junk
like `ACQ_AB : read-back 7E <> 0` (the stub's "actual" output running
far ahead of, and uncorrelated with, the real "expected" value) instead
of the failures just disappearing. Root cause: **other, unrelated self-
tests earlier in the dispatcher's sibling list also write `0` to this
same physical register for their own purposes**, so a plain address-
keyed write hook fires several extra times before `selftest_acq_ab_
addr_walk` ever gets its own turn, desyncing the counter from the very
first real step. Fixed by hooking `UC_HOOK_CODE` on the *exact
instruction address* instead (`0xE300C`, the `mov byte ptr es:[di], 0`
inside `step_acq_ab_addr_walk` itself) - the same "hook the specific
instruction, not every access to an address that might mean several
different things" technique `io_stubs.DiagnosticTextCapture` already
documents and uses, for the same underlying reason.

Verified end-to-end with a scripted `debugger_core.Debugger` run
(`interactive.py`'s and `tui.py`'s shared engine - not `emu.py`, which
doesn't carry the richer self-test-coupling stubs): a full boot trace

## Traced `HS_ACQ`/`TBD hs/2` - both are the same acquisition-memory-address-buffer register as `ACQ_AB`, read instead of address-walked

Picked up the "not yet investigated" `HS_ACQ`/`TBD hs/2` failures left
behind by the `ACQ_AB` coupling-stub work above. Traced the call chain
(`run_adc_selftest`/`wait_stable_measurement`/`verify_pattern_with_
report`, reached via `configure_measurement_hw`) back to its one and
only configuration point, `init_selftest_register_group` (`0xE4443`),

Reading that function's full disassembly body
(`disasm/sysrom_3532_3633.lst:8413-8470`) decoded all 8 of
`configure_measurement_hw`'s far pointers to physical addresses, every
one of which was already independently confirmed in `MEMORY_MAP.md`'s

| far ptr | physical  | identity (Table 3-1)                  |

| `0x31E` | `0x48000` | Acquisition RAM U3418/U3419            |

ADC at all; it's re-reading the acquisition-memory address buffer with
a plain busy-flag+value read instead of `ACQ_AB`'s address-line walk.
This also explains the failure text literally for the first time:
`"acq_mem cntr"` = *acquisition-memory counter*, not "ADC counter."
`[0x31E]`'s buffer (`0x48000`) is confirmed genuine Acquisition RAM,
not a counter/PROM as first guessed mid-session - though nothing in
this call chain ever writes the incrementing-ramp pattern `verify_
pattern_with_report` later checks there, so what fills it (real
hardware during a capture cycle, or untraced firmware) is still open.

## Built the `HS_ACQ`/`TBD hs/2` coupling stub - resolved the `acq_mem cntr` mismatch for both

Continued directly from the above: re-derived `run_adc_selftest`'s
full parameter map byte-exact against `selftest_hs_acq`'s actual
pushed arguments (previously only partially mapped), by reading its
whole body end-to-end alongside the live push-order disassembly at
`0xE28FE`-`0xE2936` - correcting a discrepancy flagged mid-derivation
(a prior guess had `[bp+0x14]`/`[bp+0x16]` backwards, which would have
implied an implausible zero-fill count for `TBD hs/2`).

**Full map**: `bp+6`/`bp+8` = far-ptr report label; `bp+0xa` = zero-
fill start-offset component (`(buffer+0x1000)-[bp+0xa]`), also
forwarded to `configure_measurement_hw`; `bp+0xc` = zero-fill count
component (`[bp+0xc]+[bp+0xa]`), also forwarded to `configure_
measurement_hw`, *also* reused as one of the two final-comparison
thresholds; `bp+0xe`/`bp+0x10`/`bp+0x12` = forwarded straight through
to `configure_measurement_hw`'s remaining 3 register-write params, no
other local use; `bp+0x14` = busy-wait retry-count limit; `bp+0x16` =
the other final-comparison threshold; `bp+0x18` = failure-message flag
bits, only read on the busy-timeout-never-cleared path - `selftest_hs_
acq`'s call doesn't even supply it (9 pushes total, not 10), which is
harmless only because that path is never reached when the busy bit
already reads clear. Confirmed against the live capture: `bp+0xc=0xa2`
+ `bp+0x16=9` = `0xAB`, exactly matching `"HS_ACQ : acq_mem cntr 800 <>
0AB"`.

The key realization that made a general stub possible rather than a
per-self-test hack: `run_adc_selftest`'s comparison code is the *same*
code for every caller, so a stub that reads `[bp+0xc]`/`[bp+0x16]`
live off the stack at the exact read instruction (`0xE137A`) resolves
`TBD hs/2` too, without ever decoding `run_indexed_adc_selftest`'s own
`[0x1DCC]` device table. Added `io_stubs.AdcSelftestReadbackStub`
(hooked `UC_HOOK_CODE` at that one instruction, same "hook the
instruction, not the address" reasoning `AcqAbAddrWalkStub` already
established, since a plain address hook on `0x4377E` would also catch
the busy-wait loop's own earlier reads and `verify_adc_calibration`'s
unrelated `ACQ_AB` read of the same physical register) and wired it
into `debugger_core.py`'s `_setup_stubs` alongside `AcqAbAddrWalkStub`.

**Verified live**: a full boot trace (`Debugger.run(60_000_000)`) no
longer prints either `"acq_mem cntr"` mismatch line; the `"fill @"`
ramp-pattern mismatch (the separate, still-open `[0x31E]`/`0x48000`
question) persists unchanged for both, and the run now continues one
self-test further into a third, previously-unreached, still-unnamed
`"TBD ps/2"` failure with the same `"fill @"` shape. Ran an A/B
comparison (same trace with the stub reverted via `git stash`) to
confirm the run's eventual `halt_cpu` panic stop at physical `0xF1611`
happens identically either way (5513062 vs. 5519061 instructions -
the tiny difference being only the new hook's own overhead) - a
pre-existing stopping point unrelated to this change, not a regression
introduced by it.
