# 2026-09-23

## Replaced the Textual TUI with a Tkinter dashboard that also renders the captured vector-display buffer

Following up on an earlier request ("can you replace the TUI with some
other GUI such as a webform or winform that can have a canvas that can
display the vector buffer?") and the explicit instruction "convert to
tkinter" (Pygame was considered and rejected - no built-in widget
toolkit for the registers/log/front-panel controls; Tkinter ships in
the standard library and its `Canvas` widget natively supports vector
drawing via `create_line`). Rewrote `emulator/tui.py` from scratch on
Tkinter/`ttk`, keeping the same filename and `Tek2230App` class name.
Preserves every feature of the Textual original - registers panel,
incoming/outgoing/log scrollback, front-panel checkboxes plus the
3-way horizontal-mode dropdown, DIP-switch checkboxes, a command input
bar with history, F1-F7/Ctrl+Q key bindings, busy/live-mode guarding,
and the reset button - and adds a new `Canvas` rendering captured
oscilloscope plot segments.

Tkinter has no `call_from_thread` equivalent, so worker threads that
run long emulator commands only ever enqueue zero-arg callables via
`self._post(fn)`; `self.root.after(50, self._drain_ui_queue)` polls
and drains that queue on the main thread, the only place any widget
method gets touched as a result of background-thread work.

The vector-display capture backend (`io_stubs.VectorDisplay`, hooking
`plot_line_to`'s raw entry point at physical `0xE7E0D` before its own
`push bp` prologue runs, reading the previous pen position from
`[0x6b2]`/`[0x6b4]` and the new target directly off the stack) turned
out to already exist as prior, uncommitted work by the time this
session started - it was wired into `Debugger` (`vector`/`vector
clear` REPL command) but not yet surfaced in any GUI. Added a `total`
monotonic counter to `VectorDisplay` (increments per captured segment,
resets on `clear()`) so `tui.py`'s `_redraw_vector` can draw only
newly-arrived segments incrementally instead of redrawing up to 4000
lines every UI-queue tick, falling back to a full redraw only when the
buffer is cleared or more segments arrived since the last redraw than
the bounded deque (`maxlen=4000`) could hold.

Verified via the project's own `.venv`: full app construction plus
command dispatch, front-panel/DIP/mode-dropdown toggles cross-checked
against `Debugger` state, command history, reset, clean shutdown, a
3,000,000-instruction `run` completing cleanly (0 vector segments
captured - a firmware-reachability fact, a cold boot doesn't drive the
plotter that deep, not a capture bug), and a synthetic-segment
injection test confirming the draw/clear pipeline end to end.

`requirements.txt` no longer lists `textual`; `tui.bat`'s and
`interactive.py`'s docstrings were updated to match. Full writeup in
`emulator/docs/design.md`'s new "Tkinter vector-display GUI, converted
from Textual" section.

## Follow-up: made the vector canvas resize-but-stay-square

User feedback: the vector display should be square. The coordinate
math was already uniform between X and Y (`VectorDisplay`'s raw
coordinates are both ~0-1023, 10-bit, one scale factor applied to
both), but the canvas itself was a fixed 520x520 `tk.Canvas` sitting
in a resizable `PanedWindow` pane - square at startup, but it neither
tracked the pane on window resize nor used any extra space offered to
it. Packed the canvas into a holder frame that fills its pane and
bound the holder's `<Configure>` event to pick the largest square that
fits (`min(event.width, event.height)`, minus a small pad), resize the
canvas widget to it, and force a full redraw at the new per-instance
scale (`self._vector_size`/`self._vector_scale` now drive the draw
call site, replacing the old fixed module-level constants there;
those constants remain only as the startup default). Verified with a
synthetic resize-event call confirming the canvas shrinks to a
centered square and redraws existing segments correctly at the new
scale.
