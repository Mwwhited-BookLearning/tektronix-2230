# 2026-09-13

A day dominated by one huge development: the user provided the actual
Tektronix 2230 operator's and service manuals, resolving a large batch
of hardware-identity questions that had been open for many sessions.

## Hardware finding: no 8087 coprocessor on the main board

Direct user observation, before the manuals arrived: visually inspected
the main digital/acquisition board (A10) and found no 8087 chip
present. Since `convert_sample_value`'s `fmul` only runs as part of
`assert_and_halt`'s panic-argument computation (a path meant to almost
never trigger), this fits the broader pattern already established of
real call paths that never actually execute on shipped hardware - the
instruction is real but essentially never reached in practice, not
evidence of a coprocessor. Documented in `HARDWARE.md`/`disasm/NOTES.md`.
Not fully closed - other boards in the unit haven't been checked.

## The manuals arrive: operator's manual (070-4998-02) and service manual (2230)

Tracked via git-lfs given their size (~8.7MB and ~23MB). Extracted text
via `pdftotext -layout` and mined the service manual's Theory of
Operation Section 3 (Table 3-1, "Memory Space Allocation") and
Maintenance Section 6 (Tables 6-16 through 6-23) for the complete
memory-mapped I/O address map. This resolved or substantially advanced
most of the open hardware-identity items that had accumulated over many
sessions:

- **`0x41000`/`0x42000`**: confirmed "Display chip interrupt reset"/
  "Display chip next frame", not per-channel front-end status as
  guessed for many sessions. Renamed `read_channel1_status`/`clear_
  channel1_status` and the channel2 counterparts to `read_display_
  chip_int_reset`/`clear_display_chip_int_reset` and `read_display_
  chip_frame_trigger`/`clear_display_chip_frame_trigger` (verified
  byte-identical after regenerating, diff counts unchanged).
- **`0x403FFA`/`0x403FFB`**: confirmed "Front Panel Buffer U9301"/
  "U9302" - matches the long-standing "front-panel key/encoder status"
  guess for `scheduler_tick_service`'s `[0x758]`/`[0x759]` exactly.
- **`0x48000-0x4BFFF`**: confirmed genuine Acquisition Memory (4 images
  of RAM U3418/U3419), not a readout attribute plane as guessed - the
  real attribute/LSB plane is a different address, `0x08000-0x0FFFF`.
- **`0x4007DE`**: confirmed "Time Base Mode Register U4119" - the exact
  address `detect_comm_option_hw`'s write-probe pokes for `[0x1B83]`.
- **`0x4067C`/`0x406BC`/`0x406F8`**: confirmed "Option Status Latch
  (in)"/"Option Parameters Latch (in)"/"Option Interrupt Mask Latch
  (out)" - resolves `selftest_comm_readback`'s old "surprising and
  unreconciled" address note from an earlier session; `COMM_RB` really
  does mean the GPIB/RS-232 option board after all.
- **GPIB controller confirmed as a TMS9914A**, resolving the old
  TMS9914A-vs-µPD7210 open question.
- **Two separate ADCs confirmed**: `U2204` (signal acquisition, matches
  the existing Sony CX20052A spec exactly - 8-bit, 20MHz, ECL) and
  `U6105` (front-panel controls, separate and much slower).
- **New genuine puzzle found**: `write_readout_port_byte` writes
  unconditionally to `0x40000+0x6F0`, but the manual labels that exact
  address range as comm-option-only UART/GPIB registers. Not
  reconciled - flagged honestly in `MEMORY_MAP.md`/`TODO.md`.
- Checked the AUX-connector pen-lift relay as a candidate for `write_
  hw_shift_register`'s target - doesn't cleanly fit (Pen-Down is a
  single digital line, not a multi-bit shift-register write); still
  open, X/Y plot-output DACs are a better structural fit but not
  confirmed.

Updated `MEMORY_MAP.md` (substantial "Confirmed regions" rewrite),

## Manual markdown + figure-extraction pipeline

Built `hardware/gen_manual_markdown.py` (using `pymupdf`, installed via
pip since poppler's `pdfimages`/`pdfinfo` aren't available in this
environment, only `pdftotext`) to transcribe both manuals to markdown:
OCR text for typeset pages, rendered page images (150 DPI JPEG) for
pages with under 500 characters of OCR text (a heuristic for "probably
a figure/schematic/photo page" - not perfect, but validated by
spot-checking several output pages, including a schematic parts-
location table that stayed fully legible at this resolution). Produced
`hardware/manuals/2230_service/` (451 pages, 94 rendered as images,
~23MB) and `hardware/manuals/2230_operators/` (188 pages, 20 images,
~2.4MB).

**Restructured for readability** after user feedback that the first
pass (flat per-page OCR dumps) wasn't well-structured: rewrote the
script to use the PDF's own per-line font-size data (from the OCR
layer) to detect real section headings, and to join lines into
flowing paragraphs by the PDF's text-block structure instead of one
markdown line per original PDF line break. Real section headers (e.g.
"MENU SELECTED FUNCTIONS", "STORAGE CONTROLS") now render as proper
`##`/`###` headings matching the manual's own structure. Tables still
read as plain paragraphs (OCR column alignment isn't reliable enough
to reconstruct as markdown tables) - documented as a known limitation.

## Read the operator's manual for menu/UI-flow context

Found the exact physical control scheme behind `update_menu_position`
in the operator's manual's "MENU SELECTED FUNCTIONS" section: the
`WAVEFORM REFERENCE/MENU SELECT` switch (held in `MENU SELECT`
position) gates the 3 `MEMORY` switches into menu-navigation mode;
`SAVE REF/►` enters the next (deeper) menu level; the repurposed
`MEMORY` switches move up/down within the current level or back to the
previous level. Cross-referenced against the service manual's `SWB2`
signal names (`MENU ADV`, `MEM 1`/`2`/`3`) - a strong new lead for
pinning down `[0x4E7]`/`[0x4E8]`'s exact bit positions, not yet
individually confirmed against the disassembly. Documented in
`HARDWARE.md`'s new "Menu navigation control scheme" section. The full
top-level menu tree itself was already documented from hardware photos
in an earlier session and didn't need re-deriving.

## Continued ROM decoding: comm ROM far-pointer table, stroke-font negative result, small confirmations

Decoded `init_far_pointer_table`'s (`0x80133`, comm ROM) own embedded
31-entry table, following up on the "practical takeaway" note from
the sysrom far-pointer table discovery. Unlike that one, this table
didn't yield new functions - most targets in the `0x90000` comm-ROM-
alias range decode as garbage, and the rest land mid-instruction
inside already-covered code. Still worthwhile: 3 entries write far
pointers to `0x406F0`/`0x4067C`/`0x406BC`, the exact addresses
confirmed from the service manual - independent confirmation from the
comm ROM's own init code. Also found a striking, unexplained
coincidence: one entry's target (physical `0xF25E5`) is the exact same
byte the sysrom table's own entry #54 points to.

Re-checked the strict proven-only landing-artifact/gap analysis -
confirmed fully exhausted (only the 3 already-documented instances
exist in the proven call graph; the project's other ~46 candidates are
all heuristic-layer-only, lower priority). The largest remaining
proven-listing address gaps were checked and are normal, expected
heuristic-only territory, not hidden data blobs.

Attempted to decode and render the `0xEA5E6`-`0xEB131` stroke-font
candidate (flagged 2026-09-12): traced `draw_readout_char`'s exact
bit-packing formula precisely, then rendered the region as a grid of
glyphs. Result: 405 tiny fragments, all generic repetitive shapes, no
letterforms - a genuine negative result. `0x00` appears far too often
in this region to be a per-character terminator. Downgraded from "real
lead" to "ruled out" - the stroke-font table's true location remains
unknown.

Confirmed the 2 `push`-with-stray-`0x67`-prefix mismatches
`validate_2998.py` flags land inside an already-catalogued printable-
text region (`strings_160-2998.json` offset `0x400a`) - decode drift
into data, not a validator bug, as suspected. Closed out.

## More ROM decoding: the [0x4E0]-[0x4FC] cluster, and a real doubt cast on write_readout_port_byte

Traced `update_menu_position`'s `[0x4E7]`/`[0x4E8]` bit tests looking
for a clean cross-reference to the service manual's `SWB1`/`SWB2`
names - found instead a heuristic-only function (`FUNC_3633_92D1`, no
confirmed caller) that initializes a whole cluster of ~11 neighboring
bytes together, with different defaults depending on the existing
`[0x1B83]==0x14` comm-detection branch - confirms the cluster is real,
doesn't resolve the physical mapping.

Bigger finding: viewed the service manual's Table 3-1 page image
directly (not just OCR text) while investigating the `write_readout_
port_byte` puzzle, and found specific new evidence that this whole
self-test-banner-printing cluster (`write_readout_port_byte`/`init_
readout_port_config`/`print_char`/`print_string_far`) might actually
be writing to the comm-option's UART/GPIB chip directly, not CRT
readout hardware as currently named - `init_readout_port_config`
writes 3 bytes to exactly 3 of the comm option's documented 8-register
bank, and the manual separately confirms the GPIB controller has
exactly 8 internal registers. Not confident enough to rename (`print_
string_far`'s per-character pacing via `wait_readout_tick` doesn't
discriminate between a UART story and a CRT story) - documented both
sides honestly as a genuinely open question.
