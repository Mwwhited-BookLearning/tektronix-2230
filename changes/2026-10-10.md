## Landing-artifact thread: traced the 5-caller candidate (`0xECE82`)

Continued down `find_landing_artifacts.py`'s caller-count ranking after
the `>=6`-caller tier closed out the prior day. `0xECE82` sits inside
`FUNC_3633_CE5B` (real entry `0xECE5B`), 1 byte into a local `je
L_ECE9C` - read fresh, it decodes as `sbb word ptr [bp+si+2], di` and
lands exactly on the address the real "branch not taken" path reaches,
so an external call to it never evaluates the branch at all (clean,
unconditional reconvergence, the `write_hw_shift_register`/`0xF4CE8`
shape, not `0xE951A`'s weaker branch-dependent one).

All 5 real `lcall SUB_ECE82` sites (`0xF3C1E`, `0xF4D44`, `0xF54C9`,
`0xF5581`, `0xF562E`) push 2 far pointers (8 bytes) and clean only 4 of
them via `add sp,4` - on its face the same shape as `0xE951A`'s
mismatch. It isn't: `SUB_ECE82` skips `FUNC_3633_CE5B`'s own prologue
entirely (never sets its own `bp`), and the function's shared exit
(`mov sp,bp` / `pop bp` / `retf`) resyncs the stack against the
*inherited* `bp` from whatever enclosing function is actually live -
the same mechanism already established for `0x88729` and `SUB_F5F56`.
That means the simple push-vs-retf-immediate arithmetic that cleanly
confirmed `write_hw_shift_register`/`0xF4CE8` and cleanly ruled out
`0xE951A` doesn't mechanically apply here - the real `SP` delta is a
runtime quantity (depends on the live `bp`), not something static
reading alone can finish. Also confirmed `FUNC_3633_CE5B`'s true entry
point has zero real callers anywhere in the corpus, same "only ever
reached past its own prologue" pattern as `extract_strided_channel_
samples`/`SUB_F5F56`.

Net: a third clean instance of the shared-frame secondary-entry
mechanism, not a second `0xE951A`-style negative. Flagged the general
lesson (check for `mov sp,bp` in the shared exit before trusting the
push-vs-retf stack check) for whoever continues down the remaining
candidates (`0xEDDE2` at 4 callers, `0xEFD99` at 3, mostly
single-caller after that).

Updated `docs/decode-anomalies/landing-artifacts-and-jump-tables.md`
("Follow-up, 2026-10-10"), `TODO.md`, and `STILL_PENDING_DECODE.md` to
match.

## Explained `SUB_ECEDA`'s `hlt` opening - not a new function, just a mislabeled internal shared-tail entry that external callers reach 4 bytes early

Followed up on the `SUB_ECEDA` anomaly flagged (but deliberately not
written up) earlier this session: its heuristic-listing label at
`0xECEDA` decodes as `hlt` followed by a `jmp`, odd for something with
14-17 external callers. Reading the function in full context resolved
it: `0xECEDA` isn't a separate function at all. It sits inside the
already-documented `step_item_subvalue_back_guarded`/`step_item_
subvalue_back` (`0xECE5B`/`0xECE82`), whose own body has a genuine
internal `jle L_ECEDE` branch (`0xECE66`, the "nothing to step" case)
landing exactly 4 bytes *after* `0xECEDA`, at `0xECEDE` - which falls
through to the real shared dispatch tail (read `[0x464]`, index
`[0x1D10]`, check `+6`/`+8`, push command code `3`, `lcall es:[bx+di
+6]`, exit). That's the same "push 3 when there's nothing to step"
behavior `changes/2026-10-10.md`'s earlier `0xECE82` section already
documents - not an undocumented 4th sibling as briefly suspected.

The 14-17 external `lcall` sites (checked 2 sample sites - one
same-chip at `0xEB879`, one cross-chip from `160-3532` at `0xF33E8` -
both decode as clean, coherent calling-convention code: push a far-
pointer buffer argument plus a byte value, clean the stack, consume an
`ES:BX` return afterward) are real, deliberate code, not scanner
noise. All of them target `0xECEDA` itself - 4 bytes *before* the real
dispatch entry at `0xECEDE` - where the ROM byte is `hlt` immediately
followed by an unconditional `jmp` straight to the function's exit,
skipping the dispatch body (which is therefore dead code when reached
this way). Per 8086 `HLT` semantics, a real call here would freeze the
CPU until the next unmasked interrupt, then return immediately without
touching `[0x1D10]` or using the pushed arguments.

Left unresolved, flagged as competing hypotheses only: this could be a
deliberate "block until next timer tick" idiom, or this specific call
path could have been patched out/disabled in this ROM revision while
the internal fallthrough keeps working. No rename (not a distinct
function to name). Updated `docs/decode-anomalies/landing-artifacts-
and-jump-tables.md` (new "Follow-up, 2026-10-10" section with the full
byte-level trace), `STILL_PENDING_DECODE.md`, and `TODO.md`.

## Resolved the 2 remaining ranked landing-artifact candidates (`0xEDDE2`, `0xEFD99`); named `format_word_decimal_and_copy_out`; surfaced a new unresolved cross-function case (`SUB_EFDC2`)

Picked up `TODO.md`'s explicitly-deferred tail of the landing-artifact
caller-count ranking: `0xEDDE2` (4 callers) and `0xEFD99` (3/1
callers, per `symbols.json`'s own `ref_count`).

**`0xEDDE2`**: confirmed via direct byte decode to land 2 bytes into
the real 3-byte `cmp ax, 0` (`3d0000`) at `0xEDDE0`, inside a real,
cleanly-prologued function at `0xEDD89` that digit-extracts an
unsigned word into a 9-byte stack buffer (space-padded, written
backward from the end) then copies the result forward to a far
destination and returns the char count via `retf 2`. Named it
`format_word_decimal_and_copy_out`. The artifact decodes exactly one
harmless bogus instruction (`add byte ptr [bx-0x27], dh`) before
landing exactly on the real function's own unconditional
`jmp L_EDE01` - since that jump is unconditional only because the
artifact's decode swallowed the bytes of the real conditional `ja` it
would normally replace, every one of the 4 external callers always
skips digit extraction and falls straight into copy-out, meaning they
always get back whatever was already sitting in that stack slot from
the function's *previous* use, not a freshly-formatted value.

Left open: why the function's own space-padding fill is never actually
copied by its own output path (the copy loop starts at the digit-
extraction's final cursor, not the padding region) - unexplained by
anything found so far. Also open: the 4 callers' own stack-parameter
convention is inconsistent across call sites (one pushes 3 words,
another path through a separately-labeled shared entry `0x3532:5C6A`
appears to push a 4th) in a way that doesn't cleanly reconcile with
the uniform `add sp,4` cleanup at every site - flagged rather than
guessed at.

**`0xEFD99`**: confirmed via manual raw-byte decode of
`binary/160-3633-14.bin`'s physical range `0xEFD96`-`0xEFDB0` to land
1 byte into the tail of the real 4-byte `les di, ptr [0x1ddc]` at
`0xEFD96`, inside an unnamed per-channel acquisition-sample-processing
function (`FUNC_3633_FC94`, `0xEFC94`). It decodes 2 bogus
instructions before reconverging with a second, inline-duplicated
"half" of a pattern the function runs twice per iteration (at offset
`+0x80` then `+0x82` into a `[0x1ddc]`-based far pointer), mirroring
the first half's own call sequence without an explicit jump between
the two. `FUNC_3633_FC94` itself stays unnamed - its mechanism (a
table offset via `imul dx,0x14` + base `0xa6`, a call to
`read_acq_sample_with_wrap`, then two calls to an unnamed
`FUNC_3532_B529`) is understood well enough to describe but not to
name confidently; what `FUNC_3532_B529` does and what the `0xa6`-based
table represents are open.

**New case found along the way, left unresolved**: `SUB_EFDC2` (3
external callers, all from a *different* function, `FUNC_3633_9611`
at `0xE9611`) sits at a clean, non-overlapping instruction boundary -
not a byte-overlap artifact, matching the already-established "clean
shared-frame secondary entry point" class (`0xF4CE8`). But its 3
callers are a genuinely separate function reaching into
`FUNC_3633_FC94`'s code without re-establishing a compatible frame:
`SUB_EFDC2`'s first instruction (`mov di, word ptr [bp-0xe]`, no
prologue) reads whatever `[bp-0xe]` means in the *caller's* frame
(`FUNC_3633_9611`'s own local, not a freshly-pushed parameter). This
doesn't fit either established category cleanly (dead/incoherent
artifact, or same-function zero-argument secondary entry) and is
flagged as a distinct, not-yet-understood third case.
`FUNC_3633_9611` turned out to be a multi-way dispatcher with its own
unexplored sub-labels (`SUB_E962C`, which follows a call to
`SUB_EFDC2` with `out 0xd1`/`out 0xd1`/`out 0x8a` writes reminiscent of
`write_hw_shift_register`'s shift-register pattern, and `SUB_EFFEE`,
reading a `[0x1d1c]`-table-indexed byte via `imul dx,6`) - good next
candidates, not chased this round.
