# 2026-10-10

## Landing-artifact thread: traced the 5-caller candidate (`0xECE82`)

Continued down `find_landing_artifacts.py`'s caller-count ranking after
the `>=6`-caller tier closed out the prior day. `0xECE82` sits inside
`FUNC_3633_CE5B` (real entry `0xECE5B`), 1 byte into a local `je
L_ECE9C` - read fresh, it decodes as `sbb word ptr [bp+si+2], di` and
lands exactly on the address the real "branch not taken" path reaches,
so an external call to it never evaluates the branch at all (clean,
unconditional reconvergence, the `write_hw_shift_register`/`0xF4CE8`
shape, not `0xE951A`'s weaker branch-dependent one).

All 5 real `lcall SUB_ECE82` sites (`0xF3C1E`, `0xF4D44`, `0xF54C9`,
`0xF5581`, `0xF562E`) push 2 far pointers (8 bytes) and clean only 4 of
them via `add sp,4` - on its face the same shape as `0xE951A`'s
mismatch. It isn't: `SUB_ECE82` skips `FUNC_3633_CE5B`'s own prologue
entirely (never sets its own `bp`), and the function's shared exit
(`mov sp,bp` / `pop bp` / `retf`) resyncs the stack against the
*inherited* `bp` from whatever enclosing function is actually live -
the same mechanism already established for `0x88729` and `SUB_F5F56`.
That means the simple push-vs-retf-immediate arithmetic that cleanly
confirmed `write_hw_shift_register`/`0xF4CE8` and cleanly ruled out
`0xE951A` doesn't mechanically apply here - the real `SP` delta is a
runtime quantity (depends on the live `bp`), not something static
reading alone can finish. Also confirmed `FUNC_3633_CE5B`'s true entry
point has zero real callers anywhere in the corpus, same "only ever
reached past its own prologue" pattern as `extract_strided_channel_
samples`/`SUB_F5F56`.

Net: a third clean instance of the shared-frame secondary-entry
mechanism, not a second `0xE951A`-style negative. Flagged the general
lesson (check for `mov sp,bp` in the shared exit before trusting the
push-vs-retf stack check) for whoever continues down the remaining
candidates (`0xEDDE2` at 4 callers, `0xEFD99` at 3, mostly
single-caller after that).

Updated `docs/decode-anomalies/landing-artifacts-and-jump-tables.md`
("Follow-up, 2026-10-10"), `TODO.md`, and `STILL_PENDING_DECODE.md` to
match.

## Named `0xECE82`'s host function and its structural twin from behavior, not callers

Followed up on the `0xECE82` trace above by identifying what
`FUNC_3633_CE5B` (its host) and the near-identical function right after
it in ROM actually *do*, independent of their messy callers - per the
project's "name from behavior, not from who calls it" convention.
Both are a "step to the previous/next alternate value" pair for a
multi-value menu item: check an alt-value count `[0x3D6]`, dispatch the
current item's `[0x1D10]` handler with a small command code (`2` if
stepping, `3` if there's nothing to step), then decrement/increment a
per-item step byte (`[0x3E3 + item index]`) with proper mod-`[0x3D6]`
wraparound and reformat it via `SUB_F5184`.

Renamed: `0xECE5B`→`step_item_subvalue_back_guarded` (real entry, zero
confirmed callers), `0xECE82`→`step_item_subvalue_back` (the
landing-artifact entry all 5 real callers actually use),
`0xECF19`→`step_item_subvalue_fwd` (structural twin, `inc` instead of
`dec`, no confirmed caller found by direct `lcall` encoding - named
from shape/pairing alone). Regenerated `sysrom_3532_3633_heuristic.lst`/
`.symbols.json` via `gen_disasm_mainrom_heuristic.py` (these addresses
are heuristic-reachability-only, so the proven-only `sysrom_3532_3633
.lst` and the committed `_readable.asm`/aligned-bin files are
unaffected - same pre-existing caveat as `extract_strided_channel_
samples`'s secondary entries).

Added a new "Per-item handler dispatch table (`[0x1D10]`)" section to
`VARIABLES.md` for `[0x464]`/`[0x1D10]`/`[0x466]`/`[0x3D6]`/`[0x3E3]`/
`[0x46C]`, and a "Found, 2026-10-10" section to `docs/acquisition-and-
plotting/mode-dispatcher-and-formatting.md`. Flagged, not resolved: the
`[0x1D10]`-dispatched handler now has 3 confirmed distinct command
codes (`2`/`3`/`4`) across different callers, looking like a generic
per-item message-dispatch convention rather than type-specific
arguments - what each code does isn't traced.

## Traced command code `4`'s dispatcher, found 2 more functions, corrected `write_hw_shift_register`'s reachability

Followed up on the flagged "3 command codes, not traced" thread by
reading `dispatch_item_handler_if_enabled`'s (`0xEDFFD`) full body.
Found it's a secondary entry into a larger real function, `0xEDF56`,
named `dispatch_item_change_notification`: branches on the current
item's `[0x466]` flag bits to call one of 3 unanalyzed helpers
(`SUB_F408E`/`SUB_F45A4`/`SUB_F47AB`) and/or dispatch the handler with
code `4`; a second internal-only block also calls `clamp_position_
counter_across_records(1,1,0)` before re-dispatching code `4` again.

Found and named `reset_current_item_to_table_default` (`0xEE0BB`),
immediately after `dispatch_item_handler_if_enabled`'s `retf`: resets
the current item index to the `[0x1D10]` table's own record-0 default
and reloads its behavior flags.

**Corrected a standing documentation error**: `MEMORY_MAP.md`/
`FUNCTIONS.md` previously described `write_hw_shift_register` as
reached via a fallback path inside `dispatch_item_handler_if_enabled`/
the `0xEE004` dispatch function. It isn't - that function `retf`s at
`0xEE0BA`, well before `write_hw_shift_register` (`0xEE13B`). The real
enclosing function is a large, not-yet-named item-list loop (`0xEE0F7`,
calls `compute_and_format_sample_delta_readout`/`clamp_position_
counter_across_records` repeatedly) that `write_hw_shift_register` is
a shared-frame secondary entry into - same mechanism as `0x88729`/
`SUB_F5F56`/`step_item_subvalue_back`. Fixed both files; flagged
`0xEE0F7` as the next good full-trace candidate in this cluster.

## Fully traced and named `0xEE0F7` -> `render_item_list_row`

Followed up on "`0xEE0F7` is the best next candidate" from the
previous section by reading its complete body (through its own
`retf 2` at `0xEE35B`).

Named it `render_item_list_row(item_index=[bp+6], row_index=[bp+8],
running_screen_position=[bp+0xa])`. It walks the `[0x1D10]` table's
`+4`/`+5` fields as a **linked-record chain** - `+4` is the index of
*another* record in the same table (re-multiplied by `0x10` and
re-applied to the `0x1D10` base), not a count as it first appeared;
`+5` of that linked record supplies the updated loop value - for
`[0x3E3+item_index]` iterations, calling `write_hw_shift_register`
once per step. This is the function `write_hw_shift_register` is a
shared-frame secondary entry into, finally located and traced -
explains its 8 external callers. Also calls `compute_and_format_
sample_delta_readout`/`clamp_position_counter_across_records`; its own
small-integer constants (`1`/`0xb`/`8`/`0xc`) belong to those
functions' argument conventions and are unrelated to the `[0x1D10]+6`
handler's command codes (`2`/`3`/`4`) - this function never dispatches
that handler, so the command-code question remains open. Has "last
row"/"past the end" branches (vs. `[0x462]`) that draw marker-box
icons via `draw_marker_box_and_update_position`, gated by `[0x1D10]
+0xE` bits `0x8`/`0x10`; a second flag pair `+0xA`/`+0xC` gates a call
to the still-unnamed `SUB_F43CC(0x57)`. Confirmed `SUB_EE15C`/`L_EE161`
in the heuristic listing are byte-overlap scanner artifacts inside
this function's own real instructions, not real control flow.
