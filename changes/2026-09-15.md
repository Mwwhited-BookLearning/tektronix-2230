## Comm ROM 160-2998-13 vs -14 byte diff

Picked up a long-standing `TODO.md` item: the two comm-ROM revisions
(Scope 1 runs `-13`, Scope 2 runs `-14`, but this project has only
ever disassembled `-14`) were known to differ but had never been
diffed at the byte/instruction level. A straight byte diff found only
**133 differing bytes total**, in exactly 3 runs: the expected 6-byte
self-ID header, plus two runs each starting at a 16KB-page boundary
(`0x4000`/`0xC000` file offset) - which is what the old TODO note
meant by "two ~16KB-aligned regions" (page-aligned *start*, not 16KB
*long*).

- **`0x84000`**: `-13` has a small, previously-undocumented
  config-check routine (`[0x0623]`/`[0x0002]`/`[0x05FA]`/`[0x05F7]`);
  `-14` has a truncated, non-NUL-terminated leftover copy of the ROM's
  own copyright string in the exact same 67-byte slot (the real,
  complete copy already exists at file offset `0x000a` in both
  revisions, already in `STRINGS.md`) - almost certainly a build/link
  artifact reusing the string constant to fill space, not new
  functional data. Flagged a disassembly-quality side effect: the
  existing heuristic layer for `160-2998-14` decoded these string
  bytes as instructions, producing a dozen spurious labels
  (`L_84005`, `FUNC_2998_4095`, etc.) that aren't real functions.
- **`0xC000`**: corrects a claim in
  `docs/comm-rom/address-map-and-cpu.md` that both comm-ROM pages 2
  and 3 carry the boot-stub far-jump (`ljmp 0xE64C:0000`) - true only
  for `-14`. A whole-image far-jump scan found `-13` has only the
  page-2 copy; page 3 in `-13` is ordinary mid-function code (a
  `push bp`/`mov bp,sp` function starting at `0x8BFCD` runs straight
  through the page boundary), patched over by `-14`'s added page-3
  boot stub.

Full writeup, hex dumps, and hand-disassembly in the new
`docs/comm-rom/revision-13-vs-14-diff.md`; `TODO.md` and
`docs/comm-rom/address-map-and-cpu.md` updated to point at it. Not
done: formally disassembling `-13`'s two changed regions into the
project's regular tooling (`gen_disasm_2998.py` etc.) - low priority
since `-13` isn't this project's baseline chip.
