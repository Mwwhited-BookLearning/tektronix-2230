## Fixed the "MI : Display controller : TIMEOUT" self-test failure

Prompted by "Fix the emulator as you expect." This TIMEOUT had been an
open item since 2026-09-16, previously attributed to `selftest_
display_irq_idle` (`0xE3F2C`). A fresh instruction-level trace
disproved that: `[0x1AEE]`/`[0x1AF2]` are both `0` immediately before
*and* after that function's `sti`/`cli` window, so its own pass branch
is taken, and it falls straight through into a second, separate
function, `selftest_display_irq_active` (`0xE3F99`), never previously
traced in this much detail.

That function's real mechanism: after committing a test vector draw,
it reads the Display Chip Interrupt Reset register (physical `0x41000`
- already named in Table 3-1 and flagged as "the leading suspect" in
`io_stubs.DISPLAY_CHIP_STUBS`'s own comment, but never wired up with
any actual side effect), then busy-polls `[0x1AEE]` for up to 100
iterations waiting for `INT2_HANDLER_EARLY` (`0xE5D67`) to OR
`[0x1AF2]` into it on an NMI tick. Nothing in this emulator ever set
`[0x1AF2]`, so the loop always exhausted and printed the TIMEOUT
message - confirmed as the exact source by decoding the function's two
string-table print calls against the real ROM string table (`0xFF7B0`
base): the first failure block's strings are literally "MI" / "Display
controller :" / " TIMEOUT"; a second, not-yet-observed failure block
later in the same function prints a different message, "MI / Display
controller : / unable to reset mi[splay controller]".

Fixed with a new `io_stubs.DisplayChipIrqStub`: on a read of `0x41000`,
sets both `[0x1AF2]` and `[0x1AEE]` directly (physical `0x1F02`/
`0x1EFE`, `DS=0x41`) instead of only `[0x1AF2]` and waiting for the
emulator's own synthetic, configurable NMI-tick cadence (`--tick-
interval`) to coincidentally land inside the test's ~400-instruction
polling window - real hardware's interrupt is architecturally
guaranteed to arrive within that budget, so tying the result to the
emulator's own arbitrary tick timing would model the emulator, not the
firmware. Installed after `DISPLAY_CHIP_STUBS`'s existing `FixedByte
Read(0x41000, 0x00, ...)` so the register's own read value is
unchanged (`0x00`, already correct) - this only adds the missing side
effect. Verified end-to-end: a full boot trace no longer prints either
of `selftest_display_irq_active`'s failure messages, and the self-test
sequence now progresses one step further into the separate, still-open
`ACQ_AB` address-line-walking-test failures.

Corrected `FUNCTIONS.md`'s entries for both `selftest_display_irq_idle`
and `selftest_display_irq_active` to reflect the fully-traced mechanism
and this attribution correction, and updated `emulator/docs/design.md`
and `TODO.md`'s stale references accordingly.

## User report: SELECT C1/C2 held at power-on suppresses UART debug output

User (from direct hands-on hardware testing): SELECT C1/C2 is a
momentary front-panel button; on the real instrument it must be held
*before* power-on for the "extended diagnostics"/RS-232 ASCII error
dump the service manual describes - not held, and the emulator showed
zero UART output at all, plus what looked like a crash into unmapped
memory shortly after.

That "crash" turned out to be a **real, separate emulator bug**: this
project's debugger never detected the CPU executing `hlt` at all.
Unicorn's `emu_start` silently returns on a real `hlt` (no error, no
stop reason) with `IP` already advanced *past* it. Nothing told any
caller a halt had happened, so a subsequent `run`/`step` call (every
one of this session's trace scripts did exactly this) resumed
execution from a CPU real hardware considers permanently stopped -
producing garbage register state that looked exactly like a wild jump
into unmapped memory. This happens on **every single successful
boot** (the ordinary end-of-boot "PRESS MENU KEYS TO CONTINUE" idle
halt) and happens to land at the same physical address (`0xF1611`,
`halt_cpu` - already documented in `docs/hardware-io/shift-register-
and-assert.md` as the firmware's own `assert()`/panic trap) as the
SELECT-C1/C2-held path, which made it look like a distinct crash
rather than the same ordinary halt reached by a different route.

Fixed by checking the raw opcode byte (`0xF4`) in the existing
per-instruction hook (`Debugger._on_code`) and stopping cleanly with an
explicit `"halted (hlt) at 0x..."` reason before the halt executes -
`IP` is left pointing at it, not past it. Unicorn's `UC_HOOK_INSN`
can't hook `HLT` directly on this version (confirmed via `UC_ERR_ARG` -
only `IN`/`OUT`/`SYSCALL`/`SYSENTER`/`CPUID` are supported), hence
checking the opcode byte instead. Verified stable across the same 4
tick intervals used to verify the display-controller fix above.

With the false "crash" cleared, the actual SELECT C1/C2 question
remains open but is now cleanly traceable: `self_test_dispatcher` does
still run when held, gated in part by `[0x1B7A]` (never written by any
code this project has disassembled in any of the 3 ROMs) and the
already-documented `[0x1B48]`. Held mode does measurably less total
work before halting (~984K vs ~2.07M instructions from
dispatcher-entry), not just silently suppressed prints. User's own
hypothesis, not yet checked: a real front-panel button press may fire
a hardware interrupt this emulator doesn't model at all - documented
as the leading next step in `TODO.md` and `emulator/docs/design.md`.

## Found the exact SELECT C1/C2 output-suppression mechanism; ruled out two fixes

User: "Keep going" on the open SELECT C1/C2 investigation. Compared
the full sequence of self-test sibling-function calls between a held
and unheld run (breakpointing all ~20 known sibling tests) and found
them **byte-for-byte identical** in order and count - the earlier
"held does ~2x less work" observation isn't from skipping tests, it's
from something inside each call doing less work. Traced a single
report-loop iteration side by side and found it: `print_string_far`
(`0xE0AF5`) checks `[0x1B48]==0` on entry and returns immediately,
printing nothing at all (not a shorter message - literally nothing),
which also explains the reduced instruction count (each suppressed
call also skips its expensive `wait_readout_tick` character-pacing
loop). `[0x1B48]==0` occurs exactly when SELECT C1/C2 is held alone.
This is real, disassembled ROM logic - confirmed dynamically twice
over (the flag-setup branch and the print-function's own gate) - not
an emulator stub gap.

That still directly contradicts the service manual's description of
this button (held should mean *more* output, not none). Chased two
concrete hypotheses to ground truth rather than guessing:
1. **"It's just a CRT mirror, the real dump goes out through the
   actual UART elsewhere"** - searched every reference to `0x6F0-
   0x6F7` in the disassembly. Disproved: `write_readout_port_byte`'s
   target (`0x40000+0x6F0`) is the exact same physical address already
   confirmed as the real UART's own data register
   (`io_stubs.InteractiveUartMock`'s mapping). It's the genuine UART,
   not a separate mirror.
2. **"Pressing a menu key afterward resumes into an extended-
   diagnostics continuation"** - built a real interrupt-injection wake
   for a halted CPU (reusing `timer.fire_interrupt`'s exact register/
   stack manipulation, the same mechanism the periodic NMI tick already
   uses) to test this properly, since naively skipping the `hlt` byte
   was already known to produce garbage. It works - the CPU does wake
   correctly - but the very next instruction after this specific `hlt`
   (`halt_cpu`, `0xF1611`) crashes into unmapped memory every time,
   regardless of how execution reaches it. This confirms `halt_cpu` is
   a genuine, intentional one-way trap (matching its other caller
   `assert_and_halt`'s already-documented "hlt never returns" shape),
   not a resumable wait state - "PRESS MENU KEYS TO CONTINUE" most
   likely means a real hardware reset of the microprocessor, not a
   resumption of the halted code. Reverted the auto-wake experiment
   (kept the simpler, clean "halted (hlt)" stop) since auto-waking
   every halt only trades a clean stop for a confusing crash here, with
   no upside found for this specific one.

Both dead ends were worth writing up in full (`emulator/docs/
design.md`, `TODO.md`) rather than silently discarding, since they
rule out real possibilities rather than just failing to find anything.
Remaining, still-open hypothesis: a real front-panel button *press*
(the physical event, not just the resulting static register bit) may
fire a hardware interrupt this emulator's button model doesn't -
`docs/interrupts/ivt-and-int255.md`'s "lead exhausted" conclusion only
covers code already reached, and the held/unheld call sequences are
now confirmed identical, so this would need an interrupt-install site
somewhere other than the code path already traced.

## Read the remaining unread comm-ROM span; found a second, undecoded dispatch table (not the SELECT C1/C2 mechanism)

Followed through on the "concrete next step" from the previous entry:
manually read the comm ROM's largest remaining unreached byte range
(`UNKNOWN_DATA.md` "Chip 2998" blocks 6/7, phys `0x08824C-0x088A57`,
~2KB) by hand rather than building more tooling.

Found it's a real, structured far-pointer table - not junk, not
string data. It ends exactly one byte before the already-confirmed
command-keyword-table cluster (`docs/comm-rom/command-keyword-
table.md`) starts, which is unlikely to be coincidental, but it uses a
different record format than that table's confirmed 6-byte/fixed-
segment-0xDE90 layout. Best-fit model: 4-byte `[offset][segment]`
records, 77% landing in a plausible ROM segment range, 41% of those
resolving exactly to an already-identified function entry point (far
above chance for a sparse label set). Working hypothesis: a companion
command-ID-to-handler-address table, complementary to the confirmed
table's command-ID-to-display-string mapping. Not fully solved - the
record boundaries aren't perfectly clean, and nothing in already-
reached code was found calling through this table's base address, so
what actually indexes it (and whether it's live code or orphaned) is
still open. Documented as new finding "6." in `docs/decode-anomalies/
unknown-data-deep-dive-2026-09-15.md`, cross-referenced from
`UNKNOWN_DATA.md`'s quick index.

Every plausible target this table resolves to is comm-ROM/main-ROM
*code* related to serial/GPIB command handling - nothing resembling
front-panel switch state. This closes the "unread comm-ROM span" lead
from `TODO.md`'s SELECT C1/C2 entry for good; the only lead left
standing is a pure hardware-level wiring effect outside any ROM's
reach, which no amount of further disassembly could settle.
