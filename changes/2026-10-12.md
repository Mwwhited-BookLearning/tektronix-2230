# 2026-10-12

## Found `[0x5fe]`'s write site; its exact numeric encoding remains an open loose end

Continued yesterday's SET-side acquisition-mode flag-family
investigation (`docs/comm-rom/command-keyword-table.md` section 5),
which had left one thing explicitly open: which command's
argument-parsing code actually *writes* `[0x5fe]` before the 8
SET-side flag-decoding functions (`FUNC_2998_C1FA`/`C22F`/`C264`/
`C2A6`/`C2E8`/`C301`/`C31B`/`C356`) read it.

**Write site found**: `FUNC_2998_43F0` (physical `0x8444C`) -
`mov al, byte ptr [0x608]` immediately followed by `mov byte ptr
[0x5fe], al`, inside a branch gated on a second pass through the
function's main loop (a structurally identical first-pass branch
writes the same `[0x608]` value into a sibling byte, `[0x606]`,
instead). No static caller was found by name, but `FUNC_2998_43F0`'s
address falls inside the comm ROM's parser-state handler table's
already-confirmed range (`0x83B1A`-`0x85098`, from the `[0x5A4]`/
`[0x72A]` jump-table work on 2026-10-11) - consistent with it being
reached only through that register-indirect dispatch, not a direct
call.

Traced `[0x608]`'s own origin further: it's set by
`FUNC_2998_5115`/`FUNC_2998_519A` (the letter-bucket table walkers,
resolved yesterday via `[0x6EA]`/`[0x6F6]`) from the matched letter
bucket's first record byte, then incremented once per rejected
candidate by `FUNC_2998_3048`'s forward abbreviation-matching scan
(`inc byte ptr [0x608]` at `0x831C5`). This is the same
letter-bucket-walk-plus-scan-increment mechanism already confirmed for
command-ID resolution - so `[0x5fe]` holds a per-match value tied to
whichever argument/value keyword (`ACCpeak`/`AVErage`/`PEAkdet`/
`SAMple`) the parser just matched.

**Tested and disproved**: whether `[0x5fe]`'s raw comparison literals
(`1`, `7`, `0x43`, `0x35`) simply equal table 1's global alphabetical
index of the matched keyword. Real indices (re-verified by an
independent manual byte-level walk of table 1 from `ABOrt`, not just
`disasm/comm_keyword_tables.json`): `ACCpeak`=1, `AVErage`=7,
`PEAkdet`=51, `SAMple`=63. `FUNC_2998_C1FA`/`C22F`'s literals `1`/`7`
match `ACCpeak`/`AVErage` exactly, but `FUNC_2998_C264`/`C2A6`'s
`0x43`(=67) and `FUNC_2998_C31B`'s `0x35`(=53) are off by `+4`/`+2`
from `SAMple`/`PEAkdet`'s real indices. Chased two possible
explanations for the growing offset and ruled both out:

- *Undercounted table-1 entries between `AVErage` and `SAMple`* -
  re-walked the raw bytes by hand with full per-entry debug output;
  got the identical entry count and boundaries as the JSON, so the
  extraction script isn't miscounting.
- *The metadata bytes between entries encode a distinct per-entry ID
  that could explain the gap* - checked directly; 1-byte metadata gaps
  are a bare `0x00`, and 3-byte gaps (`CURS2`, `INVert`, `PT.Off`,
  `RP`) are consistently `00 01 <ASCII char>`, where the char is the
  **first letter of the very next table-1 entry** (`CURS2`->`'D'`/
  `DEFault`, `INVert`->`'L'`/`LOCk`, `PT.Off`->`'R'`/`REF`, `RP`->`'S'`/
  `SAMple`) - a real structural field (plausibly a next-letter-bucket
  hint), but it doesn't encode anything resembling `[0x5fe]`'s
  comparison literals, and double-checking a 1-byte case (`AVErage`)
  against the raw bytes confirmed the heuristic's skip count was
  correct there too (not an early false-positive match).

So `[0x5fe]`'s write site and general derivation mechanism are now
confirmed, but the exact arithmetic turning a matched keyword into its
raw byte value is not - documented as an open loose end rather than
guessed at further. Importantly, this does **not** weaken yesterday's
flag-index-to-sub-argument mapping (`0x3a`=`REPetitive` etc.), which
rests on each flag's SET-side value-domain *size* and the block-6
GET-side push-order argument, neither of which depends on `[0x5fe]`'s
own numeric encoding scheme.

Also corrected a stale conclusion in
`docs/comm-rom/command-parser-token-scan-and-plot-handler.md`: its
2026-10-09 "`[0x6EA]`/`[0x6F6]` are address-reuse red herrings"
section predated yesterday's `init_far_pointer_table` decode and was
superseded by it (the comm ROM does write those offsets itself, via a
register-indirect copy loop the original grep couldn't see) - added a
pointer to the correct, already-resolved identity in `VARIABLES.md`
rather than leaving the file internally inconsistent.

## Ruled out a false lead on block 7's still-missing reader: main-ROM `[0x6fa]` hits are an unrelated plot-subsystem collision

While re-examining `[0x6FA]` (block 7's own base pointer, still with no
confirmed comm-ROM reader despite a deliberate search yesterday),
re-ran the "no reader found" grep across *both* ROMs instead of just
the comm ROM - and found the main ROM (`160-3532`/`3633`) references
flat offset `[0x6fa]` repeatedly (`sysrom_3532_3633_heuristic.lst`,
both the proven and heuristic listings, ~13 sites). Looked promising
at first, but traced it: the main-ROM `[0x6fa]` cell is written from
`[0x1ddc]+0x2be` (`[0x1ddc]` is already documented in `VARIABLES.md`
as general-purpose scratch RAM borrowed by many unrelated routines,
not a dedicated pointer) immediately before a call to
`update_plot_position` and a run of `[0x6f2]`/`[0x6f4]`/`[0x6f6]`/
`[0x6f8]`-style plot-scale-factor setup - i.e. this is a plot-subsystem
scratch record in the main ROM's own flat DS, unrelated to the comm
ROM's `[0x6FA]` byte. Same flat-offset-collision pattern already
documented for `[0x4EC]`/`[0x6EA]` elsewhere in `VARIABLES.md` - a
different ROM, different DS, unrelated byte that happens to share the
numeric offset. Block 7's reader remains genuinely unfound; this just
closes off one candidate explanation before it could cause a repeat
investigation.

## Checked (and ruled out) two leads on "which front-panel item do the main item table's indices 58/65/72/80/88 name"

Continuing down the open-items list: the 5 `ACQuisition` flag indices
(`0x3a`/`0x41`/`0x48`/`0x50`/`0x58`) are already resolved as
`REPetitive`/`HSRec`/`LSRec`/`SCAn`/`ROLl` via the comm-command
cross-reference (2026-10-11), but which specific record of the main
item table (`[0x1D10]`, the handler table `[0x464]` indexes) each
number names - orthogonal to that comm identity - was still
unlooked-up. Tried two concrete avenues:

1. **The table's own record fields**: `[0x1D10]`'s known fields
   (`+4`/`+5` chain link, `+6`/`+8` handler far pointer + flag,
   `+0xA`/`+0xC` secondary flag pair, `+0xE` behavior-flag byte - all
   from prior sessions' `render_item_list_row`/`dispatch_item_handler_
   if_enabled` traces) include no string/label field at all, so even
   if the records' live contents were read there'd be no name to find
   there directly.
2. **Literal `[0x464]` assignments**: grepped every one of the ~40
   `[0x464]` (current item index) references in the main ROM listing
   for a direct `mov [0x464], imm`-style assignment matching one of
   the 5 index values, hoping to tie a specific front-panel switch's
   handler to one of these indices by address. None exist - every
   assignment loads `[0x464]` from a register (`ax`/`dx`), meaning
   item-index selection runs through some not-yet-identified
   switch-ID-to-index lookup table rather than per-switch literal
   constants.

Also confirmed the records in question are pure RAM, not ROM-sourced:
the one 82-entry boot-init table found 2026-10-10 (destination range
`0x2090`-`0x21F0`) only reaches as far as `[0x1D10]` records 0-~22
(`0x10` bytes/record), nowhere near records 58/65/72/80/88. Resolving
this further would need either finding the switch-ID lookup table or
inspecting live RAM via the emulator - neither attempted this pass.
Given the real-world identity is already solid via the comm-command
mapping, this is now flagged as low-priority rather than pursued
further.

## The "dense cluster" (`0x88006`-`0x880F4`) is several unrelated small structures, not one table

Section 7 of `docs/comm-rom/command-keyword-table.md` had flagged 9
`init_far_pointer_table` entries packed into the narrow range
`0x88006`-`0x880F4` as "uncharacterized, dense cluster" across several
prior sessions, on the assumption they were plausibly one related,
still-undiscovered table. Raw-byte pattern-matching against that range
(treating it as fixed-stride records) had repeatedly failed to turn up
a consistent structure. This pass instead grepped each of the 9 flat
offsets for its own *runtime reader* (excluding the boot-init
`dest_offset` table-setup entry that merely sets the pointer) and read
every call site in context - which resolved 6 of the 9 offsets as
**5 unrelated structures**:

- **`[0x716]`/`[0x71A]`: a baud-rate table and a parity table feeding
  the RS-232 UART hardware.** Both are read together right after a call
  to `read_dip_switches_serial_config` (`0x8E4FF`-`0x8E524`, gated on
  `[0x4EC]!=0x1F`, the "Off Line" sentinel). `[0x716][[0x4EC]]` (the
  DIP-switch baud index) is OR'd with `2` and written to `es:[di+3]` of
  the `[0x6D6]` far pointer - the already-confirmed "Option UART/GPIB
  chips (I/O)" register bank (`MEMORY_MAP.md`, physical `0x406F0`-
  `0x406F7`); `[0x71A][[0x4ED]]` (the DIP-switch parity index) is AND'd
  with `0x3F` and written to `es:[bx+1]` of the same bank. `docs/
  options.md`'s text on UART `U1251` (an 8251) - "an internal baud rate
  generator... divided by software selectable ratios" - is consistent
  with a baud-index-to-register-byte table. Not distinguished: whether
  the byte is the 8251's own Mode-register field or a separate
  baud-generator-latch divisor code.
- **`[0x71E]`: a command-ID membership/validity list.** Read inside the
  command-ID-resolution function `FUNC_2998_57E5` (`0x857E5`) after
  `[0x608]`'s letter-match narrows to a small set of candidate command
  IDs. Loads `[0x71E]` or `[0x71E]+8` (selected by the device-variant
  byte `[0x732]+0x1F` - the already-confirmed `[0x1B83]` field - being
  `0x15`) and linearly scans for a byte matching `[0x608]`, gating later
  logic on membership. Plausibly a GPIB-only/RS-232-only or
  model-variant command allow-list; not confirmed which.
- **`[0x722]`: a short, literal null-terminated ASCII string, `"#H"`**
  (confirmed by direct byte read at its target, `0x880CC`: `23 48 00`).
  Printed via `print_string_serial` in two sibling functions - one
  follows it with two decimal fields split from `[0x612]` (shaped like
  a `"#H<hi>.<lo>"` version/revision tag, unconfirmed), the other with a
  raw-byte loop from a separate buffer at `[0x61E]`. Neither function's
  own caller (which comm command, if any, triggers either print) has
  been traced.
- **`[0x726]`: a per-command GET-response field-index list.** Read by
  `FUNC_2998_5B9B` (`0x85B9B`) in the same "config-flag index ->
  `compute_response_format_flags` -> `;`-separated field" loop already
  confirmed for `ACQuisition`'s block-6 GET response (section 4), but
  with a different literal byte sequence (9 config-flag indices, an
  `0xFE` separator/EOI marker, and a `0xFF 0xFF` terminator) - confirms
  this response-building mechanism is reused by at least one comm
  command besides `ACQuisition`. Which command is not yet identified.
- **`[0x72E]`: a 10-byte-stride record array.** Read by
  `FUNC_2998_373A` (`0x8373A`) indexed by `[bp+6]*10` (a caller-supplied
  argument). Each record's `+0`/`+2` word fields are compared, via the
  cross-ROM helper `SUB_E7753`, against a pushed pair from `[0x578]`/
  `[0x57A]`, with a `+9` flag bit (`0x80`) checked afterward - shaped
  like a numeric range/limit-check table. What `[bp+6]` and `[0x578]`/
  `[0x57A]` represent in real terms is not traced.

`[0x70E]`/`[0x712]` (the remaining 2 of the original 9 offsets) are
unaffected by this pass and remain as previously characterized
(unconfirmed baud-rate-text tokens / 2-letter mnemonic strings,
respectively) - still genuinely open.

**Net result**: the "dense cluster" framing itself - implying one
undiscovered shared table - was the obstacle; tracing actual readers
instead of pattern-matching raw bytes resolved 6 of 9 offsets in a
single pass, the same technique that resolved `self_test_dispatcher`'s
siblings in an earlier session.
