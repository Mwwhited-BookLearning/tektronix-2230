## Live mode: tick continuously while staying responsive to input

User request: "can we have a live mode where I can still push buttons
and send serial commands but the system ticks away in the background."
Until now, `step`/`run`/`continue` all called Unicorn's `emu_start` as
one long synchronous C call and disabled the input for the duration
(see the 2026-09-16 crash-fix notes above on why that call can't be
safely interrupted from another thread) - there was no way to interact
with a running emulator at all.

Added `Debugger.run_live(burst=2000)`: runs in short bursts instead of
one long call, draining a thread-safe `pending_actions` queue between
each burst - the only point where nothing is touching the Unicorn
engine, so it's always safe regardless of what a queued action does.
`queue_action(fn)` (thread-safe `queue.Queue.put`) is how another
thread hands it something to run; `stop_live()` just clears the plain
`live` bool, safe without a lock since a single attribute write is
already atomic under the GIL. `live [off]` in the REPL/TUI command set.

In the TUI (`tui.py`), `live`/F6 starts this on its own worker thread
*without* setting the busy flag or disabling the input - the whole
point is that typing, checkboxes, and DIP switches keep working. Every
front-panel checkbox/dropdown toggle and every typed command, while
live is active, goes through `queue_action` instead of touching `dbg`
directly from the main/input thread; `_launch` refuses `step`/`run`/
`continue` outright while live (those would call `dbg.run()`
concurrently with `run_live`'s own loop on another thread). Registers
keep refreshing live via the pre-existing `on_progress` callback path,
unaffected since it already runs from inside the hook.

Verified headless (Textual's `run_test()`): typed `live` leaves
`_busy=False` and the input still enabled; toggling a front-panel
checkbox while live actually flips the right register bit (confirmed
via `front_panel.status()`); typing `step` while live is refused with
a message instead of erroring; typing `serial ID?\n` while live is
accepted and queued correctly; `live off` stops it and re-enables
normal step/run/continue. Also confirmed directly against `Debugger.
run_live`/`queue_action`/`stop_live` alone (no TUI): a queued button
press applied between bursts, ~330K instructions ticked over 0.4s,
clean stop with no exception.

## A per-address memory/IO access counter

User request, prompted by real doubt about this project's own assumed
"outgoing serial" address (`write_readout_port_byte`'s diagnostic
banner never shows up on a real hardware serial capture at boot):
"could you add a memory address log that counts the reads/writes per
memory address and io address?" Added `io_stubs.AccessCounter` - plain
dicts keyed by address/port, `mem_reads`/`mem_writes`/`io_in`/`io_out`,
installed automatically for every run (`access` command shows the
summary, ranked by access count; `access clear` zeroes it). Verified
the IN/OUT hook mechanics directly first since I'd never used them in
this codebase before (`UC_HOOK_INSN` with `UC_X86_INS_IN`/`_OUT` -
confirmed the exact callback signature, and confirmed a hook
`return 0` for `in` matches Unicorn's own unhooked default exactly, so
installing this hook can't itself change what firmware observes).

Initial version required an explicit `watch <start> <end>` range,
reasoning that hooking the whole 1MB space would make a long
`continue` measurably slower. **Simplified per user request**: "can
you just create a dictionary structure so you only track addresses as
they are touched instead of every address?" - since a dict only ever
grows for addresses actually touched (nothing is pre-allocated for the
full range), there's no memory reason to require a range up front;
`install()` now just hooks the whole address space unconditionally
(Unicorn's own `begin=1, end=0` "every address" convention, the same
default already used for this project's `UC_HOOK_CODE` hook) and
`watch`/`unwatch` were removed entirely. Documented the one real cost
this doesn't remove: the hook still fires - and costs a Python call -

so it's not free, just no longer requiring the user to guess a range
in advance. Verified: 500K instructions with it always-on completed in
under a second and correctly recorded 71,064 distinct touched
addresses with real per-address read/write counts.

**Real gotcha found while verifying this against a known-hot
register**: watching `0x43FFA` (SWB2, a front-panel status byte) showed
`read=6030 write=6030` - an exact match. Traced this to every read-
override stub in this file (`FixedByteRead`, `InteractiveFrontPanel`,
etc.) calling `uc_eng.mem_write()` from *inside* its own `UC_HOOK_MEM_
READ` callback to make the CPU's read see the stubbed value - that
write-back itself fires the counter's separate `UC_HOOK_MEM_WRITE`
hook too. Documented clearly in both the class docstring and the
`access` command's help text: a nonzero write count only means real
firmware wrote there if the address isn't backed by one of this
project's own read-stubs.

**Used it immediately for real analysis**: read `enqueue_comm_char`'s
actual disassembly (physical `0x8F4E1`, comm ROM) - the real per-
character comm-ROM TX path, reached via `service_comm_tx_queue`. It
writes completely unconditionally (`les di,[0x6d6]; mov es:[di],dl`,
zero status-bit polling anywhere in the function) then calls `update_
comm_tx_ready_flag(0)` *after* writing - consistent with TX_READY
being enforced at the interrupt/mask-latch level, not by firmware
polling a status bit in a loop. This also surfaced a likely problem
with this session's earlier NVRAM-seeding fix: `[0x6D6]` is seeded
with `0x4000:0x06F8`, which this project's own `InteractiveUartMock`
treats purely as the Interrupt Mask Latch's "DR enable" byte with no
connection to the UART data register at all - meaning `enqueue_comm_
char`'s write and `set_comm_queue_busy`'s mask-latch write would land
on the exact same modeled byte, which doesn't make sense for real
hardware. That seeded pointer value was already flagged in `io_stubs.
py` as "the single most load-bearing, least-confirmed assumption" in
the NVRAM fix - this is independent evidence pointing at the same
weak spot, not a new unrelated worry. Flagged for the user to check
against the service manual (does the real chip block at `0x406F0`-
`0x406FB` really have a data register at `+0` distinct from a mask-
latch struct at `+8`, or is that one register modeled as two here?)
rather than guessing further.

## Found a real Unicorn bug: a global MEM_READ hook corrupts CPU execution

While testing the just-simplified always-on `AccessCounter`, a full
boot trace that had run cleanly to 60M+ instructions for months
crashed at instruction 3,318,839 writing to ROM - a real regression,
not a coincidence. Isolated with a minimal repro before touching
anything else: the same trace runs clean with no hook, or with only
write/IO hooks; adding *any* `UC_HOOK_MEM_READ` hook that overlaps the
stack - even a 256-byte range covering nothing else - reproduces the
identical crash at the identical instruction count every time. `trace
on` pinpointed the actual failure: an ordinary `retf` pops `CS=0x0000`
instead of the real return segment, right after a completely normal
table-walk loop and its own nested `retf` - the CPU then runs off into
low RAM as garbage "code" and crashes a few instructions later trying
to write to ROM. Ruled out the hook's own logic as the cause (a no-op
`return True` version crashes identically) and ruled out the "whole
space" `begin=1,end=0` convention specifically (an explicit `0-
0xFFFFF` range crashes the same way; a range confined to `0x40000+`,
away from where the stack actually was, never crashes). This is a
genuine Unicorn 2.1.4 defect, not a bug in this project's own hook
code - and a serious one, since it's silent memory corruption, not an
error.

**Immediate fix**: reverted `AccessCounter` to only install memory
*write* and I/O in/out hooks automatically (`install_io`, confirmed
safe over a full 25M-instruction run, byte-for-byte matching the known
590-TX-byte baseline) - `install_watch_range`/`watch`/`unwatch` for
memory *reads* are opt-in again, with the corruption risk documented
prominently in the class docstring and the `watch` command's own help
text, explicitly framed as diagnostic-only (never for a run whose
completion needs to be trusted), since there's no address range
provably safe from ever overlapping wherever the stack happens to be
at some point in a long run.

## Resolved the dump-content mystery: default `continue` is 25,000,000, not 2.5M

The user's `started-2500000.bin`/etc. dumps (and their "not installed"
string at `0x886`) didn't match a fresh reproduction run to literally
2,500,000 instructions - traced this down by first reproducing the
mismatch through the real `interactive.py` REPL (not just an ad-hoc
script, to rule out a test-harness difference), then testing the
hypothesis that a bare `continue` (no explicit count) was used, which
defaults to `--continue-length`'s own default of **25,000,000** in all
3 entry points. Confirmed: a fresh boot to exactly 25,000,000
instructions is byte-for-byte identical to `started-2500000.bin` - the
filenames' numbers were never raw instruction counts.

With the right instruction range in hand, traced the actual writer of
`"not installed"` properly (a `UC_HOOK_MEM_WRITE` watch on `0x886-
0x893` plus `trace on`, not text-search): `detect_comm_option_hw`
(~3.3M instrs) correctly detects the comm option present (`[0x1B83]=
0x14`); `check_comm_option_installed` (~4.7M) sets `[0x1BF9]=0x01`;
`check_comm_installed_gate`'s first call (~4.735M) sees it set and
proceeds normally. Then something between 4.735M-5.3M (very likely
`selftest_comm_readback`, already documented as requiring `0x4067C` to
read back *exactly* `0xD0` to pass) fails and **clears `[0x1BF9]` back
to 0** - so `check_comm_installed_gate`'s *second* call (~5.309M, for
the next of the "3 comm-board tests" it gates) now sees it cleared and

## A real write-then-readback coupling stub for the diagnostic latch output

User: "can you just hardcode that value for a test pass?" - tried
exactly that first (`comm_stat` fixed to `0xD0`), then traced the
actual disassembly of `selftest_comm_readback`'s check and found it's
mathematically impossible: it reads `comm_stat` *twice* (before and
after toggling Interrupt Mask Latch output 3D at `0x406FB` 0->1),
masks each to bits `0xC0`, shifts the first read's mask right by 2,
and ORs the two together - `(read1&0xC0)>>2 | (read2&0xC0)`. For a
byte that never changes between the two reads, this can only ever
produce `0x00`/`0x50`/`0xA0`/`0xF0` - never the required `0xD0`, for
*any* fixed value. Solving backwards showed the real requirement: bit
`0x40` fixed at 1 (matches the real captured `0x7D` baseline) and bit
`0x80` going `0`->`1` exactly when `3D` goes `0`->`1` - a genuine
write-then-readback coupling, the same class of gap `CommPresenceProbe`
already fixed for a different register pair.

Added `io_stubs.DiagCommLatchLoopback`. **First version didn't work** -
tried to persist the loopback bit by writing straight into `0x4067C`'s
underlying RAM from the `0x406FB` write hook; an isolated unit test
showed the bit never actually appeared on the next read. Root cause:
`FixedByteRead`'s own read hook for `comm_stat` unconditionally resets
that same underlying byte back to `0x7D` on *every* read, before this
stub's change could ever be observed - the familiar "any stub's write-
back inside a read hook can stomp a change" hazard, hit from the
opposite direction this time. Fixed by keeping the bit as the
instance's own plain attribute and overlaying it via a *read* hook on
`0x4067C` too (installed after `FixedByteRead`'s, on top of the
baseline, exactly like `InteractiveDipSwitches` already does for its
own bits) instead of trying to persist it through shared RAM.

Verified in 2 stages: an isolated unit test confirms the exact required
value (`(0x45&0xC0)>>2 | (0xC5&0xC0) = 0xD0`); the full boot trace now
shows `[0x1BF9]=0x1`/`[0x1BFA]=0x1` (comm self-test genuinely passes)
and `[0x886]` (the self-test result buffer) now reads `"FAILED"`
instead of `"not installed"` - a real, different outcome, not just a
forced pass. Execution now halts at 5,391,063 instructions on a real
`HLT` (not a crash) with `"POWER UP FAILURES / PRESS MENU KEYS TO
CONTINUE"` and `"MI : Display controller : TIMEOUT"` in the diagnostic
log - the firmware is waiting for a front-panel keypress instead of
auto-continuing through to completion the way the "not installed" path
did (590 TX bytes, `"Power up tests complete"`). This is a genuinely
different, deliberately-changed code path now, not the documented
known-good baseline - worth keeping in mind before comparing against
it in future sessions.

## Fixed a real DIP-switch polarity bug: active-low, not active-high

User shared a fresh `/DIAGNOSTICS/EXERCISERS/IO/INPUT_PORTS` exerciser
photo showing `comm_param`=`11110011` - different from the `0xF8`/
`0xF9` captured on 2026-09-13 - and asked "It looks like the values
for the state and parameters are inverted in the register." Clarified:
"When the comm parameter dip switches are 1 they show as 0 on these
numbers" - i.e. the PARAMETERS DIP switches are wired **active-low**
(switch physically ON pulls its bit to 0), while `InteractiveDip
Switches`'s `_on_param_read`/`_on_status_read` had it backwards
(active-high: ON set the bit to 1).

Fixed both hooks to start with all switch-bit positions high (1, "off")
and clear a bit only for each switch actually ON, instead of the other
way around - `self.switches[i] = True` still means "switch i is
physically ON," only the bit-translation direction changed. Verified
two ways: an isolated test toggling individual switches confirms the
bit-clear/set direction is now correct, and - the real proof - the
default switch pattern (`0011000000`, switches 3+4 ON, unchanged by
this fix) now produces `comm_param = 11110011` **exactly matching the
user's fresh photo**, byte-for-byte. Also confirmed no regression:
the full boot trace still halts at the same instruction (5,391,063)
with the same diagnostic-text output as the comm-latch-loopback fix
above - this bug was isolated to DIP-switch bit polarity only.
