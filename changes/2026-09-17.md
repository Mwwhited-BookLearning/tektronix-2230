## Live-updating registers, an interrupts/mask panel, and real hardware ground truth

User request: "I would like the registers and so on updated as the
system runs in the emulator so you can see the running values." Added
`Debugger.on_progress` - a callback fired periodically (wall-clock
throttled to 100ms, checked only every 1000 instructions so the check
itself doesn't add per-instruction overhead) during any step/run/
continue. `tui.py` wires this to `refresh_registers()`, so the panel
now updates live during a long `continue` instead of only once it
stops - verified via a headless test confirming the rendered widget
text (not just the internal counter) changes over time during a run.

Then: "add the interrupts and their masks to that area." Added
`Debugger.interrupts_status()`/`_interrupts_line()` - the CPU's IF
flag, the Option Interrupt Mask Latch's 4 outputs (`0D`-`3D`, read
live from `0x406F8`-`0x406FB`), the UART's own Rx/TxEN command bits
and resulting RxRDY/TxRDY pin signals, and the synthetic INT2 ticker's
fired/skipped counts - shown in both the REPL's `regs`/`interrupts`
commands and the TUI panel continuously. Then: "the TX queue should be
shows as well" - relabeled the UART status line for RX/TX symmetry
(`RX queue: N pending` / `TX queue: N sent`, the TX side having no
real backlog concept since `data_w()` completes "instantly" - see
`i8251.py`) and added explicit `RX_READY`/`TX_READY`/`TX_EMPTY`
status-bit display alongside the pin-level RxRDY/TxRDY signals.

## Real hardware ground truth from a live scope on COM3

User connected a real scope and offered to let me query it directly.
Probed with `pyserial` across several baud rates to find the current
DIP-switch setting; user confirmed **4800 baud, 8N1, DTR+RTS**. Got a
completely clean response set matching `docs/comm-rom/rs232-
breakthrough.md`'s documented protocol exactly: `ID?` -> `ID TEK/2230,
V81.1,VERS:14;`, `EVEnt?` -> `EVENT 0;`, `SET?` -> the full settings
dump - also newly confirming 4800 baud (not just the previously-
documented 1200) is reliable with hardware flow control asserted. The
very first `ID?` attempt showed a stale `STATUS 97` (Command Error),
traced to contamination from my own earlier wrong-baud probing before
switching to the correct settings - not a real protocol issue, cleared
by one `EVEnt?` call. This is now the live, freshly-reconfirmed target
the emulator work is aiming to reproduce, once the RS-232 interrupt
path is actually reachable.

User confirmed the plan going forward: "yes, I want you to fix the
emulator... if you step the code and see an address or io that isn't
functioning that you can't figure out, let me know and I will check
the hardware from the service manual" - the collaborative loop for the
NVRAM pre-seeding fix and whatever surfaces next.

## Implemented and verified the NVRAM pre-seeding fix

`io_stubs.seed_comm_nvram_defaults()` writes the plausible factory-
calibrated far pointer (`0x4000:0x06F8`) into `[0x6D6]`/`[0x6E2]`
(physical `0x8FED6`/`0x8FEE2`) at startup, in both the interactive
Debugger and emu.py. Docstring flags this as the single least-
confirmed assumption in the fix, per the user's own request to flag
uncertain hardware assumptions rather than guess silently.

Verified with a manually-constructed far-call, since the natural boot
trace still doesn't reach this code. Got the calling convention wrong
twice while building the test (wrong push order relative to `[bp+6]`,
then forgot to set `DS` to the comm ROM's flat-variable segment) -
both caught immediately by execution landing somewhere nonsensical,
not from the fix itself. With the test corrected, the result is clean:
`set_comm_queue_busy(0)` now writes `01` to both `0D` and `1D`
(unmasking DR and TBRE) at the real Interrupt Mask Latch, returns
cleanly, and the IVT is byte-for-byte unchanged before and after -
exactly right, and definitively not the IVT-corrupting behavior the
zero pointer caused before. Full self-test sequence re-verified
unaffected (590 TX bytes, identical to before).

Still open: the natural boot trace doesn't call this function on its
own yet - this fix makes the mechanism correct once something reaches
it, not the reaching itself. Finding that code path is the next target.

## Interactive front-panel controls: checkboxes, a dropdown, headers, an incoming panel

User requests: checkboxes/toggle buttons for front-panel buttons plus
dropdowns for mutually-exclusive values, then headers on every panel
and a small incoming-serial box above the outgoing one.

Added `Checkbox` widgets for the 14 genuine independent toggle buttons,
wired straight to `dbg.front_panel.set_button()`. Represented `A_ONLY`/
`B_ONLY` (both active-low bits in the same register, mutually exclusive
on real hardware) as a single 3-option `Select` dropdown instead of 2
checkboxes that could otherwise represent an impossible "both pressed"
state. `_sync_front_panel_widgets()` initializes every control to match
the real captured idle baseline (`SWB2=0x08`, `SWB1=0x44`) rather than
defaulting everything to unchecked - verified via a headless test that
`1K_4K` starts checked, the dropdown starts at `A_ONLY`, and toggling
either correctly flips the right register bits.

Every panel (`registers`, `incoming`, `front panel`, `outgoing`, `log`)
now has a `border_title` header. Added a small fixed-height `incoming`
panel showing the RX queue's actual contents continuously, refreshed
from the same place `refresh_registers()` already runs from rather
than a second call site.

scrollable on overflow; add up/down-arrow command history to the input.
