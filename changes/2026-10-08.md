# 2026-10-08

## Stroke-font `[0x1DB0]`-reader family turned out to span both main-ROM chips, not just `160-3633`

Picked the stroke-font glyph-table investigation back up per an
explicit request to keep digging rather than close it out as likely
dead code. A direct grep for every `[0x1DB0]` reference across both
proven and heuristic listings for *both* main-ROM chips at once (never
run exactly this way in prior sessions - earlier sessions had only
ever examined `160-3633`) turned up two new things:

- A third sibling within `160-3633` itself, immediately before the
  already-tracked `FUNC_3633_E60C`/`FUNC_3633_DF56` - structurally
  identical (same `[bp+6]` char argument, same `shl` x2 index into
  `[0x1DB0]`, same `[0x45E]`-based output), `ref_count: 0`.
- Three entirely new readers in **`160-3532`**, the other main-ROM
  half - a branch of this investigation nobody had opened before.
  Same lookup mechanism, but writing through a different buffer
  (`[0x6AE]`, offset via `(ES-DS)<<4` rather than a flat add) with a
  separate accumulator (`[0x6AA]`). Crucially, all three share the
  `[0x1C02]` second-plane-offset variable with `160-3633`'s own
  family - real evidence both chips compile the same underlying
  display-list-append logic, not just a coincidental resemblance. A
  fourth, adjacent `160-3532` function shares the same output buffer
  but draws a repeating tick-mark pattern instead of reading
  `[0x1DB0]` - part of the same output cluster, not a glyph reader.

Ran the same multi-method caller search already exhausted on the
`160-3633` pair against all four new `160-3532` functions: zero hits
in any listing, and an independent Ghidra decompile cross-check agrees
- for the first of the four, Ghidra's own auto-analysis didn't even
create a function boundary there, consistent with code unreached from
any entry point either tool can find. Net result: the known footprint
of this mechanism is now **6 functions across both main-ROM chips**,
still only one (`draw_readout_char`, already confirmed dead on this
project's real comm-equipped hardware) provably reachable.

Since the mechanism itself (not just its reachability) is now
confidently understood for all 6, named them in `disasm/
gen_disasm_x86.FUNCTIONAL_NAMES` (`draw_readout_char_dup1`/`_dup2` for
the `160-3633` siblings, `draw_readout_char_3532_1`/`_2`/`_3` plus
`draw_tick_marks_3532` for the `160-3532` cluster) and regenerated
`disasm/sysrom_3532_3633.lst`/`_heuristic.lst` and both `.symbols.json`
files. Per explicit follow-up request, also applied the same names to
the local Ghidra project via `decompile/apply_names.py` (after
discovering the Ghidra install itself had moved to `C:\repo\tools\
ghidra` - `pyghidra.start()` needed `GHIDRA_INSTALL_DIR` pointed there
explicitly) and regenerated the two affected decompiled-C exports
(`decompile/exports/160-3633-14.c`/`160-3532-14.c`). Added `[0x6AE]`/
`[0x6AA]`/`[0x1C02]` to `VARIABLES.md` (previously undocumented despite
`[0x1C02]` already being referenced in `plot_readout_point`'s
`FUNCTIONS.md` entry) and new `FUNCTIONS.md` rows for all 6 renamed
functions.

## Naming hygiene sweep: found and fixed stale `SUB_`/`FUNC_` leftovers across the docs

Per a follow-up request to keep improving naming, cross-checked every
`SUB_XXXXX` placeholder still appearing in prose across `FUNCTIONS.md`/
`VARIABLES.md` against the live `disasm/gen_disasm_x86.FUNCTIONAL_NAMES`
dict. Found two kinds of drift:

- **Two true duplicate rows**: `0x97905` had both a stale, tentative
  `advance_comm_input_state` row (from an earlier, shallower pass) and
  the fuller, confirmed `parse_next_gpib_command_byte` row it was later
  superseded by - both survived in `FUNCTIONS.md` at once. Same thing
  for `0xE094B`/`0xE097B` (`init_selftest_report_record`/
  `append_selftest_report_char`), which still had their original
  unnamed `SUB_E094B`/`SUB_E097B` rows sitting alongside the renamed
  ones. Merged the one genuinely new fact each stale row had (a
  `[0x732+0x97]` flag-toggle detail; a "only one call site" note) into
  the surviving confirmed row, then deleted the stale duplicates.
- **~20 stale prose mentions**: rows for already-renamed functions
  (`enqueue_comm_char`, `reinit_comm_channel`, `run_selftest_sequence`,
  `update_plot_position`, `notify_comm_rom_a`/`_b`,
  `selftest_measure_mode`, `selftest_display_result_mode`,
  `selftest_comm_loopback_a`/`_b`, `clear_selftest_status_flags`,
  `print_selftest_report_line`, `print_unsigned_decimal_serial`, etc.)
  still referred to their own callees by old `SUB_XXXXX` placeholder
  names in descriptive text, even though those callees had real names
  by the time the describing row was written. Updated every one to the
  real name. Extended the same check to `docs/self-test/
  dispatcher-and-siblings.md`, `docs/self-test/hardware-probes.md`,
  `docs/acquisition-and-plotting/mode-dispatcher-and-formatting.md`,
  `JUMP_MAP.md`, `PSEUDOCODE.md`, and `STRINGS.md` - fixed the live
  ones, left dated `changes/*.md` entries alone (append-only by
  convention), and left a few deliberately-historical "found while
  renaming `SUB_X`/`SUB_Y`" narrative mentions intact but annotated
  with "(now `real_name`)" so they stay useful without rewriting the
  history they're describing.

No mechanism/fact claims changed - this was pure name-drift cleanup,
not new analysis. Confirmed via a script cross-checking every
remaining `SUB_`/`FUNC_` token in `FUNCTIONS.md`/`VARIABLES.md` against
`FUNCTIONAL_NAMES` that everything left really is still unnamed.
